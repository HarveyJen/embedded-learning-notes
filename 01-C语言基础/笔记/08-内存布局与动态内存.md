# 08 · 内存布局与动态内存

**这一篇讲什么**：程序运行时，内存不是一个大杂烩，而是像小区一样**分区管理**——代码住哪儿、全局变量住哪儿、临时变量住哪儿、向系统"租房"住哪儿，各有各的区域和规矩。搞懂分区，你才能理解"局部变量为什么函数一结束就没了""malloc 的内存为什么要自己还""单片机 RAM 为什么会爆"。

## 1. 程序的内存分区（必考）

**这是什么**：C 程序一启动，系统（准确说是"启动代码+操作系统/裸机启动文件"）就把内存划成几个功能不同的区。类比一栋公寓楼：底层是**只读展示厅**（代码段，谁也不许改），中间是**长租房**（数据段，全局/静态变量整个程序都住着），上面是**日租公寓**（堆，随用随租）和**会议区**（栈，函数开会用完就撤，一层层往上摞）。

C 程序内存从低地址到高地址：

```
高地址
┌──────────────┐
│    栈 stack   │ ← 局部变量、形参、函数调用信息（向下增长）
│      ↓        │
│      ↑        │
│    堆 heap    │ ← malloc 分配（向上增长）
├──────────────┤
│ 全局数据段 .data │ ← 已初始化的全局/静态变量  int g = 5;
├──────────────┤
│  BSS 段 .bss  │ ← 未初始化的全局/静态变量（自动清0）  int g;
├──────────────┤
│ 代码段 .text  │ ← 机器码 + const 常量 + 字符串常量（只读）
└──────────────┘
低地址
```

| 分区 | 存放 | 生命周期 | 嵌入式对应 |
|------|------|----------|-----------|
| 栈 | 局部变量、形参 | 函数运行期 | MCU 里通常只有几 KB，深递归/大数组爆栈 |
| 堆 | malloc 的内存 | 手动 free | 很多小型 MCU 不用堆 |
| .data | 已初始化全局/静态 | 程序全程 | 启动时从 Flash 拷到 RAM |
| .bss | 未初始化全局/静态 | 程序全程 | 启动时清零 |
| .text/rodata | 代码、const | 程序全程 | 放 Flash，不占 RAM |

> 读表补充——**栈（Stack）为什么"向下增长"、堆（Heap）为什么"向上增长"**：栈和堆从中间相向而行，中间空着的才是自由空间。函数嵌套越深、局部变量越大，栈占得越多；malloc 越多，堆占得越多。两头一碰面（比如深递归 + 大量 malloc），就是"内存爆了"。**栈像叠盘子**：调用一个函数摞一个盘子，返回就端走一个，永远只动最上面那个（所以函数返回后它的局部变量就"没了"）。

> 嵌入式视角：**RAM 占用 = data + bss + 堆 + 栈**；**Flash 占用 = text + data**。Keil 编译完显示的 `Program Size: Code+RO-data+RW-data+ZI-data` 就是这个。
> 对号入座：Code ≈ .text，RO-data ≈ 只读常量（const），RW-data ≈ .data，ZI-data ≈ .bss（Zero Initialized）。前两者进 Flash，RW 要占 RAM，ZI 上电时在 RAM 里清零。

验证代码：

**这段代码要做什么**：把住在各个区的变量地址打印出来，亲眼看一次"分区"——地址会呈现明显的分段规律。

```c
#include <stdio.h>
#include <stdlib.h>
int g_init = 10;          // .data
int g_zero;               // .bss
static int s_var = 20;    // .data
int main(void) {
    int local = 0;                       // 栈
    static int s_local = 30;             // .data（static 局部变量在数据段！）
    int *heap = malloc(4);               // 堆
    const char *str = "hello";           // 字符串常量在只读区
    printf("code %p\n data %p\n bss  %p\n heap %p\n stack %p\n",
           (void*)main, (void*)&g_init, (void*)&g_zero, (void*)heap, (void*)&local);
    free(heap);
    return 0;
}
```

## 2. malloc / calloc / realloc / free

**这是什么**：堆区的"租房三件套 + 退租"。`malloc` = 按面积租房（房里可能有前租客的垃圾，不清扫）；`calloc` = 按面积租房并打扫干净（清零）；`realloc` = 换更大的房（家具搬过去，但门牌号可能变）；`free` = 退租。**租了的房子必须退，不退就永远占着（内存泄漏）**。

**这段代码要做什么**：演示四种操作的标准搭配。

```c
#include <stdlib.h>

int *p1 = (int *)malloc(10 * sizeof(int));   // 分配未初始化内存，失败返回 NULL
int *p2 = (int *)calloc(10, sizeof(int));    // 分配并清零
p2 = (int *)realloc(p2, 20 * sizeof(int));   // 扩容（内容保留，地址可能变）
free(p1); free(p2);                          // 用完必须释放
```

读法拆解：
- `malloc(10 * sizeof(int))`：申请 10 × 4 = 40 字节。**必须乘**——malloc 只认字节数，写 `malloc(10)` 只租到 10 字节，装第 3 个 int 就越界了；
- 返回值是 `void *`（不知道你拿去装什么），所以前面加 `(int *)` 转回具体类型；
- `calloc(10, sizeof(int))` 两个参数：10 个元素 × 每个多大，并且全部填 0；
- `realloc` 扩容后**必须用返回值**——原地扩不动时它会在别处新开一块并把旧内容搬过去，旧地址作废。

**使用四步曲（规范）**：
1. 检查返回值是否 NULL；
2. 使用中不越界；
3. 用完 free；
4. free 后立刻置 NULL，不再使用。

```c
int *arr = malloc(n * sizeof(int));
if (arr == NULL) {
    /* 处理分配失败：嵌入式里通常报错并进入安全态，而不是硬着头皮继续 */
    return -1;
}
/* ... 使用 arr ... */
free(arr);
arr = NULL;
```

## 3. 常见动态内存错误（面试必问）

**这是什么**：动态内存的坑全部源于一条规则——**堆内存的生杀大权完全交给你**：malloc 才有、free 才死、free 之后就作废。以下 6 种错误，每一种都是把这条规则破坏了一角。面试时能主动讲出这 6 条，比背概念加分得多。

**这段代码要做什么**：逐个演示 6 种典型错误（只在测试环境里跑！）。

```c
// 1. 忘记 free → 内存泄漏（长时间运行的设备会耗尽内存）
void leak(void) { malloc(100); }

// 2. 重复释放 → 堆结构损坏，行为未定义
free(p); free(p);

// 3. free 后使用（悬空指针）
free(p); *p = 1;

// 4. 越界写：malloc(10) 却写第 11 个元素 → 破坏堆管理元数据

// 5. realloc 错误用法
p = realloc(p, size);        // 失败返回 NULL，原内存也丢了！
// 正确：
void *tmp = realloc(p, size);
if (tmp) p = tmp; else /* 保留 p，处理失败 */;

// 6. free 栈地址 / 只 free 后半段 / free 非起始地址 → 未定义行为
```

> 动态分配的内存**起始地址**才是 free 的凭证；`free(p + 1)` 是错的。
> 记忆口诀：**谁租的谁退、退整不退半、退一次就好、退了别再住**（对应泄漏、偏移 free、重复 free、悬空指针）。

## 4. 嵌入式为什么少用 malloc（重要思想）

**这是什么**：不是 malloc 不好，而是嵌入式设备"命薄"——RAM 小、要跑好几年、出了错没有人工重启。租房模式（随用随租）在这种环境下风险高，所以业界更倾向"盖房时就规划好房间"（静态分配）。理解这一节的思想，比会用 malloc 更重要。

1. **碎片化**：频繁 malloc/free 把堆切成碎片，明明总空间够却分不出连续块；
2. **不确定性**：分配耗时不可预测 → 硬实时系统不能容忍；
3. **泄漏风险**：设备 7×24 运行，小泄漏就是致命事故；
4. 小 MCU 堆区可能根本没开（Keil 默认 heap=0）。

**嵌入式替代策略**：
- **静态分配**：全局/静态数组、结构体，编译期确定，永不泄漏；
- **内存池**：预先划好 N 块定长内存，用链表管理，申请归还 O(1)（FreeRTOS 的 heap_4 就是带合并的池方案）；
- 栈上临时小缓冲区（注意别太大）。

> 原则：**MCU 裸机开发 → 尽量全静态；Linux 应用层 → 正常用 malloc，但要配对。**

## 5. 动态内存经典项目：动态通讯录（阶段验收项目）

**这是什么**：把本篇 + 笔记06（指针）+ 笔记07（结构体）串起来的验收项目：通讯录人数不固定，所以联系人数组放堆上，人满了就 realloc 扩容。看懂 `grow` 函数，realloc 的正确用法就掌握了。

**这段代码要做什么**：定义联系人结构体和"通讯录"结构体（后者持有指向堆数组的指针、当前人数、容量），并实现自动扩容。

```c
typedef struct {
    char   name[16];
    char   tel[16];
    int    age;
} Contact;

typedef struct {
    Contact *data;      // 指向堆上的数组
    int      size;      // 已用人数
    int      cap;       // 容量
} AddressBook;

/* 增容逻辑 */
int grow(AddressBook *book)
{
    int newcap = (book->cap == 0) ? 4 : book->cap * 2;
    Contact *tmp = (Contact *)realloc(book->data, newcap * sizeof(Contact));
    if (tmp == NULL) return -1;
    book->data = tmp;
    book->cap  = newcap;
    return 0;
}
/* 增删改查 + 排序 + 退出时 free(book->data) */
```

grow 运行逻辑逐段拆解：
- `newcap`：第一次容量给 4，之后每次翻倍（4→8→16）——翻倍策略让扩容次数是 O(log n)，比每次只加 1 高效得多；
- 用临时指针 `tmp` 接 realloc 的返回值（第 3 节错误 5 的正确姿势），确认不是 NULL 才写回 `book->data`；
- 整个函数体现"扩容三部曲"：算新容量 → realloc 到临时变量 → 成功才替换。
