# 05 · 内存管理与中断处理

> 目标：heap_1~5 五方案选型；FromISR 中断委托全套纪律；栈溢出的排查与根治。

## 1. FreeRTOS 内存方案 heap_1~5（面试常问）

这一节回答"内核的 malloc/free 长什么样、五种方案怎么挑"。内核堆就是一大块静态数组，heap_*.c 决定"怎么切、怎么收"。

类比**五种食堂打饭制度**：heap_1 = 打一次管到底（餐盘只发不收，最省心也最死板）；heap_2 = 餐盘回收但不拼桌（回收了空位，但相邻空位不合并不利用，久了一地碎渣）；heap_4 = 回收还拼桌（相邻空位合并，通用首选）；heap_3 = 外包给标准库 malloc（线程安全自己兜底）；heap_5 = 多场地联营（几块不连续 RAM 统一调度）。

FreeRTOS 的堆（`ucHeap[]` 静态数组，大小 = configTOTAL_HEAP_SIZE）由 heap_*.c 决定分配策略：

| 方案 | 策略 | 适用 |
|------|------|------|
| heap_1 | 只分不收 | 任务/队列建完永不动——最简单最安全 |
| heap_2 | 分块回收，**不合并**相邻空闲块 | 大小固定的块反复分收 |
| **heap_4** | 回收 + **相邻空闲块合并** | **默认推荐**：动态建删对象、碎片友好 |
| heap_3 | 包 malloc/free（用 libc 堆） | 特殊定制（线程安全要自保证） |
| heap_5 | 多段不连续内存池 | RAM 分裂在两块的芯片（如外挂 SRAM） |

**嵌入式内存原则**（呼应 C 笔记08）：
- **能静态就静态**：任务/队列在启动时建好，运行期不再 malloc——"启动期分配，运行期只使用"；
- 必须 malloc 时用 `pvPortMalloc/vPortFree`（内核堆），**绝不用裸 malloc**（与 ISR/任务混用非线程安全且堆碎片不可控）；
- `xPortGetFreeHeapSize()`/`xPortGetMinimumEverFreeHeapSize()` 监控水位（最低水位逼近 0 = 要加内存了）。

pvPortMalloc / vPortFree 三个关键行为：**会阻塞吗？** 不会——失败直接返回 NULL（所以返回值必须查），不让你等；**超时是什么单位？** 无超时概念，成败只看返回值；**ISR 里能不能用？** 不能——分配要走内核临界区，中断上下文禁止调用（中断里需要的缓冲提前静态备好）。

## 2. 栈 vs 堆（RTOS 新手最容易混的两个栈）

这一节先把两个最容易混的"内存池"掰开：任务栈和内核堆是**两个独立的池子**，溢出/耗尽的症状也完全不同——症状不同，排查方向才不同。

| | 任务栈 | 内核堆 |
|---|--------|--------|
| 谁用 | 每个任务的局部变量/调用深度 | 动态创建的任务控制块/队列/信号量本体 |
| 大小 | xTaskCreate 参数（字） | configTOTAL_HEAP_SIZE |
| 溢出症状 | HardFault/数据诡异损坏 | 创建返回 NULL |

## 3. 栈溢出：RTOS 头号杀手

这一节回答"任务栈为什么会爆、爆了长什么样、怎么防"。先建立画面，再谈工具。

任务栈像**一杯水**：函数每调深一层水位涨一截（局部变量、返回地址都往里放），溢出 = 水漫过杯口泼到邻桌——泼坏相邻任务的栈或内核堆，所以症状不是"当场死"，而是"诡异"。

**症状诡异**（不是必死）：偶发 HardFault、某变量莫名被改、任务串台——因为溢出踩的是相邻任务栈或堆。

**两层防线**：
1. **检测**：`configCHECK_FOR_STACK_OVERFLOW=2`（方法2：栈底填 0xA5 水印 + 切换时校验指针边界）+ 钩子函数 `vApplicationStackOverflowHook()` 里记录是哪个任务；
2. **定量**：`uxTaskGetStackHighWaterMark(NULL)`——历史最少剩余（字）。**工程习惯**：跑满全部功能路径后查各任务水位，剩余 < 30% 就加栈。

uxTaskGetStackHighWaterMark 三个关键行为：**会阻塞吗？** 不会，扫一遍水印立即返回；**返回值什么单位？** "字"（4 字节）——返回 200 = 只剩 800 字节，读数别乘错；**ISR 里能不能用？** 不能，在任务里调用（传 NULL 查自己，传句柄查别人）。

**涨栈大户**：局部大数组（改静态/指针传递）、printf 家族（栈深，几百字节起步）、深递归（嵌入式尽量别用）。

## 4. 中断处理：FromISR 全家纪律

这一节回答"中断里怎么安全地跟 RTOS 打交道"。一句话记住核心矛盾：**中断必须快进快出，而 RTOS 大量 API 会睡觉——所以中断里只能用"特制的不睡觉版"**。

**核心规则：ISR 里不能阻塞**（中断没有"睡醒"机制），因此所有可能阻塞的 API 都有 `_FromISR` 变体。

为什么 ISR 不能阻塞？正确姿势是**快递员把包裹放前台（信号量/队列），喊一声就走**；若快递员堵在你家门口死等签收，整栋楼的其他快递全停摆——中断期间同级/更低优先级中断不响应，调度也停摆，系统"半身不遂"。

```c
void EXTI0_IRQHandler(void)
{
    BaseType_t woken = pdFALSE;
    /* 正确三件套 */
    xSemaphoreGiveFromISR(evtSem, &woken);   /* 1. FromISR 版通信 */
    portYIELD_FROM_ISR(woken);               /* 2. 请求切换（若有更高优先级被唤醒） */
    /* 3. 清外设标志（STM32 层的事，别忘了） */
    EXTI->PR = EXTI_PR_PR0;
}
```

这段代码做什么：演示中断委托的标准三件套——发事件、请求切换、清标志，一行都不能少。

关键行拆解：

- `xSemaphoreGiveFromISR(evtSem, &woken)`——放旗的中断版：绝不阻塞、绝不当场切换调度；若唤醒了更高优先级任务，它把 woken 写成 pdTRUE（"带话"给内核）；
- `portYIELD_FROM_ISR(woken)`——把话递到：中断退出时直接切到高优先级任务，而不是回到被打断的任务再绕一圈；
- `EXTI->PR = EXTI_PR_PR0`——清外设挂起标志，这是 STM32 层的规矩，与 RTOS 无关但忘写会疯狂重入。

**一次"中断→任务"的完整时间线**（把三件套串起来）：

- 第 1 步：ADC 转换完成，硬件跳进 ISR——此刻 CPU 在**中断上下文**，没有"任务"身份，睡不得；
- 第 2 步：GiveFromISR 放旗：旗挂上、等旗的任务标为 Ready，**到此为止，不切换**；
- 第 3 步：GiveFromISR 发现被唤醒任务优先级更高 → woken = pdTRUE；
- 第 4 步：portYIELD_FROM_ISR 看到标记 → 中断退出时**直接切换**到高优先级任务（微秒级响应）；
- 第 5 步（对照：忘写第 2 件套的后果）：也能跑，但高优先级任务要干等到下一个 tick 才被调度——**最多 1ms 的隐形延迟**，在硬实时路径上就是偶发超时。

**三条铁律**：
1. 只用 FromISR 版 API（普通版内部可能请求调度 → 中断里切换 = 死机）；
2. `portYIELD_FROM_ISR(woken)` 别忘写——不写也能跑，但高优先级任务要等下一次 tick 才被调度（**延迟最多 1ms 的隐形 bug**）；
3. **ISR 尽量短**：只"收数据+发事件"，处理全交给任务（01 篇优先级设定"紧急且短"原则）。

**中断优先级与 RTOS 的隐藏契约**（F103 专属坑，必须设 `NVIC_SetPriority` 对齐）：先讲为什么有这契约——内核进临界区时要"屏蔽"会调内核 API 的中断，但它屏蔽不到优先级数值 0~4（更高）的中断；所以规定只有数值 ≥ 5 的中断才允许调 FromISR API，更高的中断"内核管不到"，碰了就是玄学事故。
```
configMAX_SYSCALL_INTERRUPT_PRIORITY = 5（CubeMX 默认）
→ 优先级数值 5~15 的中断：可以用 FromISR API（会被内核管理）
→ 0~4（数值更小=更高）：不能调任何 FreeRTOS API（内核管不到它）
违反 = 断言 configASSERT 命中或玄学死机——CubeMX 里 SysTick/PendSV 固定最低 15
```

## 5. 中断委托标准模式汇总

这一节是速查表：拿到一个中断场景，按"事件 / 数据 / 广播"三问选委托方式。

| 中断场景 | 委托方式 |
|----------|----------|
| "事件发生了" | 二值信号量 Give / 任务通知 Give |
| "来了一批数据" | 队列 SendFromISR（字节/帧） |
| "多个事件源" | 事件组 SetBitsFromISR |
| 数据量巨大 | DMA 循环 + 半满/全满中断只发通知（STM32 篇 DMA 收口） |

## 6. 常见坑

| 坑 | 现象 |
|----|------|
| 运行期频繁 pvPortMalloc/Free | 堆碎片化 → 明明总量够却分配失败（heap_4 也救不了高频长短混合） |
| ISR 调普通 API | configASSERT 命中/死机 |
| 忘 portYIELD_FROM_ISR | 隐形 1ms 延迟（最难查的"偶发不实时"） |
| 高优先级中断里调 FromISR | 违反 SYSCALL 优先级契约 → 玄学故障 |
| 栈只给默认 128 字 | 深调用/printf 后溢出 |
| heap 用量不监控 | 某天创建队列失败，排查半天发现堆见底 |

## 7. 章节小结

- 内存：静态优先、heap_4 通用、heap_5 救分裂 RAM；水位监控是习惯不是选修
- 任务栈 vs 内核堆分清；栈溢出两层防线=检测钩子+水位定量
- ISR 纪律：FromISR + portYIELD_FROM_ISR + 短；中断优先级契约（≥5 才能调内核 API）
- 委托选型按"事件/数据/广播"分流；大流量 DMA+通知收口

## 课后思考题

1. 为什么嵌入式鼓励"启动期分配，运行期只使用"？（运行期分配=不确定性：碎片/失败时机不可控；嵌入式生命周期内资源需求固定，把不确定性消灭在开机自检阶段）
2. 方法 2 栈溢出检测为什么能抓住"溢出后已返回"的案例？（0xA5 水印涂在栈底区域，溢出踩过必然破坏水印，下次切换检查即暴露——事后取证式检测）
3. portYIELD_FROM_ISR 忘写为什么"大多数时候没事"？（唤醒的任务要等下一个 tick 才被调度，若它本来就周期跑，1ms 延迟无感；但对硬实时路径就是偶发超时——"低概率高伤害"类 bug 的典型）
