# 04 · 事件组与软件定时器（含任务通知）

> 目标：多事件同步（事件组）、定时回调（软件定时器）两件套；顺带掌握"性价比之王"任务通知。

## 1. 事件组：多条件齐活才开工

这一节回答"要等**多个条件**同时（或任一）成立才开工，用什么工具"。信号量是一面旗，事件组是**一排旗（24 个位）**，还支持指定"全齐"或"任一"两种等法。

**问题**：开机自检要"MPU6050 OK + Flash OK + 网络注册 OK"三个都完成才进主界面——用三个信号量轮询太丑。
**事件组 = 一组事件位（24 位——FreeRTOS 拿一个 32 位整数的低 24 位当事件位，高 8 位内核自用，所以上限是 24）+ 与/或等待**：

```c
EventGroupHandle_t sysEvents = xEventGroupCreate();
#define BIT_MPU   (1 << 0)
#define BIT_FLASH (1 << 1)
#define BIT_NET   (1 << 2)

/* 各自检任务完成时置位 */
xEventGroupSetBits(sysEvents, BIT_MPU);

/* UI 任务：等三位全齐（与等待），10s 超时 */
uint32_t bits = xEventGroupWaitBits(sysEvents,
                    BIT_MPU | BIT_FLASH | BIT_NET,
                    pdFALSE,            /* 退出时不清除（要清除传 pdTRUE） */
                    pdTRUE,             /* pdTRUE=与（全齐）；pdFALSE=或（任一） */
                    pdMS_TO_TICKS(10000));
if ((bits & (BIT_MPU|BIT_FLASH|BIT_NET)) == (BIT_MPU|BIT_FLASH|BIT_NET))
    EnterMainUI();
else
    ShowSelfTestFail(bits);             /* 用 bits 反查哪个自检没过 */
```

关键行拆解：

- 第二参数 `BIT_MPU | BIT_FLASH | BIT_NET`——"我关心哪些位"（掩码）；
- 第三参数 pdFALSE——醒来时**不清位**（要"一次性"等待就传 pdTRUE）；
- 第四参数 pdTRUE——与等待：三个位**全齐**才醒；传 pdFALSE 则任一位置位就醒（或等待）；
- 返回值 bits——**超时也会返回**！它是"当前实际置位情况"，所以失败分支能反查"谁没到"，而不只是笼统的"没到齐"。

xEventGroupWaitBits 三个关键行为：**会阻塞吗？** 会——条件不满足就睡，这正是它的用途；**超时是什么单位？** 最后参数是 tick 数（示例用 pdMS_TO_TICKS(10000) 换算 10s）；**ISR 里能不能用？** Wait 不能，置位要用 `xEventGroupSetBitsFromISR`。

类比：**拼团出发**——与等待=全员到齐才发车；或等待=来一个人先上一个。事件位"广播式"（多个任务可等同一位），与信号量"点对点握手"互补。

| 选型 | 用什么 |
|------|--------|
| 一个事件通知一个任务 | 二值信号量 / 任务通知 |
| 一串数据流水 | 队列 |
| 多事件组合判断（与/或） | 事件组 |
| 广播给所有关心者 | 事件组（SetBits 后所有等待者醒来） |

## 2. 软件定时器：不占硬件定时器的回调

这一节回答"想要几十个秒级定时器、又不想烧硬件定时器外设"的问题——把定时交给内核，你只写回调。

**原理**：RTOS 内核自带一个"定时器服务任务"（prvTimerTask），所有软件定时器到期后**由它排队执行你的回调**——回调跑在任务上下文。类比**前台代管的闹钟**：你跟前台说"10 点提醒我"（创建+启动），到点前台来敲你门（回调）；前台同时服务全公司几十个闹钟，你敲太久（回调阻塞）就把别人的闹钟全耽误了。

```c
/* 建：单次（pdFALSE）/周期（pdTRUE），1000ms */
TimerHandle_t tReport = xTimerCreate("Rpt", pdMS_TO_TICKS(1000),
                                     pdTRUE, NULL, ReportCallback);
xTimerStart(tReport, 0);                    /* 启动（也可运行中动态启停） */

void ReportCallback(TimerHandle_t t)        /* 回调军规：短！ */
{
    UploadCounter();                        /* 只做轻活，重活丢队列 */
}
```

xTimerCreate / xTimerStart 三个关键行为：**会阻塞吗？** 都不阻塞——Start 只是往定时器命令队列投条"启动"消息；**单位是什么？** xTimerCreate 的第二参数是**周期**（tick，用 pdMS_TO_TICKS 换算）；xTimerStart 的第二参数是**命令入队最多等几个 tick**（命令队列满才可能等，一般填 0）；**ISR 里能不能用？** 普通版不能，中断里用 `xTimerStartFromISR` 等 FromISR 版。

**回调三纪律**（因为它本质是别人的任务上下文）：回调里**禁止阻塞**（osDelay/死等队列会卡死所有其他定时器）；重活发队列/通知交给工作任务；不要回调里建/删定时器以外的重操作。

**软件 vs 硬件定时器**：数量不限（内存决定）、精度 ms 级（tick 决定）、可动态启停改周期——**秒级心跳、UI 呼吸、周期上报**全用它；μs 级 PWM/捕获仍用硬件定时器（STM32 篇）。

## 3. 任务通知：轻量通信之王（工程加分项）

这一节回答"一对一的简单通知，能不能不建对象、更快更省"。答案：每个任务出厂自带一个信箱，直接用。

**本质**：每个任务自带一个 32 位"信箱"（TCB 里的 ulNotifiedValue），可直发到任务——**不用建对象、速度比信号量快 ~45%、RAM 省**。

```c
/* ISR：通知处理任务（值=事件码） */
vTaskNotifyGiveFromISR(hProcessTask, &woken);

/* 任务：等通知（可作为轻量二值信号量/事件/邮箱） */
ulTaskNotifyTake(pdTRUE, portMAX_DELAY);    /* pdTRUE=取时清零（模拟信号量） */
```

ulTaskNotifyTake 三个关键行为：**会阻塞吗？** 会——通知值为 0 时睡到有人发通知；**超时是什么单位？** 第二参数 tick 数（portMAX_DELAY 最常用）；**ISR 里能不能用？** 接收（Take）只能在任务里，发送端必须用 `vTaskNotifyGiveFromISR` / `xTaskNotifyFromISR`。

还能当"单值邮箱"（xTaskNotify 带值 + eSetValueWithOverwrite）、当轻量事件组（按位或）。**局限**：点对点（发给指定任务）、单接收者——多任务广播还是事件组。

**选型速记**：能一对一、值简单 → 任务通知；要多对一/广播/组合 → 信号量/事件组；要数据流 → 队列。

## 4. 常见坑

| 坑 | 现象 |
|----|------|
| 事件组 WaitBits 后忘记清位 | 下次等待"秒过"（旧位还在） |
| 定时器回调里 HAL_Delay | 所有软件定时器集体停摆（服务任务被卡） |
| 回调里用阻塞 API | 同上 + 断言 |
| xTimerCreate 后忘 Start | 永不触发（创建≠启动） |
| 任务通知发错句柄/句柄为 NULL | 无声失败（返回值要查） |
| 与等待把超时当失败但不查 bits | 分不清"哪个条件没过" |

## 5. 章节小结

- 事件组=事件位+与/或等待：自检齐活、状态广播场景标配；注意清位
- 软件定时器=内核任务代跑回调：秒级心跳不占硬件定时器；回调短平快
- 任务通知=零开销点对点通信，简单同步首选；广播/数据流退回事件组/队列
- 通信四件套终局选型：通知（一对一轻量）→ 信号量（握手）→ 队列（数据）→ 事件组（组合/广播）

## 课后思考题

1. 事件组的"置位广播"和队列的"排队消费"根本差异是什么？（事件组=状态量，关心"现在是什么状态"，不排队、易覆盖；队列=事件流，关心"发生了几次"，逐条消费——状态与事件两种世界观）
2. 为什么软件定时器回调不能阻塞，而 osDelay 却可以？（回调运行在定时器服务任务里，阻塞它=阻塞所有定时器；osDelay 是"自己这个任务"阻塞，不连累别人——上下文归属决定纪律）
3. 任务通知比信号量快的 45% 从哪省的？（不用查/锁内核对象（对象就在目标 TCB 里）、不用唤醒列表排队、不需要创建/销毁——省的是"对象管理开销"）
