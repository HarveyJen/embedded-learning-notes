# 01 · 裸机到 RTOS：任务与调度

> 目标：理解"为什么需要 RTOS"，掌握任务创建/状态/优先级，跑通多任务工程。

## 1. 裸机前后台的极限（从毕业项目说起）

这一节先回答最根本的问题：**裸机 while(1) 明明能跑，为什么非要引入 RTOS？** 痛点看明白了，后面所有概念才有落点。

STM32 毕业项目的主循环：读 ADC、刷 OLED、解析串口、按键扫描——四件事挤在一个 while(1)：

- **实时性互相拖累**：OLED 刷一屏 20ms，期间 ADC 采样间隔被迫抖动（FFT 精度崩）；
- **延时即停摆**：任何 HAL_Delay 期间全系统不响应；
- **维护噩梦**：四个功能的标志位/状态互相纠缠，加一个功能牵一发动全身。

**RTOS 的答案**：把"四件事挤一个循环"变成"四个员工各干各的"，调度器当经理分时间。**逻辑不省，省的是耦合**——每个任务独立成模块，通信走"信箱"。

把公司画面对应到代码里（本篇乃至整套笔记的统一类比）：

- **员工 = 任务**：每人有自己的办公桌（栈空间）和岗位职责（任务函数），干完一件歇一会儿（阻塞），不用替别人操心；
- **经理 = 调度器**：决定这一毫秒谁上工位干活，谁在旁边待命；
- **信箱 = 队列等通信对象**：员工之间不喊话不抢白板，资料投信箱，收件人自己取。

一句话：裸机是"一个人四条线来回切换"，RTOS 是"一套制度让四个人有条不紊"。

## 2. 任务：RTOS 的员工

这一节回答"任务到底是什么、怎么造一个出来"。一句话：任务就是把要干的活写成**永不返回的函数**，交给 RTOS 托管调度。

任务 = **带独立栈空间的死循环函数**，三要素：函数、优先级、栈大小。想成给新员工办入职：函数 = 岗位职责（干什么），优先级 = 他的事有多急（排班谁先上），栈大小 = 给他多大的办公桌（放得下他的文件）。

```c
/* CubeMX 开 FreeRTOS 后的 CMSIS-V2 风格任务 */
void StartCollectTask(void *argument)        /* 任务函数原型：void f(void*) */
{
    for (;;)                                  /* 任务永远不许 return！返回=栈被拆=死机 */
    {
        collect_once();
        osDelay(10);                          /* 主动睡 10 tick——阻塞，让出 CPU */
    }
}
```

关键行拆解：

- `void StartCollectTask(void *argument)`——任务函数签名固定：收一个指针、永不返回。argument 用于创建时传参（比如告诉这个任务"你负责 ADC1"）；
- `for (;;)`——任务体必须包在死循环里，函数本身永远不退出；
- `osDelay(10)`——本任务的"礼貌"所在：睡 10 tick，睡的期间 CPU 完全让给别人。

osDelay 的三个关键行为（新手最容易懵的点）：**会阻塞吗？** 会，"阻塞"正是它的功能——调用后任务进 Blocked，CPU 立刻让给别人；**超时是什么单位？** 参数是 tick 数（CubeMX 默认 1 tick = 1ms，osDelay(10) 即睡 10ms）；**ISR 里能不能用？** 绝对不能——中断里没有"睡一觉再回来"的上下文，中断里也不存在延时 API。

**三条军规**：
1. 任务函数必须 `for(;;)` 或 `while(1)`，永不 return（要结束用 vTaskDelete(NULL) 自杀）；
2. **绝不空转**：没事干就 osDelay 阻塞，占着 CPU 不干活是 RTOS 头号反模式（裸机的坏习惯要戒）；
3. 栈大小按需给（CubeMX 默认 128 字=512B），用 `uxTaskGetStackHighWaterMark()` 实测水位后定。

### 创建任务的两种方式

| 方式 | 时机 | 说明 |
|------|------|------|
| 静态创建（CubeMX 里加 Task） | 调度器启动前 | 简单任务全走这里 |
| 动态创建 `osThreadNew()` | 运行中随时 | 按需造任务（收到某命令再开任务） |

创建 API 的三个关键行为（以 osThreadNew 为例）：**会阻塞吗？** 不会，立即返回任务句柄（失败返回 NULL，返回值要查）；**超时是什么单位？** 无超时参数——创建是"登记名册"不是"排队等待"；**ISR 里能不能用？** 不能——创建要改内核的调度名册，只能在任务上下文（或调度器启动前）做。

## 3. 任务状态机（本篇核心概念）

这一节回答"一个任务从出生到干活的每一刻处于什么状态、谁在推它换状态"。先看图，再用下面的对照和时间线把它走活。

**生活化对照**（沿用公司场景）：Running = 正在工位干活的员工；Ready = 能干活但暂时没轮到、坐着等经理点名的员工；Blocked = 请假离场，事情来了才回来（等快递、等会议室，期间不占公司任何资源）；Suspended = 被老板勒令停职，不喊回来就永远不来。

```
                xTaskCreate/osThreadNew
                        │
                        ▼
   ┌────────┐  被抢占/时间片到  ┌────────┐
   │ Ready  │◀─────────────────│Running │──▶ 调 vTaskDelay/等队列/等信号量
   │ 就绪   │─────────────────▶│ 运行   │
   └────────┘  调度器选中        └────────┘
        ▲                            │        │
        │  等的事件到了(超时/队列来数据) │        ▼
        └────────────────────────────┘    Blocked 阻塞
                                      （等到了→回Ready；vTaskSuspend→Suspended 挂起）
```

| 状态 | 一句话 | 谁造成的 |
|------|--------|----------|
| Running 运行 | 正在占 CPU | 调度器选中 |
| Ready 就绪 | 能跑，排队等 CPU | 创建后/阻塞解除后 |
| **Blocked 阻塞** | **主动等事件（延时/队列/信号量）**，不占 CPU 不参与调度 | 自己调的（osDelay 等） |
| Suspended 挂起 | 被暂停，调度器当它不存在，要显式 Resume | 别人调 vTaskSuspend |

**Blocked vs 空转的差别**：Blocked 任务不消耗任何 CPU——这就是"10ms 采一次"在 RTOS 里零成本的原因（裸机里只能数标志位）。

**一条完整的时间线**（拿采集任务走一遍，状态机就活了）：

- 第 0 步：`osThreadNew()` 创建任务 → 状态 Ready。注意此刻它一行代码都没跑过，只是在"排班表"上挂了号；
- 第 1 步：调度器盘点就绪表，它是最高优先级的就绪任务 → 选中，进 Running，开始执行 collect_once()；
- 第 2 步：跑到 `osDelay(10)` → 自己写"请假条"（Blocked，10 tick 后回来），调度器立刻叫下一位上岗——这次切换只花几微秒；
- 第 3 步：它 Blocked 的 10ms 里，CPU 归别的任务。**它连"被调度器想起"的资格都没有**——这才是零成本等待的确切含义；
- 第 4 步：第 10 个 tick 的中断里，内核把它挪回 Ready（假期结束，回排班表排队）；
- 第 5 步：再次被选中 → Running，接着跑。如此循环，宏观上就是稳定的 10ms 周期。

四个任务各自这样循环，每个 99% 的时间都躺在 Blocked——一颗 CPU 才"同时"养得起四个员工。

## 4. 调度器：谁来用 CPU

这一节回答"一个 CPU 工位，经理按什么规矩分配"。FreeRTOS 默认**抢占式调度**：经理全程盯着，谁的事最急谁随时可以顶上去，不需要低优先级"主动让位"。

三条规则（FreeRTOS 默认抢占式）：

1. **高优先级优先**：高优先级任务一就绪，立刻抢占运行中的低优先级；
2. **同优先级时间片轮转**：轮流各跑一个 tick（可关）；
3. **没人跑就跑空闲任务**（优先级 0 兜底），其钩子里可进低功耗。

**优先级设定经验法**（数字越大优先级越高，CubeMX 里注意 V1/V2 方向相反的坑）：

```
硬实时响应（采样、安全检测）      > 数据处理（滤波、协议）> 人机交互（显示、按键）> 日志统计
紧急且短  → 优先级高 + 执行快
紧急且长  → 高优先级任务只"触发"，重活交给低优先级任务（中断委托思想放大版）
```

**一次抢占的时间线**（把规则 1 演成慢动作）：

- 第 1 步：显示任务（低优先级）正在 Running，慢悠悠刷 OLED 的第 8 行；
- 第 2 步：ADC 采样完成中断触发，ISR 里唤醒采集任务（高优先级）→ 采集任务变 Ready；
- 第 3 步：调度器一看就绪表里有优先级更高的 → 立刻把显示任务"定格"在当前这条指令（寄存器现场全部保存），采集任务上台；
- 第 4 步：采集任务干完活 osDelay 睡了 → 显示任务从第 8 行原地继续，对刚才发生的一切毫无察觉。

"定格-恢复"由内核全自动完成，任务代码里看不出任何痕迹——这就是抢占式调度给程序员的承诺。

## 5. Tick 与延时：RTOS 的心跳

这一节回答"RTOS 的时间是怎么数的"。所有延时、超时、时间片，底层都是同一个节拍源——Tick。

把 Tick 想成公司的**考勤钟**：每"滴答"一次（默认 1ms），经理抬头看一次排班表——有没有人假期到了该回来？有没有更急的活进来了？没有这口钟，调度器就是没有表的经理，一切时间概念无从谈起。

- **Tick 中断**（SysTick，CubeMX 默认 1ms）：RTOS 的"钟摆"，每摆一次更新调度判断——它把 SysTick 从"HAL_Delay 的秒表"升级为"系统总节拍"；
- **相对延时 `osDelay(10)`**：从"现在"起睡 10 tick——每次醒来时刻会因执行时间漂移（累计误差）；
- **绝对延时 `osDelayUntil()`**：对齐固定节拍唤醒——**周期性采样必须用它**（呼应 STM32 篇"匀速采样"：RTOS 下靠 delayUntil 保节奏）。

**单位换算提醒**：凡是以 tick 为单位的参数，工程上建议一律写 `pdMS_TO_TICKS(毫秒数)` 宏换算，别硬编码数字——将来 tick 频率一改（如 1ms → 100us），硬编码处全部返工，用宏则一行不用动。

osDelayUntil 顺带交代三个关键行为：**会阻塞吗？** 会（睡到指定节拍才回来）；**参数是什么单位？** 传的是"唤醒时刻"（tick 计数值，配合记录上次唤醒的变量用），不是"睡多久"；**ISR 里能不能用？** 不能（任务专用）。

## 6. 最小工程：多任务流水灯

这个工程做什么：两个任务各按各的周期翻转一颗 LED——五分钟验证"同一颗 CPU 能同时干两件事"。

```c
/* CubeMX: FreeRTOS 开启 + 两个 Task（ prio=Normal, stack=128 words ） */
void StartLed1(void *arg) {                 /* 任务1：500ms 翻 LED1 */
    for (;;) { HAL_GPIO_TogglePin(LD1); osDelay(500); }
}
void StartLed2(void *arg) {                 /* 任务2：300ms 翻 LED2 */
    for (;;) { HAL_GPIO_TogglePin(LD2); osDelay(300); }
}
```

烧进去两灯各闪各的——**同一颗 CPU"同时"干两件事**。再用调试器暂停，看 Call Stack 里调度器上下文切换现场，感知"员工切换"真实存在。

关键行拆解：

- `HAL_GPIO_TogglePin(LD1); osDelay(500);`——翻灯后立刻睡 500ms。算笔账：LED1 任务 99% 以上时间在 Blocked，CPU 大部分时间其实在空闲任务里打转（或进低功耗）；
- 两个任务**零共享资源**，不需要锁、不需要队列——最干净的多任务 demo，专证"并行"这件事本身；
- 反过来试：把任务 1 的 osDelay 删掉改成纯空转——同优先级下靠时间片 LED2 还能每 tick 分到一点时间（两灯都闪但节奏诡异、CPU 占用飙满）；若任务 1 优先级更高，LED2 彻底饿死——坑表里第一个要复现的就是它。

## 7. 常见坑

| 坑 | 现象 |
|----|------|
| 任务里 return | HardFault（栈被当返回地址） |
| 任务里死循环不 delay | 低优先级任务全部饿死（系统"假死"） |
| CMSIS-V1/V2 优先级方向记反 | "最高"变"最低"，实时任务被饿 |
| 栈给太小 | 栈溢出：HardFault 或数据诡异损坏（开 configCHECK_FOR_STACK_OVERFLOW=2 抓） |
| osDelay 与 HAL_Delay 混用 | HAL_Delay 是忙等——在任务里白烧 CPU |
| 任务函数用大局部数组 | 栈瞬间爆（大缓冲用静态/堆，呼应 C 笔记08） |

## 8. 章节小结

- RTOS 解的是**耦合与实时性冲突**，不是"显得高级"
- 任务=独立栈的死循环；状态四分类，Blocked 是 RTOS 效率之源
- 调度三规则：抢占、同优先级轮转、空闲兜底；优先级按"紧急且短"排
- 周期任务用 osDelayUntil 对齐节拍；任务军规：不 return、不空转、栈够用

## 课后思考题

1. 为什么任务里 osDelay(10) 后 CPU 能"立刻"给别人用，而裸机里 HAL_Delay(10) 不能？（osDelay 把任务挪出就绪表并设唤醒时刻——调度器在 tick 里换人；HAL_Delay 只是 while 循环数 tick 计数，CPU 没让出来）
2. 三个任务优先级同为 Normal 且都在跑 osDelay(100)，实际执行顺序有规律吗？（先按创建顺序就绪，同优先级时间片轮转；每次都 delay 100 无抢占则顺序稳定循环——实验验证时间片的存在）
3. 空闲任务存在的意义是什么？钩子函数能干什么？（保证调度器永远有任务可跑（算法简化）；钩子里进低功耗（Tickless）、喂狗统计——"没人干活"也是需要管理的状态）
