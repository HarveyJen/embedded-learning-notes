# 06 · 综合项目：RTOS 版多传感器数据采集系统（阶段毕业）

> 把 07-STM32 毕业项目**整体重构为 RTOS 架构**——这是阶段三验收，也是作品集里最值钱的一个项目（体现架构升级能力）。

## 1. 项目目标（对照裸机版的升级点）

这一节先明确"重构到底图什么"：不是换个框架显得高级，而是对着裸机版的四个痛点逐项升级——做完回看这张表，每一行都要能指出代码里对应的位置。

| 维度 | 裸机版（05 阶段） | RTOS 版（本阶段） |
|------|-------------------|-------------------|
| 架构 | 前后台：主循环轮询 + 定时器时基 | 5 任务 + 队列/信号量通信 |
| 实时性 | 采集间隔受显示拖累 | 采集任务高优先级，间隔精确 |
| 可靠性 | IWDG 单点喂狗 | 看门狗任务**监督每个任务打卡** |
| 可观测 | printf | 任务状态/栈水位/队列水位实时监控 |

## 2. 任务划分（架构图——答辩主图）

这一节回答"活怎么分、分给谁"。划分原则：**一个任务一类职责、一个节拍**；任务间通信全走内核对象，绝不共享全局变量。

先给系统一个类比——**小型流水线车间**：采集是"进货口"（高频快活）、处理是"质检台"（中频思考）、显示是"展示柜"（低频慢活）、通信是"对外窗口"、看门狗是"巡查主管"（自己不干活，只查岗）。优先级按 01 篇"紧急且短"排序，主管最闲所以优先级最低。

```
优先级：采集(4) > 通信(3) > 处理(2) > 显示(1) > 看门狗监控(低+特殊)

[ADC DMA] ──(半满/全满中断+任务通知)──▶ [采集任务 p4] ──均值滤波结果──▶ [dataQueue]
                                                                        │
[串口 ISR] ──字节──▶ [rxQueue] ──▶ [通信任务 p3] ◀──响应帧──┐            │
                                     │ 解析/打包            │            ▼
                                     └──命令──▶ [cmdQueue]  │      [处理任务 p2]
                                                              │       │ 阈值判断/整合
[按键 EXTI] ──通知──▶ [显示任务 p1] ◀──────screenQueue─────────┴──── 数据/界面切换
                         │ OLED 刷新（拿 I2C Mutex）
                         ▼
                    [看门狗任务]：每 5s 收集四任务"打卡"事件组 → 全齐才喂 IWDG
```

**任务职责卡**：

| 任务 | 优先级 | 栈(字) | 职责 | 通信 |
|------|--------|--------|------|------|
| 采集 Collect | 高 | 256 | osDelayUntil 10ms 触发 DMA 结果处理、均值滤波 | 通知收、dataQueue 发 |
| 通信 Comm | 中高 | 384 | rxQueue 收字节拼帧、解析命令、组响应帧 | rxQueue 收、cmdQueue 发 |
| 处理 Process | 中 | 256 | 收 dataQueue，阈值判断/越限报警，整合数据包 | dataQueue 收、screenQueue 发 |
| 显示 UI | 低 | 256 | screenQueue 收指令刷 OLED、按键切页 | screenQueue 收，持 I2C Mutex |
| 看门狗 Watchdog | 低 | 192 | 各任务心跳打卡 → 全齐喂 IWDG；缺卡即复位上报 | 事件组收 |

## 3. 关键实现点（对应各篇笔记）

### 3.1 周期采集用 osDelayUntil（01 篇）

这段代码做什么：采集任务的骨架——收到 DMA 半满通知处理一批数据，处理完睡等下一次通知（或按固定节拍对齐唤醒，两种策略二选一并写清理由）。

```c
void CollectTask(void *arg)
{
    TickType_t last = osKernelGetTickCount();
    for (;;) {
        ProcessDmaBuffer();                      /* 均值滤波 → push dataQueue */
        ulTaskNotifyTake(pdTRUE, portMAX_DELAY); /* 等下一次 DMA 半满通知 */
        /* 若坚持固定节拍：osDelayUntil(&last, 10) 二选一，写清理由 */
    }
}
```

### 3.2 I2C 互斥（03 篇）

这一小节落实"共享总线必须上锁"：锁的持有时间 = 一次传输，多一毫秒都不多。

OLED 刷新（UI 任务）与 MPU6050 读取（采集任务）共用硬件 I2C → `i2cMutex`，临界区只包一次传输。

### 3.3 看门狗任务：分布式喂狗（05 篇思想放大）

这段代码做什么：每个任务循环末尾"打卡"（置自己的事件位），看门狗任务每 5s 查一次全员打卡，全齐才喂硬件 IWDG——把"喂狗"从单点变成对全系统的监督。

类比**门禁打卡机**：五个员工各有一个打卡位（事件位），保安每晚 10 点查一遍——全员打过卡 = 系统正常（喂狗）；有人缺卡 = 记下名字（日志）再拉闸复位。裸机版只能"主循环还活着就喂"，任务卡死它根本不知道。

```c
#define BIT_C (1<<0)  #define BIT_M (1<<1)  #define BIT_P (1<<2)  #define BIT_U (1<<3)

/* 每个任务循环末尾： xEventGroupSetBits(wdgBits, 自己的位); */
void WatchdogTask(void *arg)
{
    for (;;) {
        uint32_t b = xEventGroupWaitBits(wdgBits, ALL_BITS, pdTRUE, pdTRUE,
                                         pdMS_TO_TICKS(5000));
        if ((b & ALL_BITS) == ALL_BITS) HAL_IWDG_Refresh(&hiwdg);
        else { LogMissingTask(b); NVIC_SystemReset(); }  /* 记录饿死任务后复位 */
    }
}
```

关键行拆解：

- `ALL_BITS`——即 BIT_C、BIT_M、BIT_P、BIT_U 四个位按位或的"全员"掩码（示例里没给定义，自己写工程时别落下）；
- `xEventGroupWaitBits(..., pdTRUE, pdTRUE, pdMS_TO_TICKS(5000))`——两个 pdTRUE：前者"醒来后清位"（下一轮重新打卡），后者"与等待"（全员齐才算数）；5s 超时 = 有任务卡死时的兜底闹钟；
- `HAL_IWDG_Refresh(&hiwdg)`——只有"全员打卡"才喂狗：硬件狗监督的其实是**所有任务健康的总和**；
- `LogMissingTask(b)`——复位前把"谁没打卡"写进日志：复位不可怕，可怕的是不知道为什么复位。

任何一个任务卡死 → 5s 内系统复位且留下"谁饿死"的日志——比裸机单点喂狗强一个量级。

### 3.4 可观测性面板（答辩加分）

这一小节回答"系统跑起来之后，我怎么知道它健康"——把内部状态做成一条命令可见，问题来临时才有抓手。

串口命令 `stats`：打印 `vTaskList()`（任务/状态/优先级/栈水位）、各队列 `uxQueueMessagesWaiting`、`xPortGetMinimumEverFreeHeapSize()`——运行期一切尽在掌握。

## 4. 开发与调试路线图（两周节奏）

这一节给落地顺序，核心纪律：**一次只迁移一个任务，每步都能编译、能回退**——大爆炸式重写是重构翻车的第一原因。

```
① CubeMX：FreeRTOS + 原 STM32 毕业项目外设全量迁移
② 空任务骨架跑通 → 逐任务迁移裸机代码（一次一个，随时可回退）
③ 通信骨架：先 rxQueue+通信任务，命令行灯亮 → 再 dataQueue 链
④ 看门狗任务 + 心跳打卡最后接入（有骨架了再上保险）
⑤ 压力测试：串口 100ms 高速发命令 + 显示刷新 + 采集并发，跑 24h
⑥ stats 面板全程监控栈/堆/队列水位，收尾调栈
```

**每步 Git 提交**（路线横向要求），最后打 tag `v1.0-rtos`。

## 6. 常见坑（重构期实录预警）

| 坑 | 现象 |
|----|------|
| 裸机代码直接搬进任务不改 | HAL_Delay 占 CPU、大局部数组爆栈 |
| 采集任务优先级给低了 | 采样间隔抖动（等于白上 RTOS） |
| OLED 刷新不拿 Mutex | I2C 偶发 NACK 死锁 |
| 看门狗打卡位忘了清 | "与等待"永远真 → 假喂狗（pdTRUE 清位参数） |
| stats 面板没留 | 出问题抓瞎，答辩缺说服力 |

## 课后思考题

1. 为什么看门狗任务优先级低反而合理？（喂狗的权威来自"所有人打卡"而非自己跑得快；若它优先级最高，打卡位没齐它也白等——逻辑上只需周期性醒来，低优先级省 CPU）
2. 若显示任务偶发 2s 卡顿（刷大图），系统该怎么表现？（I2C 被持有时采集任务等 Mutex→注意"采集不该依赖显示"——正确设计是 MPU 读取与 OLED 刷新分用不同 I2C 或给读加独立传感器，架构题：**依赖方向决定健壮性**）
3. 对比裸机版与 RTOS 版同功能代码量与 RAM 占用，值不值？（代码量相近（逻辑搬家），RAM +2~3KB（任务栈/内核对象）；换来实时性解耦、可维护性、可扩展——"用资源买架构"，面试时这是绝佳的成本收益论述）
