# 03 · 信号量与互斥量：同步与锁

> 目标：分清"同步用信号量、互斥用互斥量"这条铁律；吃透优先级反转（面试最高频 RTOS 题）。

## 1. 信号量：事件旗与资源票

这一节回答"信号量是什么、为什么有了队列还要它"。一句话：队列传**数据**，信号量只传**"发生了"这个事实**——事件通知的专用工具。

**本质 = 内核维护的计数器 + 等待队列**。取票（Take）减一，发旗（Give）加一，没票就睡。类比**值班室门口的小旗子**：事件发生 = 挂旗（Give）；巡逻员看到旗才出动（Take），出动顺手收旗；没旗时巡逻员在值班室打盹（Blocked），绝不空跑一趟。

### 二值信号量：中断→任务的"事件通知"

先记 Take/Give 的三个关键行为：**会阻塞吗？** Take 会——没旗时任务进 Blocked 睡到旗出现（这正是用途）；Give 永不阻塞（只放旗，二值量已有旗时再 Give 不叠加）。**超时是什么单位？** Take 的第二参数是 tick 数（用 pdMS_TO_TICKS 换算，portMAX_DELAY = 死等）；**ISR 里能不能用？** Give 可以但必须用 `xSemaphoreGiveFromISR`；Take 在 ISR 里禁止（不能睡，所有权语义也不允许）。

```c
/* 建队：xSemaphoreCreateBinary() 初始为空 */

void ADC_IRQHandler(void)                 /* ISR：事件发生，放旗 */
{
    BaseType_t woken = pdFALSE;
    xSemaphoreGiveFromISR(adcSem, &woken);
    portYIELD_FROM_ISR(woken);
}

void ProcessTask(void *arg)               /* 任务：等旗，来了再干重活 */
{
    for (;;) {
        if (xSemaphoreTake(adcSem, portMAX_DELAY) == pdTRUE)
            HeavyProcess();               /* 滤波/计算——在任务态放心干 */
    }
}
```

这就是 **"中断上半部/下半部"** 模型（操作系统理论课的对应物）：ISR 只喊一嗓子（Give），重活全在任务里干——07-STM32 中断委托思想的 RTOS 标准化。**信号量不含数据**（对比队列），只传递"发生了"这个事实；要传数据用队列。

### 计数信号量：资源池门票

`xSemaphoreCreateCounting(10, 10)`——10 个停车位，进一辆减一，出一位加一，没位排队。典型用途：**限制并发**（如"最多 3 个任务同时访问 DMA"）、事件累积（ADC 连续来 5 次，任务一次取 5 张批量处理）。

## 2. 互斥量：带保护的锁

这一节回答"多任务共享一个外设/一段数据时，怎么防止打架"。信号量管"通知"，互斥量管"排队使用"。

**问题场景**：两个任务都要读 MPU6050（I2C 总线），并发访问 → 半个测量值 + 半个测量值 = 乱数据。

**互斥量 = 带"谁拿谁还"+优先级继承的锁**。类比**公共厕所的门锁**：进去的人反锁（Take），门外的人排队等（Blocked），用完开锁（Give）；锁上写着"谁锁的谁开"（所有权，别人开不了）；而且管理员有个特权——外面排着 VIP 时，可以让里面的人"抓紧办完出来"（优先级继承，第 3 节揭晓）。

```c
SemaphoreHandle_t i2cMutex = xSemaphoreCreateMutex();

void TaskA(void *arg)
{
    for (;;) {
        if (xSemaphoreTake(i2cMutex, 100) == pdTRUE) {   /* 拿锁（带超时！不写死等） */
            MPU6050_ReadAll();                            /* 临界区：独占 I2C */
            xSemaphoreGive(i2cMutex);                     /* 用完立刻还 */
        } else {
            /* 超时没拿到：记日志降级，别死等 */
        }
        osDelay(50);
    }
}
```

关键行拆解：

- `xSemaphoreTake(i2cMutex, 100)`——带 100 tick 超时的拿锁：锁在别人手里就睡 100ms 等它；等到返回 pdTRUE，等不到返回 pdFALSE 走降级分支。**不带超时的死等是新手事故高发区**；
- `MPU6050_ReadAll()`——临界区本体：此刻整条 I2C 归本任务独占，别人要么等锁、要么干别的去；
- `xSemaphoreGive(i2cMutex)`——用完立刻还。拿锁和还锁之间只夹一次传输，这就是"临界区短"该有的样子。

**互斥量三铁律**：
1. **谁拿谁还**（所有权检查，Give 别人的锁会报错）——和二值信号量的本质区别；
2. **临界区越短越好**：锁内禁止延时、打印、长循环（拿着会议室钥匙去吃饭，全公司瘫痪）；
3. Take 必须带超时 + 分级加锁顺序（A→B、B→A 并发 = 死锁）。

## 3. 优先级反转（必须会讲的悲喜剧）

这一节是面试最高频 RTOS 题，也是"为什么互斥必须用 Mutex 而不是二值信号量"的唯一原因。目标：读完这个时间线，你能合上笔记给别人讲明白。

**场景**：低优先级 L 拿了 I2C 锁 → 高优先级 H 抢占后想拿锁，**被挂起干等** → 此时**中优先级 M**（不碰锁）横插进来跑了很久 → 结果：H 反而被 M 压着，优先级体系形同虚设。

**事故时间线**（三个员工一台戏，逐步定格看）：

- 第 1 步（t0）：低优先级任务 L 拿到 I2C 锁，开始读传感器——预计 10ms 干完还锁；
- 第 2 步（t1）：高优先级任务 H 被中断唤醒，抢占 L 上台；干着干着它也要读 I2C → Take 锁 → 锁在 L 手里 → **H 进 Blocked 干等**。此刻最高优先级任务的命运，攥在了最低优先级任务手里；
- 第 3 步（t2）：更荒诞的来了——中优先级任务 M 就绪（比如串口来了一大批数据）。调度器比较就绪表：M 比 L 高 → M 抢占 L 上台。**H 因为在 Blocked，根本不参与比较**，只能干瞪眼；
- 第 4 步（t3）：M 跑一个 100ms 的长活。M 一天不跑完，L 一天没机会还锁，H 一天出不了 Blocked——**H 的响应时间被毫不相干的 M 支配**，这就是"反转"二字的全部含义；
- 第 5 步（t4）：M 终于跑完 → L 恢复上台，把剩下的几 ms 读完 → 还锁 → H 立刻被唤醒接管。

复盘：优先级数字上 H > M > L，真实时序里 H 被 M 拖了近 100ms——高优先级形同虚设。用二值信号量当锁，这个剧本随时上演。

```
时间轴：  L拿锁 → H就绪抢CPU→等锁被挂 → M就绪开跑（L被挤下台）→ M跑完 → L才还锁 → H终于跑
实际感受：最高优先级 H 的响应时间被 M 支配——"反转"
```

类比：小职员（L）占着打印室，总经理（H）来了只能排队；这时保安（M）路过把小职员叫走了闲聊，总经理干瞪眼。

**解法 = 优先级继承**：H 等锁的瞬间，内核把 L 的优先级**临时抬到 H 一样**（L 变身"代总经理"），M 插不进队 → L 快速干完还锁 → 降回原级 → H 顺利接管。互斥量自带此机制，**二值信号量没有**——这就是"互斥用 Mutex"铁律的由来。

**同一剧本换 Mutex 重演**（对照上面找继承生效的位置）：

- 第 1 步：L 拿锁开跑（和事故版一样）；
- 第 2 步：H 抢占上台 → Take 锁被卡住。**就在 H 进 Blocked 的瞬间，内核把 L 临时抬到与 H 同级**——"代总经理"上线；
- 第 3 步：M 就绪，调度器一看：就绪表里 L 已经和 H 一样高，M 排不进去 → 继续待命；
- 第 4 步：L 顶着高优先级把剩下的几 ms 跑完还锁 → 降回原级 → H 被唤醒接管；
- 结果：M 全程没捞到上场机会，H 的等待被压缩到"锁本身的持有时长"（有界）——反转被消灭。

一句话记忆：**继承不是消灭等待，是把"无界的恶意插队"压成"有界的一手交锁"**。

> 关联记忆：火星探路者号 1997 年著名的优先级反转死机事故（VxWorks，未启用继承）——这道题面试讲出来是加分项。

| 对比 | 二值信号量 | 互斥量 |
|------|-----------|--------|
| 用途 | **同步**（事件通知） | **互斥**（资源保护） |
| 所有权 | 无（A Give B Take 天经地义） | 有（谁拿谁还） |
| 优先级继承 | 无 | 有 |
| ISR 里 Give | 可以（FromISR） | 不可以（无上下文所有权） |

## 4. 临界区：更粗的保护

这一节给出锁之外的第二个选项：**几行以内的短原子操作**，用临界区比上锁更轻——轻在不用建对象，也重在"太粗"。

`taskENTER_CRITICAL()/exit()` 成对包裹：把中断屏蔽到内核管理线（configMAX_SYSCALL_INTERRUPT_PRIORITY）——比这条线更急的中断（F103 上数值 0~4）照样能打断，但 SysTick/PendSV 等调度相关中断被一并挡住，期间不会发生任务切换，代码等效原子执行。**适用**：几行寄存器级操作；**禁用**：长临界区（把 RTOS 退化为裸机）。优先级：**互斥量 > 临界区 > 关全局中断**，能轻则轻。

顺带分清两种保护手段：临界区走的是**屏蔽中断**（挡中断，顺带挡住调度心跳）；而 `vTaskSuspendAll()/xTaskResumeAll()` 走的是**挂起调度器**——只拦任务切换、不关任何中断（挂起期间中断照常响应，ISR 请求的切换会攒到恢复调度时才执行）。两者是不同的保护工具，按"要不要连中断一起挡"选，别混为一谈（05 篇中断契约段的 configMAX_SYSCALL 讲的就是这条内核管理线）。

## 5. 常见坑

| 坑 | 现象 |
|----|------|
| 用二值信号量当锁 | 优先级反转（没有继承），偶发实时性崩坏 |
| 拿锁后中途 return 忘 Give | 锁永久丢失，其他任务全卡（成对书写/提前给"异常路径还锁"） |
| 临界区里 osDelay | 断言死机（阻塞禁止出现在临界区） |
| ISR 里 Take 阻塞信号量 | 死机（ISR 不许阻塞，必须 FromISR+不阻塞） |
| 两把锁交叉拿 | 死锁（统一加锁顺序，或一次 TakeAll） |
| 计数信号量上限溢出 | Give 超上限丢弃计数，事件丢失 |

## 6. 章节小结

- 同步（通知"发生了"）用信号量；互斥（保护"正在用"）用互斥量——一句话选型铁律
- 二值信号量 = 中断委托标准件；计数信号量 = 资源池/事件累积
- 优先级反转：L 持锁、H 干等、M 插队；解法 = Mutex 的优先级继承
- 锁三纪律：谁拿谁还、临界区短、带超时防死锁

## 课后思考题

1. 互斥量的优先级继承能完全消灭优先级反转吗？（消灭"无界反转"，只剩"持锁期间的短暂等待"（有界）；链式继承在复杂锁关系下有局限——所以还要靠"临界区短"的设计）
2. 为什么 ISR 里不能 Take 互斥量？（Take 可能阻塞睡下去，而中断没有"任务上下文"可睡；且互斥量的所有权/继承机制需要任务身份）
3. "Give 优先级高于 Take 的任务"用二值信号量，顺序对吗？为什么？（对：先 Give 后 Take，旗子先挂着也行（二值量上限1）——同步语义允许"事件先发生"；但互斥量必须"先 Take 后用后 Give"，方向不可反——再次印证两者语义不同）
