# 07 · 调试实战：断点、寄存器与 HardFault 定位

> 本篇是路线修订补充的**高优先级缺口**——"会不会调试"是入门者与工程师的分水岭。目标：ST-Link 全功能掌握 + HardFault 10 分钟定位。

**开篇大白话**：printf 打印是"隔门喊话"，芯片死机了它一句话都喊不出来。调试器是"进屋办案"——能让芯片暂停、翻它的口袋（寄存器/变量）、看它从哪摔的（调用栈）。本篇目标：把 ST-Link 用成随身工具箱，再学一套"程序跑飞"的标准勘查流程。

## 1. ST-Link：调试能看穿芯片

**这一节说什么/解决什么问题**：先弄明白"调试器凭什么比串口强"——SWD 是芯片内核自带的旁路通道，不依赖你写的程序好不好。理解这一点，你才知道"变砖了也能救"不是玄学。

| 功能 | 串口下载 | ST-Link(SWD) |
|------|----------|--------------|
| 烧录 | 能 | 能（更快） |
| 断点/单步 | × | √ |
| 看变量/寄存器/调用栈 | × | √ |
| 擦除抢救变砖 | × | 能（Connect under reset） |

**SWD 是什么**：Serial Wire Debug，ARM 内核自带的调试接口——为什么能"看穿"芯片：它是独立于用户程序的硬件旁路（DAP 调试单元），CPU 死没死、程序跑飞没跑飞都不影响它访问内存和外设，像给保险柜配了官方万能钥匙。

**接线与配置，每步为什么**：
- **接线**：**SWDIO**（数据线，调试命令/数据走这）+ **SWCLK**（时钟线，调试器吹节拍）+ GND + 3.3V，四线搞定——比 JTAG 的十几根线省事，是 STM32 的主流选择；
- Keil 里 Debug 选 ST-Link Debugger → Settings 里勾 **Reset and Run**（下载完自动跑——不勾的话每次烧完都要手动按复位，纯属折磨）+ **SWJ 端口使能**（明确告诉调试器用 SWD 两线模式而不是 JTAG）；
- 芯片锁死/下载失败时勾 **Connect under Reset** 模式抢救。**为什么它能救砖**：用户程序可能一上电就跑飞并干扰 SWD；"复位瞬间先接管"= 趁 CPU 还没来得及乱跑就抓住它，先断开再擦除——电门没落锁就撬开了门。

## 2. 调试器三板斧（每天都要用）

**这一节说什么/解决什么问题**：调试 80% 的场景就靠三招。每招背后是同一个原理：让 CPU 停下、把内存搬给你看。

1. **断点+单步**：怀疑哪行点哪行；Step Over(执行整函数)/Step Into(进函数)/Step Out(跳出)。**断点原理一句话**：调试器把该地址喂给内核的断点比较器，PC 执行到这 CPU 自动暂停——所以硬件断点数量有限（见思考题 2）；
2. **Watch/内存窗口**：Watch 看变量（地址+值实时刷新）；Memory 窗口看裸内存（验证结构体对齐、缓冲区内容——C 笔记08 的落地）；**Peripherals 窗口直接看外设寄存器当前值**（判断"配置写没写进去"——代码写了 RCC 使能但寄存器里那一位还是 0？说明时钟没开成功，一秒定位）；
3. **Live Watch（周期刷新）**：不断点看运行中的变量变化（采样值、状态机状态）——**为什么需要它**：打断点会破坏实时性（电机、通信类程序一停就乱），"不停机观察"才是这类程序的打开方式。

**调试心法**：先二分定位（在中间点断点看数据对不对，逐步夹逼——**为什么二分**：20 步的流程逐行查要 20 次，二分只要 5 次， logarithm 的胜利）；先看"数据对不对"再看"逻辑对不对"（数据错了逻辑再"对"也是白搭）；改一行烧一次，禁止凭想象连环改（改了三处再测，好了也不知道是哪处救的，坏了更没法回退）。

## 3. HardFault 定位（事故现场勘查）

**这一节说什么/解决什么问题**：程序"突然卡死"的头号解释是 HardFault。本节给一套照着走就能定位到出错代码行的标准流程——这是面试和实战双重高频。

**HardFault = CPU 跑飞的兜底异常**（非法地址、未对齐访问、除零、栈溢出都会跳到这）。现象：程序突然卡死不跑。

**类比**：HardFault 像"事故现场的警戒线"——CPU 撞墙的那一刻，现场（寄存器、调用栈）被冻结保存。你要做的不是重启（毁灭现场），而是勘查：谁在什么位置、撞的什么墙。

**先认识勘查要用的三个名字**：
- **LR（Link Register，链接寄存器）**：函数调用时存放"返回地址"的寄存器——看它就知道"从哪跳进来的"；
- **MSP/PSP**：两个栈指针（主栈/进程栈）——异常固定用 MSP，RTOS 任务用 PSP；勘查时先确认用的是哪个栈，找错了栈=勘查错了现场；
- **SCB->CFSR**（Configurable Fault Status Register，故障状态寄存器）：硬件留下的"事故报告单"，哪一位是 1 就说明撞的什么墙（非法地址/未对齐/除零……）。

### 标准定位流程（Keil）

```
① 全停挂在 HardFault_Handler → 点"Stop"，看 Call Stack 窗口
   （为什么看 Call Stack：它记录了"事故发生时每层函数调用的来路"——
     死在叶子函数不要紧，顺着栈往上找是谁把它带进坑的）
② 找到最底层的"形如 0x0800xxxx 的返回地址"→ 右键 Show Disassembly / 或直接在
   Flash 窗口输地址 → 对应到出错代码行
   （0x0800xxxx 是 Flash 区间——0x2000xxxx 是 RAM 变量地址，0x0800 是代码，
     别混；这一步=把"机器的事故报告"翻译成"你的第几行代码"）
③ 看现场：LR 寄存器（区分 MSP/PSP 栈）、出错访问的地址（SCB->CFSR 可读故障类型）
   （CFSR 是硬件写的"事故原因"栏，比如提示非法地址 0x00000000——
     空指针解引用直接实锤）
```

**走一遍例子**：Call Stack 显示 `memcpy ← parse_frame ← main`，最底层返回地址 0x08001234；在 Flash 窗口输入 0x08001234，定位到 parse_frame 里 `memcpy(dest, src, len);` 这行；CFSR 显示非法地址 → Watch 看 dest → 发现它是未初始化的野指针 → 上溯发现 dest 来自一个没判 NULL 的参数。三步，事故报告变修复方案。

**高频原因榜**（按真实工程频率排序）：

| 原因 | 典型代码 |
|------|----------|
| 野指针/空指针解引用 | 结构体指针未初始化就 `p->x` |
| 数组越界 | 缓冲区写穿，踩坏函数返回地址 |
| 未初始化外设指针 | 手写寄存器地址拼错 |
| 栈溢出 | 大局部数组 + 深递归 |
| 中断里调不可重入函数 | ISR 里 printf/malloc |

**预防**：指针用前判空（系统边界处）；C 笔记11 的环形缓冲容量检查；打开编译警告当错误（-Werror）；调试时 Watch 栈水位。

## 4. printf 之外的调试手段

**这一节说什么/解决什么问题**：断点会破坏实时性、printf 有开销且 ISR 里不能用——工具箱要够深，按问题类型挑工具。

| 手段 | 适用 | 说明 |
|------|------|------|
| **逻辑分析仪** | 时序/协议问题 | I2C/SPI/串口/PWM 波形解码（几十元的 24MHz 版够用） |
| 串口日志 | 运行逻辑追踪 | 带文件行号的打印，量产可关 |
| GPIO 翻转+示波器 | **测函数耗时** | 进函数拉高出函数拉低，示波器看脉宽=执行时间（性能分析土办法但极有效） |
| SEGGER RTT | 实时日志 | J-Link 专属，不占串口、速度极快 |
| 硬件断点/数据断点 | "谁改了我的变量" | Watchpoint：变量被写入时停下——查内存踩踏神器 |

**GPIO 翻转法走一遍**：函数第一行 `PA0=1;`，最后一行 `PA0=0;`——示波器测得高电平持续 340μs，这就是函数真实耗时（含编译器优化的真实世界表现）。**为什么比数指令周期靠谱**：真实芯片上 cache/总线竞争/中断都影响耗时，实测一锤定音。

## 5. 故障案例演练（把方法串起来）

**这一节说什么**：把前四节的工具按"真实排障剧本"串一遍——注意每一步都在"缩小包围圈"，这正是排障思维的精髓。

**案例**：设备运行几小时后偶发死机。

```
① 上电正常 → 排除初始化问题 → 怀疑运行时内存/缓冲
   （为什么先排除初始化：时好时坏说明"配置正确但被运行时破坏"，
     初始化类的错通常"上电就坏"，不会挑时间）
② 挂 ST-Link 等复现 → 死机时 Stop → Call Stack 定位：卡在 memcpy
   （"等复现"是耐心活：偶发 bug 的第一策略=保持现场等它再犯，
     复位重启=毁灭现场）
③ 查 memcpy 的目的地址 → 是环形缓冲区 → Watch 读指针 → 发现为脏值
   （脏值=不是合法范围内的数，说明被谁改坏了——"谁改的"→ 下一步）
④ 数据断点盯着读指针 → 抓到"串口 ISR 入缓冲时索引越界"
   （数据断点=在这一变量被"写"的时刻拍照，直接抓到修改者现行）
⑤ 根因：缓冲区满未判断 → 加满判断 → 72 小时压力测试通过
   （为什么测 72 小时：偶发 bug 的修复必须用"时间×压力"验证，
     修完跑 10 分钟就宣布痊愈是最常见的假治愈）
```

这套"现场勘查→二分夹逼→数据断点抓现行"是嵌入式排障的标准剧本。

## 6. 章节小结

- ST-Link 四线 + Reset and Run + Connect under reset 抢救
- 三板斧：断点单步、Watch/Memory/Peripherals、Live Watch
- HardFault 流程：Call Stack → 返回地址 → 对应源码；高频原因是野指针/越界/栈溢出
- 手段组合：逻辑分析仪查时序、GPIO 翻转测耗时、数据断点查踩内存
- 排障心法：先数据后逻辑、二分夹逼、一次改一处

## 课后思考题

1. 为什么调试器能"暂停"正在运行的芯片？（SWD 调试接口是 Cortex 内核硬件的一部分，DAP 单元可停核/读内存/单步——独立于 CPU 运行的旁路通道）
2. 断点为什么有数量限制？（硬件断点靠 Flash 地址比较器，Cortex-M3 只有 8 个——比软件断点强在不改代码，但硬件资源有限）
3. "时好时坏"的 bug 为什么栈溢出嫌疑最大？（溢出踩坏的是相邻内存/返回地址，破坏程度取决于当时的调用路径——每次踩的位置不同，表现随机）
