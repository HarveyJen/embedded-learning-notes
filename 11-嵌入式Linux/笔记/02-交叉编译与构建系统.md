# 02 · 交叉编译与构建系统

> 目标：搞懂"为什么 PC 编译的程序板子跑不了"，掌握工具链三件套、手写 Makefile、CMake 入门、GDB 远程调试——把宿主机变成板子的"云厨房"。

## 1. 交叉编译：两头语言不通的翻译官

**这是什么/解决什么问题**：PC 是 x86，板子是 ARM——指令集不同，gcc 直接编出的程序 ARM CPU 看不懂。类比：**在 A 国翻译 B 国的书**——翻译官（工具链）住在中国（x86 PC），产出的书（可执行文件）是给德国读者（ARM 板子）看的。为什么不直接在板子上编？嵌入式板子算力和内存小，跑不动编译器这头"大象"。

**解法**：**交叉工具链**（运行在 x86、产出 ARM 代码的编译器全家桶）：

```
arm-linux-gnueabihf-gcc     编译器（-hf=硬浮点）
arm-linux-gnueabihf-ld      链接器
arm-linux-gnueabihf-gdb     远程调试器
arm-linux-gnueabihf-objdump 反汇编（看启动代码神器）
```

命令格式规律：**架构-系统-abi-工具**。i.MX6ULL 用 arm-linux-gnueabihf-，RK/全志同款。

**工具链从哪来**：①板厂 SDK 自带（首选，版本匹配最稳）；②Linaro 官方下载；③Buildroot 自动生成。C 笔记01 的"编译四步"（预处理→编译→汇编→链接）在交叉编译里一步不少——只是每步换成了 ARM 版工具。

```bash
export CROSS_COMPILE=arm-linux-gnueabihf-     # 环境变量声明（内核/Buildroot 都认它）
${CROSS_COMPILE}gcc main.c -o main
file main                                      # 验证：ELF 32-bit ARM → 对了
```

**命令白话**：`export`=把变量广播给之后的所有命令（不 export 就只在本行有效）；`${CROSS_COMPILE}gcc`=拼出完整编译器名字再调用；`file`="验货员"——查验一个文件到底是给谁编译的（x86 还是 ARM、静态还是动态链接）。编完必用 `file` 验一眼，能省掉一大半"板上跑不起来"的冤案。

## 2. Makefile 精讲：工程自动化的通用语法

**这是什么/解决什么问题**：工程一多（几十上百个 .c），手敲 gcc 命令要命，且改一个文件不知道要重编哪些。Makefile 就是给 `make` 这个"施工队长"的**施工单**——写清哪个成品（目标）由哪些材料（依赖）、用什么工序（命令）做成；你只管敲 `make`，队长自动比对时间戳，**只重做必要的工序**。

### 2.1 三大核心规则

```makefile
目标(target): 依赖(prerequisites)
<TAB>命令(command)              # 必须是 TAB！空格必报错（新手第一大坑）

# 语义：目标比依赖旧（或不存在）→ 执行命令更新它
```

### 2.2 手写一个通用工程 Makefile（背下来当模板）

```makefile
# ===== 可变配置 =====
CROSS   = arm-linux-gnueabihf-
CC      = $(CROSS)gcc
CFLAGS  = -Wall -O2 -I./include          # -I 头文件搜索路径
LDFLAGS = -lpthread                       # 链接库：线程
TARGET  = gateway
SRCS    = $(wildcard src/*.c)             # 自动收集 src 下所有 .c
OBJS    = $(SRCS:.c=.o)                   # 变量替换：.c → .o

# ===== 总目标 =====
$(TARGET): $(OBJS)
	$(CC) $^ -o $@ $(LDFLAGS)             # $^=全部依赖  $@=目标名

# ===== 模式规则：所有 .o 由同名 .c 编出 =====
%.o: %.c
	$(CC) $(CFLAGS) -c $< -o $@           # $<=第一个依赖（那个 .c）

clean:
	rm -f $(OBJS) $(TARGET)

.PHONY: clean                              # 声明伪目标（若目录里恰好有个叫 clean 的文件，make 见"目标已存在"就跳过；声明后 make clean 永远执行）
```

**五个自动化变量**：`$@` 目标、`$^` 全部依赖、`$<` 首依赖、`$(wildcard)` 通配收集、`$(SRCS:.c=.o)` 后缀替换。**make 的心智**：只重编改过的文件（按时间戳比对）——几百个文件秒级增量构建。

### 2.3 常用姿势

```bash
make                 # 全量构建
make -j4             # 4 线程并行（提速）：派 4 个工人同时开工
make clean && make   # 推倒重来
make V=1             # 显示完整命令（排错）：把队长的暗语展开成明话
```

## 3. CMake 入门：写一次，处处生成 Makefile

**这是什么/解决什么问题**：Makefile 平台相关、手写繁琐 → CMake 用 `CMakeLists.txt` 描述工程，**自动生成**对应平台的 Makefile/Ninja（大型工程事实标准）。类比：Makefile 是手写施工单，**CMake 是"施工单生成器"**——你只描述工程长什么样（有哪些源文件、编成什么），它在 Linux 生成 Makefile、在 Windows 生成 VS 工程，一次编写到处构建。

```cmake
cmake_minimum_required(VERSION 3.10)
# 交叉编译设置必须放在 project() 之前——project() 会据此选择/探测编译器
set(CMAKE_SYSTEM_NAME Linux)                        # 声明交叉编译
set(CMAKE_SYSTEM_PROCESSOR arm)
set(CMAKE_C_COMPILER arm-linux-gnueabihf-gcc)

project(gateway C)

set(CMAKE_C_FLAGS "-Wall -O2")
include_directories(include)
file(GLOB SRCS "src/*.c")
add_executable(gateway ${SRCS})
target_link_libraries(gateway pthread)
```

```bash
mkdir build && cd build
cmake ..            # 生成 Makefile（只第一次）：建个"施工棚"单独放生成的文件，不污染源码目录
make -j4            # 编译（以后改代码只跑这步）
```

**选型**：小工程手写 Makefile（学原理）；工程化一律 CMake（少造轮子）。**先懂 Makefile 再用 CMake**——否则出错看不懂。

## 4. 运行与调试：nfs/ssh/scp 三条搬运路

**这是什么/解决什么问题**：程序在 PC 上编好了，怎么弄上板、怎么调试？三条搬运路各司其职。最省事的是 **NFS 网络文件系统**：把 PC 的一个目录"共享"给板子挂载——PC 上编译完，板子上立刻能跑，**免拷贝**，开发期全程用它。

`mount` 命令白话：把一个存储位置"接到"本地某个目录上（挂载）——之后访问该目录就是访问那个存储位置。

| 方式 | 姿势 | 适用 |
|------|------|------|
| scp | `scp gateway root@192.168.1.100:/root/` | 偶尔传文件 |
| **NFS 挂载** | 板子 mount 宿主机目录，编译完立即见 | **开发首选**（免拷贝） |
| tftp/ftp | U-Boot 阶段拉内核用 | 系统构建时 |

```bash
# 板子上（NFS）：
mount -t nfs -o nolock,vers=3 192.168.1.50:/home/user/nfs_root /mnt
/mnt/gateway
```

**GDB 远程调试三板斧**（C 笔记01 gdb 技能的跨机版）。白话：`gdbserver`=板子上先跑一个"被遥控的替身"，替身带着你的程序跑；宿主机上的 gdb 通过网络发指令遥控它——**断点、单步都作用在板子真机上**，操作手感却和本机调试一样：

```bash
# 板子：gdbserver :1234 ./gateway        # 等 CPU 端
# 宿主机：
arm-linux-gnueabihf-gdb gateway
(gdb) target remote 192.168.1.100:1234  # 接上
(gdb) b main / c / bt / info threads     # 断点/继续/调用栈/线程列表——单步走起
```

## 5. 静态库与动态库（板子上的 .so 之惑）

**这是什么/解决什么问题**：库=别人写好打包的常用功能（"预制菜"）。两种吃法：**静态库**=把菜直接炒进你的便当（程序独立、体积大）；**动态库**=到饭店点菜（运行时才去找 .so，多个程序可共享一份、体积小但依赖环境）。

命令白话：`ar`=把一堆 .o 打包成 .a 静态库；`-fPIC -shared`=生成"位置无关"的动态库（装到内存哪个地址都能用）；`-L. -lfoo`=告诉链接器去当前目录找名叫 foo 的库。

```bash
# 静态库：编进程序，体积大但独立
ar rcs libfoo.a foo.o
gcc main.c -L. -lfoo -static

# 动态库：运行时才找，体积小、可热更
gcc -fPIC -shared foo.o -o libfoo.so
gcc main.c -L. -lfoo        # 板上运行报 "not found"？
export LD_LIBRARY_PATH=/root/lib:$LD_LIBRARY_PATH    # 告诉它去哪找（或 ldconfig 配置）
```

`LD_LIBRARY_PATH` 白话：给系统加"额外货架"——程序运行找 .so 时，除了默认货架（/lib /usr/lib），也去这些目录翻。

**头号坑：交叉编译的程序板子上"library not found"**——宿主机链接的 .so 与板上根文件系统的 .so 版本不一致/没拷过去。解法：库也从板厂 rootfs 取，或 Buildroot 里一起构建。

## 6. 常见坑

怎么读这张表：左列是出错原因，右列是你看到的报错/症状——排查时**从现象反查原因**。构建类报错信息很"凶"，其实九成是这张表里的老面孔。

| 坑 | 现象 |
|----|------|
| Makefile 用空格缩进 | missing separator |
| 忘 export CROSS_COMPILE | 内核/Buildroot 编出 x86 版 |
| -I 头文件路径漏 | fatal error: xxx.h: No such file |
| -l 库名顺序错 | undefined reference（链接器从左往右扫：用到符号时它依赖的库还没登场就报错——被依赖的库放在用它的目标文件后面） |
| 板上跑 PC 版程序 | cannot execute binary file: Exec format error |
| 动态库版本不匹配 | version `GLIBC_x.xx' not found（工具链 glibc 与板端不匹配——换板厂工具链） |
| NFS 挂载忘 nolock | 卡死无响应 |

## 7. 章节小结

- 交叉编译=x86 上产 ARM 代码；工具链认 `arm-linux-gnueabihf-` 前缀，`file` 命令验真身
- Makefile 三规则+五变量+增量构建；CMake 一份描述生成多平台构建——先懂 make 再用 cmake
- 搬运三板斧 scp/NFS/tftp；gdbserver 远程调试=断点单步上板
- 库两分法：静态独立、动态共享；板上 not found 先查 LD_LIBRARY_PATH 与 glibc 匹配

## 课后思考题

1. 为什么内核和 U-Boot 必须用交叉编译而"板子上的程序"也可以在板上原生编译？（工具链产出的代码与运行平台绑定；板上原生编译=自己编给自己（速度慢、依赖全）——**谁产码给谁跑**，交叉只是"产地与消费地分离"）
2. make 的增量构建依据什么？什么情况会"该编不编"？（文件时间戳；时钟错乱（NFS 两端时间不同步）或头文件依赖未声明（.h 改了 .o 不重编）——大型工程用 `-MMD` 自动生成依赖文件解决）
3. 为什么大厂偏爱 Yocto/Buildroot 而不是"手工 rootfs+apt"？（可复现性：配置文件进 git，一键重建一模一样的系统；apt 在板上装=版本漂移不可控——**构建即代码**，与 CI/DevOps 思想同源）
