# 04 · 设备树与字符设备驱动

> 目标：理解"驱动=内核代理硬件"的分层模型，写通 LED 驱动与按键中断驱动，吃透设备树——Linux 方向面试的深水区。

## 1. 驱动的世界观：三层分离

**这是什么/解决什么问题**：在 Linux 里，应用程序**永远不许直接碰寄存器**——所有硬件都由"驱动"这个内核代理人代管。本节建立三层世界观：应用（提需求）→ 系统调用（传话窗口）→ 驱动（真正动手）→ 硬件（物理世界）。理解了这三层，驱动开发的一切语法都是给这个模型填空。

```
用户态：myapp.c     open("/dev/led") → write(fd,"1",1)     （应用：只认设备文件）
────────────── 系统调用边界（用户态/内核态的分界线）──────────────
内核态：led.ko 驱动  file_operations{ .write = led_write }  （驱动：真正碰寄存器的唯一角色）
硬件 ：GPIO 控制器寄存器                                       （物理世界）
```

**为什么这么绕**（对比 STM32 直接写寄存器）：
1. **安全**：MMU 隔离下用户态碰不到物理地址，内核统一仲裁（一个程序写坏不殃及全系统）；
2. **复用**：应用写 `/dev/xxx`，底下是 GPIO 还是 SPI 传感器无所谓——**接口稳定，硬件可换**；
3. **并发**：驱动帮应用处理了多进程同时访问的竞争。

类比：**银行柜台**——你（应用）不能进金库（寄存器），只能对柜员（驱动）说要办什么业务；柜员按章程（file_operations）操作金库。

## 2. 设备树：硬件的"户口本"

**这是什么/解决什么问题**：设备树（Device Tree）是一份**描述硬件的数据文件**——这块板子有哪些设备、接在哪个地址、用什么引脚，全写在这份文本里，与驱动代码分离。类比：**硬件户口本**——驱动是"办事的人"，设备树是"户口本"，办什么事查哪页都照本本来。换了板子=换一本户口本，驱动代码不用改。

### 2.1 语法核心（.dts → dtc 编译 → .dtb）

文件链路白话：`.dts/.dtsi`=人读的文本源码；`dtc`（设备树编译器）把它编成 `.dtb` 二进制；内核启动时读的是 `.dtb`。

```dts
/ {
    model = "MyBoard";

    /* pinctrl：引脚复用与电气配置（引脚当 GPIO 用，不冲突） */
    pinctrl_led: ledgrp {
        fsl,pins = <
            MX6UL_PAD_GPIO1_IO03__GPIO1_IO03  0x10B0    /* IO03 复用为 GPIO1_3；0x10B0 是电气参数打包值（上拉/速度/驱动能力等位标志），板厂手册可查，初学照抄即可 */
        >;
    };

    leds {
        compatible = "gpio-leds";               /* 兼容字符串：内核靠它匹配驱动 */

        led0 {
            label = "run";
            gpios = <&gpio1 3 GPIO_ACTIVE_LOW>; /* 在 gpio1 控制器第 3 脚，低电平点亮 */
            default-state = "off";
        };
    };
};
```

**三条铁律**：
- `compatible` 是驱动匹配的钥匙（内核 of_match_table 逐个对）；
- 引用用 `&label`（`&gpio1` 引用芯片自带节点）；
- 改完必须 `make dtbs` 重编 dtb 并替换板上那份才生效。

### 2.2 驱动里读设备树

```c
static const struct of_device_id led_of_match[] = {
    { .compatible = "gpio-leds" },
    { }
};

static int led_probe(struct platform_device *pdev)     /* 匹配成功 → 内核喊 probe */
{
    /* 从设备树拿 GPIO 编号（代替 STM32 时代的手抄引脚号） */
    led_gpio = of_get_named_gpio(pdev->dev.of_node, "gpios", 0);
    devm_gpio_request_one(&pdev->dev, led_gpio, GPIOF_OUT_INIT_LOW, "run");
    ...
}
```

**probe 机制**：设备树节点 ↔ 驱动 compatible 匹配 → 内核自动调 probe——**硬件描述与驱动代码在运行时"相亲"**。

**probe 相亲·时间线分步看**（驱动与设备怎么对上号，逐帧回放）：

1. **第 1 帧·登记甲方**：内核启动/模块加载时，驱动把自己的 `of_match_table`（compatible 候选名单）交给总线登记处；
2. **第 2 帧·登记乙方**：设备树里的节点被内核展开成 device（设备对象），随身携带自己的 compatible；
3. **第 3 帧·牵线**：总线比对两边 compatible——`"gpio-leds"` 撞上 `"gpio-leds"`，配对成功；
4. **第 4 帧·喊 probe**：内核自动调用驱动的 `probe` 函数——"恭喜，这门亲成了，去把硬件初始化吧"；
5. **第 5 帧·probe 干活**：从设备树读 GPIO 编号、申请引脚、注册字符设备——引脚号等细节全部来自"户口本"，驱动代码里不写死。

compatible 拼错=相亲永远失败、probe 永远不来——这是新手"驱动加载了但毫无反应"的头号原因（先查 compatible，再查 dts 有没有重编替换）。

## 3. 字符设备驱动框架（最小完整版）

**这是什么/解决什么问题**：字符设备驱动=亲手写一个"银行柜员"——实现一组函数（open/read/write...）登记进内核，此后用户态对 /dev/xxx 的每次 open/read/write 都会转到这里执行。先通读下面的最小骨架，再看关键术语白话。

**术语白话**：`dev_t 设备号`=主设备号（找哪家柜员团队）+次设备号（团队里第几号窗口）；`cdev`=字符设备在内核里的"登记证"；`file_operations（fops）`=柜员的**业务章程**——用户每调一个系统调用，内核就按章程转发到你的同名函数；`copy_from_user`/`copy_to_user`=内核与用户态之间的**安检门**——用户给的缓冲区地址不可信，必须拷进来/拷出去用。

```c
#include <linux/module.h>
#include <linux/fs.h>
#include <linux/uaccess.h>

static dev_t devno;                 /* 设备号 = 主（哪类驱动）+ 次（第几个实例） */
static struct cdev led_cdev;

static int led_open(struct inode *ino, struct file *filp)  { return 0; }

static ssize_t led_write(struct file *filp, const char __user *ubuf,
                         size_t len, loff_t *off)
{
    char kbuf[2];
    if (copy_from_user(kbuf, ubuf, 1))       /* 用户缓冲不能直接碰！copy 拷进内核 */
        return -EFAULT;
    gpio_set_value(led_gpio, kbuf[0] - '0'); /* '1'→高 '0'→低 */
    return 1;
}

static const struct file_operations led_fops = {   /* 柜员的业务章程 */
    .owner = THIS_MODULE,
    .open  = led_open,
    .write = led_write,
};

static int __init led_init(void)     /* insmod 时跑 */
{
    alloc_chrdev_region(&devno, 0, 1, "myled");    /* 申请设备号 */
    cdev_init(&led_cdev, &led_fops);
    cdev_add(&led_cdev, devno, 1);                 /* 注册进内核 */
    /* 实际工程用 class_create + device_create 自动生成 /dev/led（udev/mdev 建节点） */
    return 0;
}

static void __exit led_exit(void)    /* rmmod 时跑：与 init 严格对称逆序 */
{
    cdev_del(&led_cdev);
    unregister_chrdev_region(devno, 1);
}

module_init(led_init);
module_exit(led_exit);
MODULE_LICENSE("GPL");               /* 内核本身是 GPL，部分符号只对 GPL 模块开放——不声明则 insmod 报 Unknown symbol */
```

**用户态验收**：

```bash
insmod led.ko && mknod /dev/led c 245 0     # 加载+建节点（或自动）
echo 1 > /dev/led                            # 灯亮！echo "0" 灯灭
```

**命令白话**：`insmod led.ko`=把驱动模块塞进内核运行（触发 led_init）；`mknod /dev/led c 245 0`=手工建设备文件节点（c=字符设备，245/0=主/次设备号，要与申请的一致）；`echo 1 > /dev/led`=往设备文件写一个字符"1"——内核按章程转给 `led_write`，点灯。整条链就是"第 1 节三层模型"的现场演练。

**驱动四步曲**：申请设备号 → 绑 fops 注册 cdev → (probe 里)初始化硬件 → exit 对称清理。**MISPM：Module-insmod-fops-cdev**。

## 4. 按键中断驱动：async + waitqueue

**这是什么/解决什么问题**：这一节演示驱动的**睡眠-唤醒**标准模式——read 时没按键就睡（不占 CPU），中断来了被叫醒。它是驱动处理"等待类事件"（按键/有数据到达/硬件就绪）的通用姿势，比用户态死循环轮询优雅得多。

**API 白话**：`request_irq`=向内核申请"把某个中断号接到我的 ISR 上"；`wait_event_interruptible`=条件不满足就睡（浅睡眠，可被信号打断——所以叫 interruptible）；`wake_up_interruptible`=叫醒睡在这个队列上的人；`DECLARE_WAIT_QUEUE_HEAD`=定义一个"叫醒名单"（等待队列）。

```c
static DECLARE_WAIT_QUEUE_HEAD(key_waitq);
static volatile int key_pressed;                 /* volatile：中断会改（C 笔记09 兑现） */

static irqreturn_t key_isr(int irq, void *dev)   /* 上半部：快！只记账 */
{
    key_pressed = 1;
    wake_up_interruptible(&key_waitq);           /* 叫醒睡眠的读者 */
    return IRQ_HANDLED;
}

static ssize_t key_read(struct file *f, char __user *u, size_t l, loff_t *o)
{
    wait_event_interruptible(key_waitq, key_pressed);   /* 没按键就睡（不占 CPU） */
    key_pressed = 0;
    copy_to_user(u, "P", 1);
    return 1;
}
/* request_irq(gpio_to_irq(key_gpio), key_isr, IRQF_TRIGGER_FALLING, "mykey", NULL); */
```

**与 FreeRTOS 中断委托对照**：ISR 只置标志+唤醒 → 任务（这里=read 的睡眠者）干慢活——**同一条纪律换了方言**。防抖在驱动里用 `IRQF_TRIGGER_FALLING + 定时器消抖` 或软件消抖（03-51 篇三板斧思想照旧）。

## 5. 驱动开发的调试手段

**这是什么/解决什么问题**：驱动在内核态，出错轻则 Oops 重则死机，且没有 printf 直达屏幕——所以要靠这一套"内核态专用调试工具箱"。注意头号区别：**`printk`=内核版 printf，输出进内核日志缓冲区**，要用 `dmesg` 查看（应用层 printf 走 stdout，内核没有 stdout）。

| 手段 | 用途 |
|------|------|
| `printk`/`pr_info` | 驱动 printf，`dmesg | tail -20` 看（内核日志不分 stdout） |
| `cat /proc/kmsg` | 实时追 |
| **dev_dbg + 动态调试** | 上线可关的调试日志（正规军） |
| Oops 解析 | `Oops` 崩溃贴→objdump vmlinux 按地址定位（类比 HardFault 定位） |
| devmem 工具 | 用户态偷看寄存器（调试用，产品禁） |

## 6. 常见坑

怎么读这张表：驱动问题的现象往往很吓人（崩溃/无反应/系统卡顿），但原因九成是这张表里的老面孔——**从现象反查原因**，"probe 不来"先查 compatible，"装载失败"先查许可证与符号。

| 坑 | 现象 |
|----|------|
| 用户指针直接解引用 | 内核崩溃（必须 copy_from/to_user） |
| 忘 MODULE_LICENSE("GPL") | Unknown symbol 装载失败 |
| exit 与 init 不对称 | rmmod 后泄漏/再次 insmod 失败 |
| pinctrl 与驱动重复配 GPIO | 冲突报 pin already requested |
| compatible 拼错 | probe 永远不来（设备树相亲失败） |
| 中断处理函数里 sleep/printk 大量输出 | 系统卡顿（上半部禁睡） |
| 改了 dts 忘重编/没换板上 dtb | 改动"无效"（其实没生效） |

## 7. 章节小结

- 驱动=内核代理硬件：应用→系统调用→fops→寄存器，分层换安全复用并发
- 设备树=硬件户口本，compatible 相亲触发 probe；引脚配置走 pinctrl
- 字符驱动四步曲+copy_*_user 护城河；按键驱动=waitqueue 睡眠唤醒+ISR 只记账
- 调试靠 printk/dmesg/Oops 定位；exit 对称清理是模块的"售后义务"

## 课后思考题

1. 为什么内核驱动里 copy_from_user 不能直接 memcpy？（用户态指针可能非法（未映射/被换出），copy_from_user 内部有安全性检查与缺页处理；直接 memcpy=内核被用户数据击穿——**信任边界处必须验证**，与网络编程收包前校验长度同理）
2. 驱动里 read 睡眠与 FreeRTOS 任务阻塞的底层差异？（本质相同：从调度器摘除、事件唤醒；差异：Linux 可中断睡眠会被信号打断（wait_event_interruptible 返回 -ERESTARTSYS 要处理）——**信号维度是 Linux 独有**）
3. 若传感器是 SPI 接口，驱动架构怎么变？（用户接口不变（还是 /dev/xxx 的 read）；probe 里改用 spi 核心接口 spi_read——**上层协议驱动与底层传输总线驱动分层（spi core/I2C core）**，这正是 Linux 驱动子系统的设计红利）
