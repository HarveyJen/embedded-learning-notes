## 2. 开发路线图（两周节奏）

**这是什么/解决什么问题**：两周的施工顺序——原则是**先通最小闭环，再逐层加码**：先让数据从传感器流到浏览器（①~③），再上云（④），最后驱动化+守护（⑤~⑦）。任何一步卡住都不影响前面已验收的成果，这是项目管理的"增量交付"。

```
①Buildroot 定制 rootfs：加 dropbear/你的包 → 烧卡 ssh 可进（03 篇成果验收）
②采集打通：i2c-tools 手读 SHT30 → 用户态采集模块（最快见效）
③Web 服务：epoll+HTTP → /api/data 返回 JSON → 浏览器看数
④MQTT：订阅 cmd/gw001/# 发布 data/gw001/#，遗嘱上线报备
⑤驱动化：LED 呼吸灯驱动+按键配置驱动（04 篇代码直接复用）
⑥整合看门狗线程 + init.d 自启 + 日志轮转（logrotate 或自研按天切割）
⑦压力与长跑：72h 运行，内存 fd 无泄漏（ps/ls /proc/PID/fd 监控）
```

## 3. 关键实现细节

### 3.1 线程数据流（生产者消费者标准实现）

**这是什么**：生产者-消费者队列是整个网关的"传送带"——采集线程（生产者）往里放数据，Web/MQTT 线程（消费者）从里取。`mutex` 保证同一时刻只有一人动队列，`cond`（条件变量）负责"叫醒睡着的消费者"。这个结构在 01 篇学过零件，这里是整机安装。

```c
typedef struct { float temp, humi; uint32_t ts; } Sample_t;

typedef struct {
    Sample_t buf[64];
    int head, tail;
    pthread_mutex_t lock;
    pthread_cond_t  notempty;
} SQueue;

void SQueue_Push(SQueue *q, Sample_t *s) {
    pthread_mutex_lock(&q->lock);
    q->buf[q->head] = *s;                       /* 简化：满则覆盖最旧（遥测可丢策略） */
    q->head = (q->head + 1) % 64;
    pthread_cond_signal(&q->notempty);          /* 醒消费者：按铃叫醒一个等数据的线程 */
    pthread_mutex_unlock(&q->lock);
}
```

### 3.2 HTTP API（epoll 单线程 Web）

**这是什么**：HTTP API 就是产品的"遥控面板"——GET=取数据（只读不改），POST=下发指令（会改状态）。所有远程能力都从这几个接口长出来，注意 POST 类操作必须鉴权。

```c
/* GET /api/data    → {"temp":25.3,"humi":60.1,"uptime":3600}
   GET /api/config  → 阈值配置
   POST /api/reboot → 鉴权重启（token 校验！） */
```

### 3.3 MQTT 主题设计（07 篇 06 的命名即架构）

**这是什么**：MQTT 主题（topic）是云端与设备的"分机号码"——命名规划好了，谁跟谁说话一目了然。规则：`data`=上行遥测、`cmd`=下行指令、`status`=生死报备（遗嘱）。

```
data/gw001/env          遥测（5s QoS1）
status/gw001/online     遗嘱+上线报备
cmd/gw001/reboot        远程重启（鉴权后执行，回执 status/gw001/reboot）
cmd/gw001/threshold     阈值下发 → 存配置文件 → 回执
```

### 3.4 看门狗（跨线程版）

**这是什么**：看门狗=自动"查岗"机制——每个线程定期打卡，监控线程巡检：谁没打卡说明谁卡死了，杀掉进程整体重启自愈（FreeRTOS 喂狗思想的多线程版）。这是产品"长时间无人值守"的底气。

```c
/* 各线程每 5s 心跳位打点 → 监控线程 10s 巡检：缺卡线程 → 记日志 → 杀进程重启（systemd 拉起） */
```

## 5. 常见坑

怎么读这张表：左列原因、右列现象——项目集成阶段的坑多为"多线程+外设+系统"的交叉问题，排查思路：先二分定位是哪一层（采集/Web/MQTT/驱动），再对照本表找同类。

| 坑 | 现象 |
|----|------|
| 线程读写共享 Sample 无锁 | 数据撕裂（mutex 全覆盖） |
| Web 与 MQTT 各自持锁交叉 | 死锁（统一加锁顺序：先 dataLock 后 cfgLock） |
| i2c 读偶发 NACK 不恢复 | 采集停摆（重试+总线恢复流程） |
| 日志写满 SD 卡 | 系统卡死（轮转+水位监控） |
| POST 无鉴权 | 任何人可重启设备（token/最小化暴露） |
| 自启脚本环境变量缺失 | 手动跑正常，自启就挂（PATH/LD_LIBRARY_PATH 写全） |

## 课后思考题

1. 采集与 Web 为什么分线程而不是一个大循环？（隔离故障域与节奏：Web 卡了采集照跑；epoll 单线程 Web 无锁内聚，采集侧 mutex+cond 解耦——**节奏不同、故障域不同的模块必须分流**，与 FreeRTOS 任务划分同律）
2. 为什么 LED/按键放内核驱动而 SHT30 可以用户态 i2c-dev 直接读？（LED/按键要精确时序/中断响应/多进程共享——内核代理合适；低速简单 I2C 设备用户态轮询够用——**复杂度与收益匹配，能简单就简单**）
3. 如果把它卖给 100 家工厂，你会补上哪些工程化？（OTA（08 篇思想：A/B rootfs+U-Boot 切换）、TLS+独立证书、远程日志收集、批量烧录产测流程、版本与资产管理——**从 demo 到产品隔着的是可维护性与安全**）
