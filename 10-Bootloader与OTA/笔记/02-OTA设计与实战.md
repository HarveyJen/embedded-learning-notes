# 02 · OTA 设计与固件升级实战

> 目标：在 IAP 基础上构建完整 OTA：升级协议、双分区回滚、断点续传、固件校验与加密——量产级固件升级的完整心智模型。

## 1. OTA 全景：从"云端有新版"到"设备跑新版"

这一节先立全景：一次 OTA 要过六关，**设计难度全在失败路径**——每一关都可能掉电、断网、收坏包，任何一关失败都不能变砖。

```
云端服务器（固件仓库）
   │ ①设备查询版本（MQTT/HTTP）
   ▼
APP（运行中）──发现新版──②下载固件包（W25Q64 暂存 / 直写备用分区）
   │ ③校验（CRC/签名/版本/硬件型号）
   ▼
④设置升级标志 → 复位
   ▼
Bootloader：标志有效 → ⑤搬运固件到运行区 → 校验 → 跳转
   ▼
⑥新固件自检通过 → 写"确认标志"（否则 Bootloader 回滚旧版）
```

**六步时间线**（把图走成故事，主角是设备）：

- 第 1 步（APP 在跑）：设备空闲时向云端查询版本——"有新版吗？"云端答"有，1.2.3"；
- 第 2 步：APP 里的下载任务开工，固件包一块一块落进 W25Q64 暂存区——**绝不直接覆盖运行区**：运行中的 APP 不能擦自己脚下的地；
- 第 3 步：下载完 → 全量校验（CRC/签名/版本/硬件型号，第 2 节四道安检门）→ 不合格就地丢弃，设备继续跑旧版，用户无感；
- 第 4 步：校验通过 → 把"启动 B 试运行"标志写进参数区（掉电不丢）→ `NVIC_SystemReset()`；
- 第 5 步：复位后 Bootloader 先跑 → 读标志 → 验 B 区固件头 → 跳进 B 区新固件（A 区旧版原封不动待命）；
- 第 6 步：新固件在试运行窗口（如 30s）内自检通过 → 主动写"确认标志"转正；没写 → Bootloader 下次复位自动切回 A 区。

**六个环节，任何一环失败都不能变砖**——OTA 设计的全部难度就在"失败路径"。

## 2. 升级包设计：固件头（Firmware Header）

这一节回答"升级包长什么样、设备凭什么信它"。设计思想：把"检查清单"做成结构体钉在包最前面，Bootloader 收到先查单、再收货。

升级包 = **固件头 + 固件本体**，头是"快递面单"：

```c
typedef struct {
    uint32_t magic;        /* 0x50544F48 'HOTP'——头合法性 */
    uint16_t hwVer;        /* 硬件版本——防刷错硬件！ */
    uint16_t fwVer;        /* 固件版本 1.2.3 → 0x010203 */
    uint32_t fwSize;       /* 固件字节数 */
    uint32_t fwCrc;        /* 本体 CRC32 */
    uint32_t buildTime;    /* 编译时间戳 */
    uint8_t  sign[16];     /* 签名/摘要（简化版：密钥 HMAC 截断） */
    uint8_t  res[12];
} FwHeader_t;              /* 32 字节，放包最前 */
```

**四道安检门**（Bootloader 写入前逐个过）：
1. magic 对不对（是不是我们的包）；
2. hwVer 匹配吗（A 型号固件刷进 B 硬件 = 事故）；
3. fwVer 必须 > 当前版本（防降级攻击/防手滑刷旧版）；
4. CRC32 对得上吗（传输损坏拦截）。

四道门的逻辑：1 验"是不是自家人"，2 验"衣服合不合身"，3 验"是不是倒退回旧社会"，4 验"路上有没有磕碰"——任何一道不过，包就地拒收，设备照常跑旧版。

## 3. 双分区与回滚：不变砖的最后防线

这一节回答"新固件万一是个坏固件，怎么保证设备还活着"。三件套：双分区（备胎常在）+ 试运行确认（转正要签字）+ 回滚计数（屡次失败就放弃）。

### 3.1 流程（与 01 篇 A/B 区配合）

```
新固件 → 写 APP_B → 头校验通过 → 置标志"启动B试运行" → 复位
Bootloader：读标志 → 搬 B→A？不！直接跳 B（省一次搬运）
试运行窗口（如 30s）内新固件自检通过 → APP 调 Bootloader 接口写"确认标志"
    ├─ 确认 → B 区转正，A 区留旧版待命
    └─ 30s 没确认（新固件跑飞/死循环）→ Bootloader 自动切回 A 区 + 计数
         连续 3 次启动失败 → 永久锁定旧版 + 上报告警
```

**回滚机制时间线**（拿一个"10 秒后死循环"的坏固件走一遍）：

- 第 1 步：Bootloader 读到"启动 B 试运行"标志 → 启动计数 +1 → 跳进 B 区；
- 第 2 步：新固件跑了 10s 死循环（模拟跑飞）→ 自检永远没完成 → 确认标志没人写；
- 第 3 步：看门狗复位设备 → Bootloader 又见"试运行"标志、计数已是 1 → 再给 B 一次机会；
- 第 4 步：连续 3 次试运行都没等到确认 → 判定新固件不可救药：**锁定 A 区旧版、清标志、上报"升级失败"**；
- 第 5 步：设备带着旧版本继续工作——用户损失的是"没升成级"，而不是"设备变砖"。

### 3.2 关键代码：试运行确认

```c
/* APP 侧：所有关键自检（传感器在线/通信正常/参数区完好）通过后调用 */
void OTA_ConfirmFirmware(void)
{
    if (!SelfCheckPassed()) return;                  /* 自检不过：绝不写确认标志，原地返回等 Bootloader 回滚 */
    BKP->DR1 = FW_CONFIRM_MAGIC;                     /* 写备份寄存器：F103 是 BKP->DR1（先开 PWR/BKP 时钟），F4/H7 才写作 RTC->BKPxR（01 篇思考题兑现） */
}
```

关键行拆解：

- `SelfCheckPassed()`——确认的前提：传感器在线、通信正常、参数区完好，**全部通过才轮到"转正"**（坑表里"自检没跑完就确认"就是栽在这）。纪律就一条：自检不过 → early return，绝不落到写标志那一行——旧版示例用"拖着 osDelay(1000)"是错的，睡一觉醒来还是会误写标志，把回滚机制骗过；
- `BKP->DR1 = FW_CONFIRM_MAGIC;`——写确认标志到备份寄存器：单字原子写不怕掉电半写（对照 Flash 参数区的"半写损坏"风险），且电池供电下掉电不丢。

类比：**试用期转正**——新固件先"试岗"30 秒，干得好（自检过）HR（Bootloader）转正；干不好自动退回老员工（A 区），公司不停摆。

## 4. 断点续传：弱网升级的刚需

这一节回答"4G/WiFi 传到一半断了怎么办"。思路同下载大文件：**把进度记下来，重连接着传**。

4G/WiFi 传 200KB 固件，断网重传全量 = 用户等到崩溃。类比浏览器下载的**进度条**：断线重连后从 63% 继续，而不是从零开始；位图就是设备端的进度条，存掉电不丢的地方，断电也不清零。**分块 + 已收位图**：

```c
typedef struct {
    uint32_t totalSize;
    uint32_t blockSize;      /* 如 1KB/块 */
    uint32_t receivedBlocks; /* 已收块数 */
    uint8_t  bitmap[32];     /* 位图：bit=块已收（1KB×32B=256KB 覆盖） */
} DlProgress_t;              /* 存 W25Q64 或备份域，断电不丢 */

/* 重连后：设备上报 bitmap → 服务器只发缺失块 */
```

**简化务实版**：顺序下载只记 `receivedBlocks` 偏移（HTTP Range/MQTT 分块序号），断点从偏移继续——位图版用于乱序包（差分升级场景）。

## 5. 固件安全：加密与签名（工业级必答）

这一节回答"升级通道会不会被人利用"：传输损坏、伪造固件、抓包逆向、旧版本回流——四类威胁四样对策，安全预算跟着产品定位走。

| 手段 | 防什么 | 做法 |
|------|--------|------|
| CRC32 | 传输损坏 | 头里带 CRC（已讲） |
| **签名/HMAC** | 伪造固件（逆向魔改刷入） | 服务器私钥签 → 设备公钥验（真签名）；或共享密钥 HMAC（简化，密钥在设备=可被提取） |
| **固件加密** | 升级包被抓包逆向 | AES-128 加密本体，密钥藏在加密芯片（LX-750PLUS BOM 的 LKT4105U 就是干这个的——**先烧密钥再贴片**） |
| 防降级 | 旧漏洞固件回流 | 版本单调递增（已讲） |

**分级结论**：玩具级=CRC 够了；商用级=HMAC；联网产品/涉密=加密芯片+真签名。安全预算跟着产品定位走。

## 6. 与 07 毕业项目对接：MQTT 升级通道

这一节把 OTA 挂到通信层：云端一条 MQTT 命令触发下载任务——**升级是"业务外"的重活，独立任务、独立看门狗打卡**。

```c
/* 云命令触发升级（复用 07 篇订阅命令架构） */
void OnMqttCmd(char *topic, char *payload)
{
    if (strcmp(topic, "cmd/dev001/ota") == 0) {
        /* payload = {"url":"...fw.bin","ver":"1.2.3","crc":"A5B6..."} */
        ParseOtaCmd(payload, &otaTask);              /* 校验版本>CURRENT、CRC 预检 */
        xTaskNotify(otaTaskHandle, NOTIFY_START_DOWNLOAD, eSetBits);  /* 交给下载任务 */
    }
}
```

下载任务：HTTP Range 分块拉取 → 写 SPI Flash 暂存 → 全量 CRC → 置标志 → `NVIC_SystemReset()`。**升级是"业务外"的重活，永远独立任务+独立看门狗打卡**（FreeRTOS 06 篇架构纪律）。

## 7. 常见坑

| 坑 | 现象 |
|----|------|
| 写完立即复位，缓存未落盘（外存） | 搬运读到半新半旧（写完回读校验再复位） |
| 回滚计数不放掉电保持区 | 反复复位凑不满 3 次，砖循环 |
| 新固件版本号算错（1.10 < 1.9 字符串比较） | 合法升级被拒（版本用 BCD/整数比较，别 strcmp） |
| 试运行窗口内自检还没跑完就确认 | 坏固件转正 → 变砖（确认=最后一步，别提前） |
| 下载占满带宽饿死遥测 | 升级任务低优先级 + 限速分块 |
| 升级包 URL 无鉴权 | 任意人可推固件（命令话题也要鉴权，07 篇 QoS1+鉴权闭环） |

## 8. 章节小结 & 阶段三总毕业

收尾前把全阶段串成一句话：RTOS 让设备"多线程地干活"，通信让它"听得见云端"，OTA 让它"自己长大"——三样合体，才是一台完整的现代联网设备。

- OTA 六环节：查版本→下载→校验→标志复位→Bootloader 搬运跳转→试运行确认，**失败路径决定设计**
- 固件头四安检门：magic/硬件版本/单调版本/CRC；安全分级：CRC→HMAC→加密芯片
- 双分区+试运行确认+回滚计数 = 不变砖铁三角；断点续传救弱网
- **阶段三全部毕业**：RTOS + 通信 + OTA = 一台"可远程升级的联网设备"完整能力闭环——单片机方向求职的技术底牌齐了

## 课后思考题

1. 为什么"确认标志"必须由新固件主动写，而不是 Bootloader 跳转成功就算确认？（跳转成功≠功能正常（可能跑飞/外设死）；只有新固件自己"自检通过"才证明它值得转正——**健康判定权交给当事人，退出机制留给裁判**）
2. 若升级中掉电 100 次，系统会怎样？（每次掉电：标志/位图在备份域或外存完好 → 复位后 Bootloader 发现升级未完成 → 继续等待下载或回滚——状态机的所有中间态都持久化，掉电只是"暂停"，不是"倒带"——这就是可靠性设计的本质）
3. 对比"整包升级"与"差分升级"的取舍？（整包简单可靠、流量大；差分省 80% 流量但需服务器算差分+设备端合并+合并失败回退整包路径——**弱网/海量设备才值得为流量上复杂度**，工程复杂度永远要理由）
