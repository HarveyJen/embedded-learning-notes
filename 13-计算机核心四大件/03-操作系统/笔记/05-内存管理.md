# 05 · 内存管理

> 定位：OS 的"地皮管理学"。虚拟内存、页表、malloc 底层——学完本篇，malloc 不再是黑盒，FreeRTOS 的 heap_1~5 也能讲出理论出处。

**先说人话**：本篇讲 OS 怎么**分内存**（给进程切块地皮）和**护内存**（不让进程踩别人地盘）。为什么嵌入式工程师需要它：Linux 板子上 malloc 出过事（越界、泄漏、碎片），MCU 上 heap 爆过仓——底层机理是同一套，只是复杂度不同。

## 1. 程序怎么变成内存布局：链接视角 vs 运行视角

**这是什么**：同一个 .text/.data/.bss，在**两个时刻**被看见两次。类比：装修图纸（链接视角）vs 实际入住摆家具（运行视角）——图纸决定每个房间的用途，入住时才真正搬进去。

- **链接视角（静态）**：链接器把各 .o 的段按链接脚本拼装、定好**相对地址**——它只管图纸，不知道程序将来住进哪块物理内存；
- **运行视角（动态）**：OS 加载器把 ELF 的可加载段映射进进程的虚拟地址空间，BSS 清零、堆栈建好——图纸上的段各就各位；
- C 语法层面的分段与变量归属见 [08-内存布局与动态内存](../../../01-C语言基础/笔记/08-内存布局与动态内存.md)。

嵌入式对应（裸机/MCU）：没有虚拟层，链接脚本直接定**物理地址**——.text 烧 Flash（0x08000000 一带）、.data/.bss 在 RAM（0x20000000 一带），"加载"= 启动代码把 .data 从 Flash 拷进 RAM + 清零 BSS。**链接视角几乎等于运行视角**，这正是有/无 MMU 世界的分水岭。

## 2. 虚拟内存：给每个进程的"幻觉"

**这是什么**：**虚拟内存（virtual memory）** = 每个进程都以为自己独占一整条连续内存的"幻觉"。类比：**翻译官**——每个进程说自己的方言（虚拟地址），MMU（内存管理单元，负责地址翻译的硬件）当场译成真实地址（物理地址），隔壁进程说什么、住哪，你根本听不见也摸不着。

三大好处：
- **隔离**：翻译不到的地界就是摸不到——进程 A 崩了不殃及 B（02 篇"进程有墙"的出处）；
- **重定位**：程序不管链接到什么地址，翻译官一概兜住——编译器不必关心实际物理布局；
- **超额分配**：物理 8GB 也能让进程们"以为"各有 4GB——不常用的页暂搬到磁盘（swap，交换分区），要用再搬回来。

嵌入式对应：Cortex-M 只有 MPU（权限围栏，划几块区设读写权限）**没有 MMU**（无地址翻译）——所以 FreeRTOS 没有虚拟内存；Cortex-A（跑 Linux 的）才有 MMU。

## 3. 页表与 MMU：格子 + 账本 + 小抄

**这是什么**：虚拟/物理内存都切成固定大小的格子——**页（page）= 4KB**（常见大小）；**页表（page table）** = 记录"虚拟页号 → 物理页号"的账本；**TLB** = 翻译官随身的小抄（最近翻译结果的硬件缓存，不然每次访存都查账本就太慢了）。

翻译规则（32 位系统、4KB 页）：
- 虚拟地址拆两半：**高 20 位 = VPN**（虚拟页号，账本的第几行）+ **低 12 位 = 偏移**（页内的第几个字节，4KB = 2^12）；
- 拿 VPN 查页表得 **PFN**（物理页号），PFN 拼上原封不动的偏移 = 物理地址。

**缺页中断流程时间线**（页不在内存时，白话：翻译官发现这词字典里没有 → 暂停对话，去图书馆复印一页 → 抄进字典 → 请对方把刚才那句话再说一遍）：

```
t0  CPU 执行指令，发出虚拟地址
t1  MMU 查页表：有效位=0（该页不在内存）→ 硬件触发缺页异常
t2  内核缺页处理程序接管：先判断是合法访问还是越界（非法 → 段错误杀进程）
t3  合法：找一个空闲页框（没有就按替换算法把某页换出写回磁盘）
t4  从磁盘/swap 把这一页读进页框（最耗时的一步，毫秒级——比访存慢十万倍）
t5  更新页表项：填上 PFN、有效位置 1
t6  重新执行 t0 那条指令——这次翻译成功，进程毫无感知（只觉得慢了一下）
```

**两个顺手要答的"为什么"**：
- **页为什么是 4KB**：粒度折中——页太小，页表项太多（账本变厚、TLB 小抄覆盖差）；页太大，内部碎片变重（要 3KB 也得占一整格，白扔 1KB）。4KB 是几代硬件折中出的行业惯例（部分 ARM/RISC-V 配置支持 16KB/64KB 大页，换更薄的账本）；
- **页表为什么分多级**：32 位单级页表要 2^20 项 ≈ 4MB/进程，人人白背一本厚账本。拆成"目录套目录"（64 位普遍四级）后，**只用到的分支才建表**——像字典按部首分册，查哪册翻哪册。

## 4. 地址翻译代入小算例

**这是什么**：手算一遍，MMU 就不神秘了。条件：32 位系统、页 4KB（偏移 12 位）。

求虚拟地址 **0x00401234** 的物理地址（设页表里 VPN 0x00401 → PFN 0x12345）：

```
第1步 拆位：
  0x00401234 = 0000 0000 0100 0000 0001 | 0010 0011 0100
               └────── 高20位 VPN ──────┘ └─ 低12位偏移 ─┘
  VPN    = 0x00401        （0x00401234 >> 12）
  偏移   = 0x234          （页内位置，翻译时原样保留）

第2步 查页表：VPN 0x00401 对应 PFN 0x12345（页在内存，有效位=1）

第3步 拼物理地址：PFN << 12 | 偏移 = 0x12345000 | 0x234 = 0x12345234
```

记住两点：**偏移原样搬运**（格子内位置不变）、**只有页号要查账本**。64 位系统页仍是 4KB，只是页号位数更长、页表变多级——拆位思路一模一样。

## 5. 连续分配三策略：首次 / 最佳 / 最坏适应

**这是什么**：OS 给进程分内存（或 malloc 管堆）时，面对一排大小不一的空闲块，挑哪块？三种经典挑法。类比：停车——见第一个空位就停（首次）、挑最贴合车长的位（最佳）、挑最大的位（最坏）。

统一算例：空闲块从低到高为 **100K、500K、200K、300K、600K**，现在要分配 **212K**：

| 策略 | 规则（白话） | 挑中谁 | 结果 |
|------|------------|--------|------|
| 首次适应 First Fit | 从头扫，**第一个装得下**的 | 500K | 切走 212K，剩 288K 空块 |
| 最佳适应 Best Fit | 全扫一遍，**装得下的里最小**的 | 300K | 切走 212K，剩 88K 碎块 |
| 最坏适应 Worst Fit | 全扫一遍，**挑最大**的 | 600K | 切走 212K，剩 388K 大块 |

碎片讨论：
- **外部碎片**（总空间够、连续空间不够——01 篇的白话定义）：三种策略都会产生，形态不同——最佳适应专产"细碎小空块"（量大难用），最坏适应把大块快速切碎，首次适应最快且实战碎片分布通常不差；
- **内部碎片**：按 4KB 页这类**固定格**分配时，要 3KB 占一格浪费 1KB——分页机制的固有代价。

**碎片接力小演算**（承接上表，全部按首次适应）：

```
第1次分配 212K → 用掉 500K 那块，空闲：100、288、200、300、600
第2次分配 300K → 恰好用光 300 那块，空闲：100、288、200、600
第3次分配 350K → 只有 600 装得下，    空闲：100、288、200、250
第4次要 300K  → 总空闲 838K，但最大块只有 288K —— 分配失败！
```

总量够、连续不够——**外部碎片现行**。解药是"合并相邻空块"：第 7 节 heap_4 的"拼桌"、Linux 伙伴系统的"兄弟合并"，治的都是它。

嵌入式对应：FreeRTOS heap_4 用的就是首次适应 + 相邻合并；STM32 常见的外挂 SRAM 多池方案对应 heap_5（见第 7 节）。

## 6. malloc 底层白话 + free 后内存去哪了

**这是什么**：glibc 的 malloc = **空闲链表管理员 + 两种进货渠道**。白话：它手里有一本"哪些块空着"的账（空闲链表，块头藏着大小/状态元数据），要货时从账上切一块给你；不够了再向上游（内核）进货。

- **进货渠道一：brk**——把堆顶指针上移（撕一小段），小块分配（glibc 默认阈值约 128KB 以下【可调】）从这出；
- **进货渠道二：mmap**——大块单独向内核映射一段，用完 munmap 直接整块归还；
- **free 的真相**：多数时候只是把块**插回空闲链表**（相邻空块顺手合并），内存还"挂"在你进程名下——堆顶下面压着活块时，brk 的堆顶根本没法下移。

**free 后为什么不还给 OS**：类比退房——你退的只是"这一间"（标成空房），整层楼还没退（堆顶不动），前台的账本上它确实空着、钥匙也能再发给下一位住客（下次 malloc 复用），但**房产证上的面积（进程 RSS）没变**。只有 mmap 的大块和恰好堆顶的空块才真还。

**这段代码要做什么**：连着 malloc 三块、free 中间一块、再要一小块——亲眼看到"块挨块、free 只记账、新块复用旧坑"。

```c
#include <stdio.h>
#include <stdlib.h>

int main(void)
{
    char *a = malloc(100);            /* 连着要三块堆内存 */
    char *b = malloc(100);
    char *c = malloc(100);
    printf("a=%p b=%p c=%p\n", (void*)a, (void*)b, (void*)c);
    /* 打印可发现：相邻块地址只差 112 字节左右——
       100 是你要的，多出的十几字节是"块头"（大小/状态元数据） */

    free(b);                          /* 中间块归还空闲链表：账本上记"空"，
                                         但 RSS 不变——它还挂在进程名下 */
    char *d = malloc(80);             /* 分配器先查账：80 装得进 b 的空位，
                                         d 多半就复用 b 那块 */
    printf("d=%p（多半 == b）\n", (void*)d);
    free(a); free(c); free(d);
    return 0;
}
```

易踩坑：相邻 malloc 之间那段空隙就是块头——**越界多写一个字节都可能踩碎它**，空闲链表从此带毒（FAQ Q5 说的"炸点漂移"就是这块元数据遭了殃）。

**API 三问**：malloc 是否阻塞？否（缺货要么向内核进货要么返回 NULL，不会睡等）。时间单位？无。适用上下文？线程安全（glibc 内部有锁），**中断/信号处理函数里禁用**。mmap/brk：不阻塞，失败返回 MAP_FAILED/(-1)，进程上下文调用。

## 7. 对照 FreeRTOS：heap_1~5 与 Linux 伙伴系统

**这是什么**：同一道题（怎么管空闲内存）在两个世界的答案。思想相通（空闲块记账、相邻合并、复用），复杂度不同（Linux 还要管多核、按需调页、NUMA）。

| 方案 | 一句话机制 | 适用场景 |
|------|-----------|---------|
| heap_1 | 只分不收（vPortFree 是空壳） | 对象建完永不动——最简单最安全 |
| heap_2 | 收盘子但不拼桌（释放，但**不合并**相邻空闲块） | 分配/释放大小固定的场景 |
| heap_3 | 外包给标准库 malloc/free（重定向） | 线程安全由编译器库兜底 |
| heap_4 | 收盘子还拼桌（释放 + **相邻空闲块合并**，首次适应） | **默认推荐**：动态建删对象 |
| heap_5 | heap_4 + **多段不连续内存池** | RAM 分裂两块（如外挂 SRAM）的芯片 |

（食堂类比的完整展开与水位监控见 [05-内存管理与中断处理](../../../08-FreeRTOS/笔记/05-内存管理与中断处理.md)。）

**API 三问（pvPortMalloc）**：是否阻塞？否（失败返回 NULL，绝不睡等）。时间单位？无。适用上下文？任务级（ISR 里禁用）；配套 vPortFree 同规。工程纪律：能 xTaskCreateStatic/静态建队列就别动态——heap 留给不得不动态的场景，动态了就盯水位（xPortGetMinimumEverFreeHeapSize）。

**Linux 这边的两大件**：
- **伙伴系统（buddy system）**：管大块物理页——按 2 的幂（4K/8K/…/4M）分裂分配，释放时找"大小相同、地址相邻的兄弟"合并（≈heap_4 合并思想的规整数学版）；
- **slab 分配器**：管高频小块——给 task_struct、inode 这类常用对象**预制模具**（对象池），用完洗净复用（≈嵌入式静态内存池的思想）。

对应关系一句话：**heap_1~5 是"伙食团"水平，伙伴系统 + slab 是"中央厨房"水平**——分层（先伙伴后 slab 再 malloc）是它复杂度的主要来源。

## 8. 内存泄漏 / 越界：两个世界的表现差异

**这是什么**：同一类 bug，有无 MMU 决定症状轻重。有墙的世界伤自己，没墙的世界伤全家。

| 事故 | Linux（有 MMU，有墙） | FreeRTOS/MCU（无 MMU，无墙） |
|------|----------------------|------------------------------|
| 内存泄漏 | 只涨自己进程的 RSS，进程一死 OS 全收；valgrind/ASan 可查 | xPortGetFreeHeapSize 持续下降，最终分配失败；只能靠水位监控与代码自律 |
| 越界写 | 多半踩**自己进程**的堆元数据/邻变量（延迟爆炸难查）；撞到未映射区 → 段错误当场暴露 | 直接踩**别的任务栈/内核数据**——可能 hard fault，也可能**静默改坏**（更阴险） |
| 波及范围 | 一个进程 | 全系统（所有任务共处一室） |

嵌入式对应：MCU 上"明明数组只越界一个字节，别的任务却莫名数据错乱"就是无墙世界的典型症状——查这类问题优先怀疑越界，而不是玄学。

MCU 侧排查工具箱：栈溢出看 uxTaskGetStackHighWaterMark（每任务历史最小余量）+ 开 configCHECK_FOR_STACK_OVERFLOW 钩子；堆看 xPortGetMinimumEverFreeHeapSize（历史最低水位，判断"曾经多危险"）；MPU 可当"简易围栏"用——给任务栈区设权限、把任务栈隔开，是无 MMU 世界的最后防线（细节见 08-FreeRTOS 05 篇栈溢出章）。

## 章节小结

- 链接视角 = 图纸（相对布局），运行视角 = 入住（映射进虚拟空间）；裸机无虚拟层，两者几乎合一
- 虚拟内存 = 翻译官幻觉：隔离、重定位、超额分配；Cortex-M 无 MMU 只有 MPU
- 页 = 4KB 格子；地址拆 VPN+偏移，查页表得 PFN；TLB 是翻译小抄；缺页 = 去磁盘搬页 + 重执行指令
- 手算翻译：0x00401234 → VPN 0x00401 + 偏移 0x234 → 拼 PFN 得物理地址（偏移原样搬运）
- 首次适应快、最佳产细碎、最坏保大块；分页固有内部碎片
- malloc = 空闲链表 + brk/mmap 两渠道；free 多数只记账不还 OS（堆顶不动就退不了楼）
- heap_1 只分不收 / heap_2 不合并 / heap_3 外包 / heap_4 合并 / heap_5 多池；Linux = 伙伴系统 + slab
- 越界与泄漏：有 MMU 伤自己、无 MMU 伤全家——MCU 的"灵异数据错乱"优先查越界

## 常见问题 FAQ

**Q1：物理内存 8GB，怎么装得下进程们各 4GB 的"幻觉"？**
A：幻觉不用真兑现——按需映射（缺页才搬）、swap 把冷页挪磁盘、只读段（如 libc 的代码）多进程共享同一份物理页。

**Q2：MCU 有虚拟内存吗？**
A：Cortex-M 没有（只有 MPU 做权限围栏），FreeRTOS 全员共处物理内存；Cortex-A 有 MMU，跑 Linux 才有页表/缺页/swap 这一整套。

**Q3：free 之后立刻再用这块内存，为什么常常"没事"？**
A：块还在空闲链表里、数据多半没被覆盖，但这是未定义行为——一旦链表元数据被复用改写，炸点随机漂移。纪律：free 后立即置 NULL。

**Q4：为什么栈上的内存自动回收，堆上的要手动 free？**
A：栈的生存期跟着函数走（编译器在进出函数时挪栈指针，规律明确）；堆的生存期由程序逻辑决定，编译器猜不出你什么时候不用——只能交给你。

**Q5：越界写一个字节，真有那么严重吗？**
A：有。那一个字节可能正好是 malloc 块头的元数据——空闲链表从此带毒，之后任意一次 malloc/free 都可能炸，而且炸点与案发现场相距十万八千里。
