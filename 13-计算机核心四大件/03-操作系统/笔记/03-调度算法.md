# 03 · 调度算法

> 定位：OS 的"排班学"。学完本篇再回看 FreeRTOS 的优先级抢占，你会发现它只是众多算法里的一种工程取舍。

**先说人话**：本篇讲**调度器**——一堆任务抢一个 CPU 时，决定"下一个谁上场、上场多久"的裁判规则。为什么嵌入式工程师需要它：你在 FreeRTOS 里给任务定优先级的那一刻，就是在手工执行调度策略；采样任务莫名饿死、按键响应偶发卡顿，病根往往都藏在调度知识里。

## 1. 调度器与三大指标

**这是什么**：调度器 = **CPU 坐席分配员**——车厢就几个座（CPU 核），站台上全是等着上车的任务（就绪队列），谁先上、坐多久，全由它裁决。

三大指标白话（想象去银行办业务）：
- **周转时间**：从取号到办完离开的总时长 = 完成时刻 − 到达时刻——"整体快不快"；
- **响应时间**：取号后**第一次**被叫号等了多久——"上手快不快"（交互与实时系统的命根）；
- **吞吐量**：一天总共办完多少单——"产能高不高"（批处理系统的命根）。

没有全优的算法：追求吞吐（大锅炖）与追求响应（小锅快炒）天生打架，选型就是取舍。

讲算法前先把任务的三种状态分清（调度器只对"就绪"说话）：

```
      调度器挑中             等的事件到了
就绪 ○○○○○ ────────→ 运行 ────────────→ 阻塞（等IO/信号量/延时）
  ↑                   │ 时间片用完/被抢占
  └───────────────────┘ （回到就绪队尾排队）
```

- **运行**：正占着 CPU；**就绪**：随时能跑、只差一个 CPU（排队中）；**阻塞**：在等事件（IO、信号量、延时），把 CPU 给它也没法跑；
- 调度器**只在就绪队列里挑人**——阻塞的任务不参与排队，事件到了才回队列；
- 嵌入式对应：FreeRTOS 的 Running/Ready/Blocked 三态与此一一对应（Suspended 是额外的"手动停职"态）。

**调度器什么时候出场**（三个时机，各系统通用）：
- 当前任务**时间片用完**（同优先级轮转的切换点）；
- **更高优先级任务就绪**（抢占切换点）；
- 当前任务**阻塞或主动让出**（如 vTaskDelay、等信号量、yield）。
前两个是"被动下课"，第三个是"主动交班"——后面每种算法的差异，本质上只是"按什么规则从就绪队列挑下一个"。

## 2. FCFS：排队买票

**这是什么**：先来先服务（First Come First Served）——谁先到谁先办，办完才轮下一个。类比：老式售票窗口，一条长队排到底。

- 优点：绝对公平、实现最简单、无人挨饿；
- 致命伤：**护航效应（convoy effect）**——队头一个 8 小时的大作业，能让后面 10 个 1 分钟的小作业全体陪跑。类比：前面大爷在柜台数三万枚硬币，全队干瞪眼。

**护航效应数字算例**：P1 在 t=0 到达、要跑 60ms；P2、P3 各只要 3ms，分别在 t=1、t=2 到达：

```
甘特图: |        P1（60ms）       | P2 | P3 |
时间:   0                        60   63   66
周转:   P1=60, P2=62, P3=64 → 平均 = 62ms
```

P2/P3 明明 3ms 就能办完，却硬陪跑 60ms。换成**抢占式**短作业优先（谁剩余时间短谁上）：P1 跑 1ms 就被 P2 抢、P2 完被 P3 抢，P1 最后收尾——平均周转掉到约 24.7ms。注意细节：**非抢占的** SJF 在这里救不了场（t=0 时只有 P1 一个选择）——FCFS 的死穴在于平均指标被长作业绑架，破局要么靠抢占、要么靠时间片。

## 3. SJF：短作业优先（含算例）

**这是什么**：Shortest Job First——谁办得快谁先办。它是**平均周转时间理论最优**的算法（直觉：把短的排前面，后面每个人等的时间都变短）。

算例：三个作业同时到达（t=0），CPU 需求 A=8ms、B=4ms、C=2ms。先看 FCFS，再看 SJF。

FCFS（按到达序 A→B→C）：
```
甘特图: |    A    |   B   |  C  |
时间:   0         8      12     14
周转:   A=8, B=12, C=14 → 平均 = 34/3 ≈ 11.3ms
```

SJF（按长度序 C→B→A）：
```
甘特图: |  C  |   B   |      A      |
时间:   0    2       6            14
周转:   C=2, B=6, A=14 → 平均 = 22/3 ≈ 7.3ms
```

同样的活，平均周转直降约 35%——这就是"短优先"的威力。

代价也明摆着：① 作业长度要**未卜先知**（实际只能拿历史时长预测）；② **长作业饥饿**——短的源源不断，长的永远排不上号。

## 4. RR：时间片轮转（q=2ms 手推甘特图）

**这是什么**：Round Robin——每人只跑一个**时间片 q**（固定额度），到点强制交班换下一个人。类比：KTV 切歌——铃响就换麦，谁也别想霸着话筒，队里没人干等。

算例：P1/P2/P3 同时到达 t=0，CPU 需求分别 5/3/4ms，q=2ms；就绪队列按到达序排队，跑不完的回到队尾。

逐轮推演（手推一遍才算真会）：
- 第 1 轮：P1 跑 2ms（剩 3）→ P2 跑 2ms（剩 1）→ P3 跑 2ms（剩 2）
- 第 2 轮：P1 跑 2ms（剩 1）→ P2 跑 1ms 清零（t=9 完成）→ P3 跑 2ms 清零（t=11 完成）
- 第 3 轮：P1 跑 1ms 清零（t=12 完成）

```
甘特图: | P1 | P2 | P3 | P1 | P2 | P3 | P1 |
时间:   0    2    4    6    8    9   11    12
周转:   P1=12, P2=9, P3=11 → 平均 = 32/3 ≈ 10.7ms
响应:   三者首跑都发生在 0~4ms 内——响应性远好于 FCFS
```

q 的两难：
- q 太大 → 退化成 FCFS（护航效应回归）；
- q 太小 → 切换开销占比飙升（单次切换是微秒级，q 也设微秒级就全在交班、没在干活）；
- 经验法则：q 远大于单次切换耗时（让切换开销占比 < 1%）。

**RR 与 SJF 怎么选**：RR 用平均周转换响应——大家首跑都早，但每个作业都因此慢了点；SJF 平均周转最好，但响应差、还会饿死长作业。分时/交互系统（含 Linux 桌面）走 RR 一系，批处理走 SJF 一系，实时系统（嵌入式主战场）则转向"优先级 + 截止期"那一套（第 6 节）。

## 5. 优先级调度：好用但有"饿死"暗病

**这是什么**：给每个任务定级别，级别高者先跑。嵌入式最常用（FreeRTOS 就是它最纯粹的一版），但有个恶疾——**饥饿（starvation）**：高优先级任务源源不断，低优先级永远摸不到 CPU。

解法 = **老化（aging）**：等得越久，优先级越往上抬。类比：排队的怒气值会积累——怒气攒够，经理主动请你插队。这一招同时保住两件事："要紧事先办"和"小事最终也能办"。

**老化算例**：规则设"每干等 10ms，优先级 +1"。任务 P 初始优先级 1、总抢不过源源不断的高优先级流量：干等 30ms 升到 4，干等 50ms 升到 6——迟早高过普通新任务，总能轮上；轮上跑完后老化值清零，系统回归"要紧事先办"。Windows 内核调度与多级反馈队列都内置了这一思路。注意：**FreeRTOS 没有自动老化**——低优先级任务饿死要自己防（见实操任务第 2、3 项）。

## 6. 实时调度：RMS 与 EDF

**这是什么**：实时系统的考核标准不是"平均多快"，而是"**交卷别迟到**"——每个周期任务带两个参数：执行时长 C（要做多久）和周期 T（多久来一次活）。两大经典算法：

### RMS：速率单调（静态优先级）

- 规则一句话：**周期越短，优先级越高，且运行期间不变**——采样 10ms 的任务天然比上报 1s 的金贵；
- **可调度性判据**（充分条件）：n 个周期任务的总利用率 U = Σ(Ci/Ti) ≤ n(2^(1/n) − 1)。
  代入：n=2 → 0.828；n=3 → 0.780；n→∞ → ln2 ≈ 0.693。

**算例**：三任务 T1(C=1, T=4)、T2(C=1, T=5)、T3(C=2, T=10)：
U = 1/4 + 1/5 + 2/10 = 0.25 + 0.20 + 0.20 = **0.65 < 0.780** → RMS 保证可调度。
反例：若算出 U = 0.90 > 0.780 → 判据**无法保证**（注意：只是"证明不了"，不是"必死"——实际仍可能可行，但要靠逐周期仿真验证）。

**优先级怎么指派 + 时间线快看一眼**：周期 4 < 5 < 10 → 定 T1 > T2 > T3（指派完永不改）：

```
甘特图: | T1 | T2 |  T3  | T1 | T2 | 空闲 | T1 | 空闲 |
时间:   0    1    2      4    5    6     8    9    10
```

逐段核对：T1 在 0/4/8 释放、截止 4/8/12，都最先跑（周期最短永远先占）；T2 两单（截止 5/10）准点；T3 首单 2ms 在 2~4 跑完（截止 10，富余 6ms）——**零迟到**，这就是判据 0.65 < 0.780 的画面兑现。顺带看"空闲"段：U=0.65 意味着约 35% 的 CPU 本来就该闲着，实时系统"有闲"不是坏事，是余量。

### EDF：最早截止期优先（动态优先级）

- 规则一句话：**谁的截止时间先到谁先跑**，优先级随时间动态重排；
- 优势：单处理器上利用率上界 **100%**——上面 U=0.9 的任务集，EDF 理论可调度；
- 代价：动态排序开销更大，系统过载时哪些任务崩不可预测。

**EDF 代入算例**：接上面 U=0.9 的反例——T1(C=1, T=2)、T2(C=2, T=5)：U = 1/2 + 2/5 = **0.90 > 0.828**（RMS 判据不保证），但 **0.90 < 1.0** → EDF 理论可调度——两个判据之间的差，就是 EDF 的价值。动态重排看一瞬：t=4ms 时 T1 的下个截止在 6ms，而 T2 若还压着一件截止 5ms 的活——**T2 立刻插队**，哪怕 T1 周期更短、"级别"更高；这一瞬在 RMS 里永远不会发生。优先级是"活的"，就是 EDF 与 RMS 的本质区别。

嵌入式对应：FreeRTOS 的固定优先级抢占就是 RMS 思想的工程简化版——按周期/重要性手工定级、运行期不变，把理论判据换成了"开发者自律"。

## 7. 对照 FreeRTOS：抢占 + 同优先级轮转

**这是什么**：把前几节的理论钉到你天天用的 RTOS 上（上下文切换与 PendSV 细节见 [01-裸机到RTOS任务与调度](../../../08-FreeRTOS/笔记/01-裸机到RTOS任务与调度.md)）。

- **抢占式调度**：更高优先级任务一就绪（如 ISR 里释放信号量），立刻切换、不等时间片——这是"实时性"的来源；
- **同优先级时间片轮转**：只有**同级**任务才轮流上场，每过一个 tick 轮换一次（configUSE_TIME_SLICING 默认开启）；不同优先级之间永远"高先低后"，不轮转；
- **configTICK_RATE_HZ 与时间片长度的关系**：时间片长度 = 1 个 tick 周期 = 1/configTICK_RATE_HZ 秒。配 1000 → 1 tick = 1ms → 同级任务每 1ms 轮换一次。注意：时间片**不是独立可调参数**，改它等于改 tick 频率，而 tick 频率牵动所有 vTaskDelay/超时的精度——动之前想清楚连锁反应。

Linux 一句带过：桌面/服务器用 CFS 完全公平调度（按"谁欠的运行时间多"挑人跑），实时任务另有 FIFO/RR 策略——与 RTOS 是两个世界，混型系统里实时任务永远插队。

**一个具体场景串三个词**：configTICK_RATE_HZ = 1000（1 tick = 1ms）。t=0 起两个同优先级任务 A1/A2 在轮流跑（A1 跑满 1 tick，t=1 换 A2）；t=3ms 串口 ISR 里 xSemaphoreGiveFromISR 唤醒了高优先级任务 B → **不等 tick、立即抢占**（PendSV 完成切换），A2 才跑 2ms 就让位；B 拿完数据阻塞后，A1/A2 又从各自断点继续轮流。抢占（跨优先级）、轮转（同优先级）、tick（轮换刻度）三个词在这一段里各就各位。

**全算法速查表**（考前扫一眼这张就够）：

| 算法 | 一句话规则 | 强项 | 弱项 | 典型用户 |
|------|-----------|------|------|---------|
| FCFS | 先到先办 | 公平、简单 | 护航效应 | 早期批处理 |
| SJF | 短的先办 | 平均周转最优 | 要预知长度、饿死长作业 | 批处理 |
| RR | 切片轮转 | 响应快、无人干等 | 平均周转变差 | 分时/交互系统 |
| 优先级+aging | 级别高先跑、等久升级 | 兼顾要紧与不挨饿 | 要防优先级反转 | RTOS/Windows |
| RMS | 周期短→级别高（静态） | 可预测、可提前验证 | 利用率上界 < 100% | 实时 RTOS |
| EDF | 截止早→先跑（动态） | 利用率可到 100% | 动态开销、过载难预料 | 实时系统/某些内核 |

## 章节小结

- 三大指标：周转（整体快不快）、响应（上手快不快）、吞吐（产能高不高）——不可能同时全优
- 调度只在就绪队列里挑人：任务分运行/就绪/阻塞三态，阻塞者给 CPU 也没法跑
- FCFS 简单公平但有护航效应；SJF 平均周转最优，但要未卜先知、还会饿死长作业
- RR 用时间片强制交班：q 太大退化成 FCFS，太小切换开销淹没产能
- 饥饿的解法是老化（aging）：等得越久，优先级越高
- RMS：周期短→优先级高（静态），n=3 时利用率判据约 0.78；EDF：截止早→先跑（动态），上界 100%
- FreeRTOS：抢占 + 同优先级每 tick 轮转；时间片 = 1/configTICK_RATE_HZ 秒，非独立参数

## 常见问题 FAQ

**Q1：FreeRTOS 里不同优先级的任务会时间片轮转吗？**
A：不会。轮转只发生在**同级**任务之间；不同级永远高先低后，低优先级要等"所有高的都阻塞了"才有机会。

**Q2：想让时间片变成 5ms，怎么设？**
A：没有"时间片"独立配置项——把 configTICK_RATE_HZ 改成 200 即可，但所有 vTaskDelay/软件定时器的粒度同步变粗，三思。

**Q3：RMS 判据没过，系统一定会超截止期吗？**
A：不一定。判据是**充分条件**：过了必可调度；没过只代表"公式证明不了"，实际可能仍可行——需要逐周期仿真验证。

**Q4：SJF 明明最优，为什么实际没人直接用？**
A：作业长度未卜先知做不到。实践用它的变体：拿历史平均时长当预测值，例如多级反馈队列 MLFQ——新任务先当"短作业"优待，跑久了自动降级。

**Q5：实时系统为什么偏爱静态优先级（RMS 一系）？**
A：行为可预测、可提前验证。动态算法（EDF）平均性能更好，但过载时哪些任务会崩不可预测——对安全相关系统是硬伤。
