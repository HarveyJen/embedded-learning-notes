# 04 · 同步与互斥

> 定位：并发编程的地基。竞态、锁、信号量、条件变量、死锁——学完本篇，FreeRTOS 的 Mutex/Semaphore 和 Linux 的 pthread 工具箱就是一回事。

**先说人话**：本篇讲"多个执行流共用一份资源时怎么不出乱子"。**互斥**是"一次只许一个人用"（抢卫生间的门锁），**同步**是"按先后次序来"（先装货再拉货）。为什么嵌入式工程师需要它：你写过的每个环形缓冲、每个 xSemaphoreTake，都是在解决本篇的问题——搞懂原理，锁才不会用错。

## 1. 竞态条件：count++ 是怎么丢更新的

**这是什么**：**竞态条件（race condition）** = 结果取决于执行流交错顺序的错误。类比：两人同时往同一张银行卡各存 100 元，柜员 A 读余额、柜员 B 也读余额，各自加 100 写回——结果只存进去一笔。

**这段代码要做什么**：两个线程各对 count 自增 100 万次，期望 200 万，实际往往少于 200 万——先看代码，再逐行拆穿。

```c
#include <stdio.h>
#include <pthread.h>

#define LOOP 1000000
int count = 0;                        /* 共享变量：灾祸现场 */

void *adder(void *arg)
{
    for (int i = 0; i < LOOP; i++)
        count++;                      /* 看似一步，实为三步（见下） */
    return NULL;
}

int main(void)
{
    pthread_t t1, t2;
    pthread_create(&t1, NULL, adder, NULL);
    pthread_create(&t2, NULL, adder, NULL);
    pthread_join(t1, NULL);
    pthread_join(t2, NULL);
    printf("count=%d (期望 %d)\n", count, LOOP * 2);
    return 0;
}
```

`count++` 在 CPU 上是**三条指令**：① 从内存读 count 进寄存器 → ② 寄存器 +1 → ③ 写回内存。线程可能在任意两条指令之间被切走。丢失更新的交错过程：

```
时刻 | 线程A               | 线程B               | count
t1   | ①读 count(=5)→寄存器 |                     | 5
t2   |                     | ①读 count(=5)→寄存器 | 5   ← 都读到旧值！
t3   | ②+1 = 6             |                     | 5
t4   |                     | ②+1 = 6             | 5
t5   | ③写回 6             |                     | 6
t6   |                     | ③写回 6             | 6   ← 加了两次只多 1！
```

三要素齐了：**共享资源**（count）+ **并发访问**（两线程）+ **非原子操作**（三步被打断）。单核照样出事——切换就发生在指令之间。volatile 只保证"改动立即可见"，管不了"三步不被打断"（与 [09-预处理器与关键字专题](../../../01-C语言基础/笔记/09-预处理器与关键字专题.md) 的辨析闭环）。

## 2. 临界区：卫生间 + 门锁

**这是什么**：**临界区（critical section）** = 访问共享资源的那段"碰不得被打断"的代码。类比：卫生间是共享资源，**门锁**保证一次一人——进去反锁，出来开锁，门外的人排队等。

对锁的要求就四条：**互斥**（一次一人进）、**推进**（空着时必须能让等待者进）、**有限等待**（不能让人排到天荒地老）、**忙等要少**（等的人别空转烧 CPU，最好睡着）。下面三种工具都是这四条的工程实现。

## 3. 工具一：互斥锁 mutex

**这是什么**：最常用的门锁——**谁锁谁开**（所有权），锁着时别人来拿就睡。类比：卫生间门锁上写着"占用者姓名"，只配一把钥匙，钥匙在谁手里谁说了算。

```c
#include <stdio.h>
#include <pthread.h>

#define LOOP 1000000
int count = 0;
pthread_mutex_t lock = PTHREAD_MUTEX_INITIALIZER;  /* 静态初始化一把锁 */

void *adder(void *arg)
{
    for (int i = 0; i < LOOP; i++) {
        pthread_mutex_lock(&lock);    /* 进门前拿锁：拿不到就睡（不烧CPU） */
        count++;                      /* 临界区：越短越好 */
        pthread_mutex_unlock(&lock);  /* 出门开锁 */
    }
    return NULL;
}
```

- 把第 1 节的 adder 换成这版，结果必定是 200 万——先跑无锁版再跑加锁版，体感差距；
- 临界区原则：**只装碰共享数据的几行**，printf、长循环都挪出去（持锁时间越短，排队越短）；
- 忘了 unlock、或持锁时 return，后面所有人排死——这就是"占着卫生间睡觉"。

**API 三问（pthread_mutex_lock）**：是否阻塞？是（锁被占就睡，直到被唤醒；pthread_mutex_trylock 是非阻塞版，抢不到立即返回失败）。时间单位？无（永久等；限时版 pthread_mutex_timedwait 用 timespec 绝对时间【其基准时钟随实现而定，用时查 man 页】）。适用上下文？线程内（信号处理函数里禁用）。

## 4. 工具二：信号量 semaphore（计数 / 二值）

**这是什么**：**信号量（semaphore）** = 一个计数器 + 等待队列。P 操作（sem_wait）计数减 1、减到 0 再来就睡；V 操作（sem_post）计数加 1、并叫醒一个睡着的人。类比：**停车场入口的剩余车位牌**——计数信号量是"N 个车位"（一次放 N 个车进），二值信号量就是"0/1 个车位"（单格，等效门锁但**不记车主**）。

两种用途分清：
- **计数信号量**：管理"N 份同类资源"（缓冲区空位数、连接池名额）；
- **二值信号量**：0/1 开关，常用于**事件通知**（"事情发生了，起来干活"），不强调所有权。

**API 三问**：sem_wait 是否阻塞？是（计数为 0 时睡）。时间单位？无（限时版 sem_timedwait 用 timespec）。适用上下文？线程间；sem_init 第二参 pshared 传非 0 且信号量放共享内存时可用于进程间。

## 5. 经典实战：生产者消费者（完整代码）

**这是什么**：并发模型的第一课——生产者往缓冲区放货，消费者取货，两边速度不一、还要互不踩脚。类比：**后厨出菜口**——厨师（生产者）往窗口放菜，服务员（消费者）端走；窗口满了厨师等，空了服务员等。

**这段代码要做什么**：用"空位信号量 + 满位信号量 + 互斥锁"三件套实现多生产多消费，逐行注释了每个信号量的职责。

```c
#include <stdio.h>
#include <pthread.h>
#include <semaphore.h>

#define N 5                        /* 缓冲区容量 */

int buf[N];                        /* 环形缓冲区 */
int in = 0, out = 0;               /* 写指针 / 读指针 */

sem_t empty;                       /* 空位数：初始 N（还能放几个） */
sem_t full;                        /* 满位数：初始 0（已放几个） */
pthread_mutex_t lock = PTHREAD_MUTEX_INITIALIZER;

void *producer(void *arg)
{
    for (int i = 1; i <= 10; i++) {
        sem_wait(&empty);          /* P(空位)：没空位就睡，等消费者腾 */
        pthread_mutex_lock(&lock); /* 锁缓冲区（多个生产者也要排队） */
        buf[in] = i;               /* 放货 */
        printf("put %d\n", i);
        in = (in + 1) % N;         /* 写指针环形前移 */
        pthread_mutex_unlock(&lock);
        sem_post(&full);           /* V(满位)：通知"有货了" */
    }
    return NULL;
}

void *consumer(void *arg)
{
    for (int i = 0; i < 10; i++) {
        sem_wait(&full);           /* P(满位)：没货就睡 */
        pthread_mutex_lock(&lock);
        printf("got %d\n", buf[out]);  /* 取货 */
        out = (out + 1) % N;
        pthread_mutex_unlock(&lock);
        sem_post(&empty);          /* V(空位)：通知"腾出位置了" */
    }
    return NULL;
}

int main(void)
{
    pthread_t tp, tc;
    sem_init(&empty, 0, N);        /* 初始 5 个空位 */
    sem_init(&full, 0, 0);         /* 初始 0 个满位 */
    pthread_create(&tp, NULL, producer, NULL);
    pthread_create(&tc, NULL, consumer, NULL);
    pthread_join(tp, NULL);
    pthread_join(tc, NULL);
    sem_destroy(&empty);
    sem_destroy(&full);
    return 0;
}
```

两个要害：
- **顺序铁律：先 sem_wait 后 mutex_lock**（先占坑、再锁门）。反过来的话，线程可能**持着锁去等信号量**——睡着都不撒手，全场死等；
- 单生产单消费时 in/out 各归一人用，mutex 可省；多生产或多消费必须加。

嵌入式对应：FreeRTOS 队列天生就是"带阻塞的环形缓冲"，一个 xQueueSend/xQueueReceive 抵上面三件套（对照见 01 篇总表）。

## 6. 工具三：条件变量（为什么要用 while 不用 if）

**这是什么**：**条件变量（condition variable）** = 配合互斥锁的"叫号器"——线程在"条件不满足"时**撒着锁睡着**，条件满足时被叫醒。类比：取号机——你先把柜台资源让出来（解锁），坐着等叫号（睡），叫到号再回柜台（重新拿锁）。

```c
/* 标准姿势：wait 必须持锁调用，醒来时锁也重新在手上 */
pthread_mutex_lock(&m);
while (条件不成立)                 /* 注意：必须 while，不能 if！ */
    pthread_cond_wait(&cond, &m); /* 三合一：解锁+睡觉；醒来前重新拿锁 */
/* 走到这：条件成立且持有锁，安全干活 */
pthread_mutex_unlock(&m);

/* 唤醒方（改完条件后） */
pthread_mutex_lock(&m);
条件 = 成立;
pthread_cond_signal(&cond);        /* 叫醒一个；broadcast 叫醒全部 */
pthread_mutex_unlock(&m);
```

**为什么必须用 while 不用 if**：
1. **假唤醒（spurious wakeup）**：POSIX 明确允许 cond_wait 在没人 signal 时莫名醒来——if 只查一次就往下走，假唤醒直接穿透；
2. **条件被抢**：signal 唤醒你到 wait 返回之间，别的线程可能抢先拿锁把条件又改坏了——醒来必须**重新检查**；
while 把"睡醒 → 复查"变成循环，两条坑全堵死。

**API 三问（pthread_cond_wait）**：是否阻塞？是（直到 signal/broadcast）。时间单位？无（限时版 pthread_cond_timedwait 用 timespec 绝对时间）。适用上下文？线程内，且**必须已持有配套 mutex**。

## 7. 死锁四条件与"两根筷子"

**这是什么**：**死锁（deadlock）** = 一群人互相等对方手里的资源，谁都动不了。类比：餐叙桌上两人各抓了**一根筷子**，都在等对方撒手——谁也吃不上饭。

死锁**四条件**（全中才死锁，破一条就活）：
1. **互斥**：资源一次一人用（筷子一人一根）；
2. **持有并等待**：抓着手里的，还想拿别人的；
3. **不可剥夺**：不能从别人手里硬抢；
4. **循环等待**：A 等 B、B 等 A，转圈。

**破坏法与工程预防**：
- 破"持有并等待"：一次性申请全部资源，拿不齐就先放掉手里的；
- 破"不可剥夺"：用 trylock 抢，抢不到就退回重来（适合能回滚的场景）；
- 破"循环等待"（**工程最常用**）：**锁序一致**——全局规定"先锁 m1 后锁 m2"，谁也不许反序：

```c
/* 危险：线程A 锁 m1→m2，线程B 锁 m2→m1 —— 交错时就互相卡死 */
/* 修复：全员统一"先 m1 后 m2"，循环等待永远组不成 */
pthread_mutex_lock(&m1);
pthread_mutex_lock(&m2);
/* ... */
pthread_mutex_unlock(&m2);
pthread_mutex_unlock(&m1);
```

FreeRTOS 对照：两把互斥量交叉持有照样死锁，06 篇的"分级加锁"就是锁序一致的 RTOS 版（见 [03-信号量与互斥量](../../../08-FreeRTOS/笔记/03-信号量与互斥量.md)）。

## 8. 对照 FreeRTOS：mutex/semaphore 与两种临界区

**这是什么**：把本篇工具钉到 RTOS 上——名字相同，语义有别。

| 对比项 | FreeRTOS 互斥量 Mutex | FreeRTOS 二值信号量 |
|--------|----------------------|---------------------|
| 所有权 | 有（谁拿谁还，别人还不了） | 无（谁都能 Give，当"事件铃铛"用） |
| 优先级继承 | **有**（持锁的低优先级任务临时升到等锁者的级别，防优先级反转） | 无 |
| 正确用法 | 保护共享资源 | ISR→任务的事件通知/同步 |

一句话铁律：**互斥用 Mutex，同步用 Semaphore**——拿二值信号量当锁用，就丢了优先级继承，白送一个优先级反转。

**临界区的两种手段**（库内既有表述，务必分清）：
- `taskENTER_CRITICAL()/exit()`：**屏蔽中断**到内核管理线（configMAX_SYSCALL_INTERRUPT_PRIORITY）——比这条线更急的中断照样能打断，但调度相关中断被挡住，期间不会发生任务切换，代码等效原子。**不挂起调度器**，靠"关中断"保护；
- `vTaskSuspendAll()/xTaskResumeAll()`：**挂起调度器**——只拦任务切换、**不关任何中断**，中断照常响应，ISR 请求的切换攒到恢复调度时再执行。

选择标准就一句：**要不要连中断一起挡**——几行寄存器级操作用临界区；纯任务间长一点的保护可挂起调度器；能轻则轻（优先级：互斥量 > 临界区 > 关全局中断）。

## 章节小结

- 竞态三要素：共享资源 + 并发访问 + 非原子操作；count++ 三步被打断就会丢更新，单核也逃不掉
- 临界区 = 碰共享资源的代码段；对锁的四要求：互斥、推进、有限等待、少忙等
- 三工具分工：mutex 锁数据（有所有权）、semaphore 管资源数/发事件、条件变量"撒锁等待+复查"
- cond_wait 必须配 while：防假唤醒 + 防条件被抢
- 生产者消费者 = empty/full 信号量 + mutex；顺序铁律：先 sem_wait 后 mutex
- 死锁四条件：互斥、持有等待、不可剥夺、循环等待；工程解法 = 锁序一致
- FreeRTOS：Mutex 有优先级继承、Semaphore 无；临界区（关中断到 configMAX_SYSCALL）与挂起调度器（不关中断）是两种保护手段

## 常见问题 FAQ

**Q1：volatile 能替代锁吗？**
A：不能。volatile 只保证可见性（改动立即被别人看见），不保证原子性——count++ 的读改写三步照样能被切走，详见 01-C 09 篇辨析。

**Q2：二值信号量和互斥锁长得一样，能互换吗？**
A：Linux 的二值语义上勉强可当锁，但 FreeRTOS 明确不行：信号量无所有权、无优先级继承，当锁用会白送优先级反转。记住铁律"互斥用 Mutex，同步用 Semaphore"。

**Q3：单核 CPU 也有竞态吗？**
A：有。线程切换发生在任意两条指令之间，单核照样"读到旧值再写回"。核数只影响概率，不改变本质。

**Q4：临界区越大越安全吗？**
A：错误性安全、性能性遭殃——持锁时间越长，排队越久、死锁窗口越大。原则是临界区只包住碰共享数据的几行。

**Q5：pthread_cond_signal 在持锁时发还是解锁后发？**
A：两者都正确，区别是调度时机（持锁发可能让被唤醒者立刻又阻塞在拿锁上）。新手先统一"改完条件、解锁后 signal"，不容易踩坑。
