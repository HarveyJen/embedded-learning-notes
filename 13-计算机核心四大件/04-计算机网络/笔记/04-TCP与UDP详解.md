# 04 · TCP 与 UDP 详解

> 定位：传输层的两大主力——TCP 负责可靠连接，UDP 负责快速直发。嵌入式对应物：MQTT 跑在 TCP 上、设备发现/遥测用 UDP、lwIP 的 socket API 与本篇一一对应。

**先说人话**：本篇讲传输层：应用写的每句话，要么走 TCP（像打电话——先拨通、确认彼此听得到、聊完说挂；可靠但费事），要么走 UDP（像寄明信片——写完地址直接扔邮筒；快但不保证送到）。为什么嵌入式工程师需要它？MQTT/HTTP/Modbus-TCP 全建在 TCP 上，设备发现、NTP 对时、实时遥测走 UDP，"连上了但发不出数据"这类经典故障更要靠本篇的状态机+抓包思路来破案。

## 1. TCP vs UDP：打电话 vs 寄明信片

**这是什么**：传输层决定"要不要先建立可靠通道"。TCP（传输控制协议）面向**连接**、可靠、有序、字节流；UDP（用户数据报协议）无连接、不可靠、快而简单。类比：TCP 是打电话（接通了才说话，听不清会要求"再说一遍"），UDP 是寄明信片（写完就寄，丢了你也不知道）。

| 对比项 | TCP | UDP |
|--------|-----|-----|
| 连接 | 需先握手建立 | 直接发 |
| 可靠性 | 确认+重传，不丢不乱 | 尽力而为，丢了就丢了 |
| 速度/开销 | 慢、头 20 字节起 | 快、头仅 8 字节 |
| 传输形态 | 字节流（无消息边界） | 独立数据报（一份一份） |
| 典型应用 | HTTP/MQTT/Modbus-TCP | DNS/DHCP/NTP/设备广播发现/实时流 |

选型口诀：**要"一个字都不能错"用 TCP；要"快和简单"、上层能容忍偶尔丢包用 UDP**。嵌入式对应物：MQTT 选 TCP 把可靠性下沉给协议栈，自己专注发布订阅语义；局域网设备发现常用 UDP 广播（一喊全楼听见，TCP 做不了广播）。

## 2. TCP 报文头关键字段（握手要用到）

**这是什么**：TCP 头（20 字节起）是"电话通话协议"的字段表。先认识关键字段，后面时间线才看得懂：

| 字段 | 长度 | 作用（白话） |
|------|------|--------------|
| 源端口 / 目的端口 | 16+16 位 | "哪栋楼的哪个房间"——IP 找到主机（03 篇），端口找到进程 |
| 序号 seq | 32 位 | 本报文携带数据的第几号字节（每个字节都有编号） |
| 确认号 ack | 32 位 | "到你第 N 号字节我都收齐了，下次从 N+1 发"（累积确认） |
| 标志位 | 6 位 | SYN（请求连线）、ACK（确认字段有效）、FIN（我说完了）、RST（立即掐断）、PSH/URG【用途见教材】 |
| 窗口大小 | 16 位 | "我还能再收多少"——接收方的缓冲余量，流量控制的依据 |
| 校验和 | 16 位 | 头+数据一起校验，TCP 不接受"内容损坏" |

注意：端口号是"同一台机器上进程的门牌"，0~1023 多为知名端口（80=HTTP、1883=MQTT），一连接由四元组（源IP:端口 + 目的IP:端口）唯一标识。

## 3. 三次握手：把电话接通

**这是什么**：TCP 建连仪式，客户端和服务端各确认一次"我能发你能收"。类比打电话："听得到吗？"→"听得到，你呢？"→"我也听得到"——双方都确认双向通路完好才开聊。

时间线（x、y 为各自随机选的初始序号 ISN，作用之一是避免上一条连接的旧包串门）：

```
客户端                                    服务端
   |  ① SYN=1, seq=x                        |
   | -------------------------------------> |   "我想连线，我的字节从 x 开始数"
   |                                        |   服务端：进入 SYN_RCVD，开半连接等回执
   |  ② SYN=1, ACK=1, seq=y, ack=x+1        |
   | <------------------------------------- |   "收到！我从 y 开始数，你下个字节该是 x+1"
   |  ③ ACK=1, seq=x+1, ack=y+1             |
   | -------------------------------------> |   "好，你的 y 我也收到了"
   |=== 双方进入 ESTABLISHED，开始传数据 ====|
```

**为什么是三次，两次不行吗**（面试必考）：
- 两次无法让**服务端**确认"我发的 SYN+ACK 客户端收到了"——服务端从此蒙眼发数据；
- 更实际的坑：一个在网络里迷路很久的**旧 SYN** 迟到抵达，两次握手会让服务端傻乎乎开一条没人说话的连接，白白占着资源等——三次给了客户端"验货"机会（不认识的旧连接用 RST 拒掉）；
- 为什么不是四次：②里的 SYN 和 ACK 可以合并成一包，天然四次被压缩成三次。

## 4. 四次挥手与 TIME_WAIT：挂电话的礼貌流程

**这是什么**：断连仪式。之所以四次不能合并，是因为**收到 FIN 的一方可能还有话没说完**（"你说完了我还剩半段数据要发"）。类比：一个人说"我挂了"，另一个人还得把最后半句话说完，再说"我也说完了，挂了"，前者再回一句"好"。

```
主动方（先关的）                            被动方
   |  ① FIN=1, seq=u                        |
   | -------------------------------------> |   "我说完了"
   |  ② ACK=1, ack=u+1                      |
   | <------------------------------------- |   "知道（我还没说完，稍等）"  → 被动方继续发剩余数据
   |  ③ FIN=1, ACK=1, seq=w, ack=u+1        |
   | <------------------------------------- |   "我也说完了"
   |  ④ ACK=1, ack=w+1                      |
   | -------------------------------------> |   "好"
   |  进入 TIME_WAIT，等 2MSL 后才真正关闭     |   收到 ACK 即关闭
```

**TIME_WAIT 为什么要等 2MSL**（MSL = 报文在网络里的最大存活时间）：
1. 兜底重发：最后的 ACK 若在途中丢失，被动方会超时重发 FIN——只有主动方还停在 TIME_WAIT，才能再补一次 ACK；
2. 清场：等满 2MSL，本连接的所有旧报文保证已在网络中死光，不会串进"复用了同样端口的新连接"。

工程对应：服务器上 `netstat` 看到大量 TIME_WAIT，通常是**高频短连接**（每连一次都留下一个等 2 分钟的坑）——解法是改长连接或端口复用，而不是硬关。

## 5. TCP 状态机速查（工程只记关键态）

**这是什么**：一条 TCP 连接从生到死经历的"状态"（netstat 里 State 那一列）。不用背全图，记住下面这张表就能排查 90% 的问题：

| 状态 | 出现在谁身上 | 白话 |
|------|--------------|------|
| LISTEN | 服务端 | "开店了，等客上门" |
| SYN_SENT / SYN_RCVD | 客户端 / 服务端 | 握手中（①发出 / ②收到待回执） |
| ESTABLISHED | 双方 | "通话中"，正常干活 |
| FIN_WAIT_1 / FIN_WAIT_2 | 主动关方 | "我说完了，等对方说" |
| CLOSE_WAIT | 被动关方 | "对方说完了，但我还没调 close"——**大量 CLOSE_WAIT = 你的代码忘了关连接** |
| LAST_ACK | 被动关方 | "我也说完了，等最后回执" |
| TIME_WAIT | 主动关方 | "礼节性等待 2MSL" |

## 6. 可靠传输三大件：确认重传、滑动窗口、拥塞控制

**这是什么**：网络会丢包、乱序、拥堵，TCP 靠三招把不可靠的网络洗成可靠字节流。类比一套可靠的挂号信系统：每封信念号（序号）、要回执（确认）、超时重寄（重传）、按回执速度控制寄信节奏（窗口）。

**第一件：确认与重传。** 接收方对每个收到的字节序号回执（累积确认："到 N 号都收齐了"）；发送方超时没等到回执就重发。升级版"快速重传"：后续每个包都会让接收方重复回执丢失处——发送方**连收 3 个重复 ACK** 就基本断定中间丢了，立刻重发，不必干等超时。

**第二件：滑动窗口（流量控制）。** 不是"发一封等一封"，而是**连发一批**——窗口大小 = 在途未确认数据的上限，由对方"我还能收多少"（接收窗口）决定。手推一遍（窗口 = 4 个报文）：

```
序号:    1  2  3  4  5  6  7  8  9
第1步:  [1  2  3  4]                ← 窗口内 1~4 全部发出（在途）
第2步:     [2  3  4  5]             ← 收到 ACK=2，窗口右滑 1 格，补发 5
第3步:        [3  4  5  6]          ← 收到 ACK=3，右滑，补发 6
     [ ]里的序号 = 还没被确认、允许在路上的包；ACK 每前进一步，窗口跟着滑一步
```

窗口也不是越大越好，上限由**带宽时延积（BDP = 带宽 × 往返时延）**框定——它就是"管道里最多能装的数据量"，窗口开得比 BDP 小，链路永远喂不满。代入算例：10Mbps 链路、RTT 100ms，BDP = 10Mbps × 0.1s = 1,000,000 bit = **125KB**——接收窗口若只开 64KB，链路利用率上限约 64/125 ≈ 51%，带宽再大也白搭。

**第三件：拥塞控制（照顾整条邮路）。** 流量控制照顾**收件人**，拥塞控制照顾**网络**——别把路挤瘫。三招白话：
- **慢启动**：新手上路先发 1 个探路，每轮**指数翻倍**（1→2→4→8）；
- **拥塞避免**：窗口涨过阈值后改**线性缓增**（每轮 +1），稳字当头；
- **丢包了**：窗口减半重整再出发（具体变体有 Tahoe/Reno 等演进【细节待查证】）。

嵌入式关联：07-通信 06 的 MQTT 断线重连"指数退避"（1s→2s→4s），就是应用层对这套思想的仿生。

## 7. UDP：8 字节的极简包裹

**这是什么**：UDP 头只有 8 字节，是个"只写地址不搞服务"的明信片信封。逐字段拆：

| 字段 | 长度 | 作用（白话） |
|------|------|--------------|
| 源端口 | 2 字节 | 回信地址（可不填，填 0） |
| 目的端口 | 2 字节 | 送达哪个进程 |
| 长度 | 2 字节 | 头+数据一共多少字节 |
| 校验和 | 2 字节 | 可选校验，错了丢弃（不重传） |

适用场景（丢了能忍、要快、要广播）：DNS 查询（一次一问一答，重发一次无所谓）、DHCP（必须广播，TCP 无广播能力）、NTP 对时（要最新样本不要旧包重发）、实时音视频（宁可丢帧不可等重传）、局域网设备发现（一喊全楼听见）。

## 8. socket API：TCP 客户端/服务端全套调用

**这是什么**：socket（套接字）是操作系统提供的"网络通话接口"——把它想成**电话机**：服务端装总机（bind/listen/accept），客户端拨号（connect）。调用顺序图（左侧服务端、右侧客户端）：

```
服务端                                     客户端
socket()   ← 买电话机                       socket()   ← 买电话机
bind()     ← 装机并挂上门牌（IP:端口）
listen()   ← 开台："开始接客"
accept()   ← 等客人（阻塞在这）              connect()  ← 拨号（内核自动完成三次握手）
accept 返回新 fd（专门服务这一位客人）
recv()  <--------------------------------   send()     ← 说话
send()  -------------------------------->   recv()     ← 听话
close()     ← 挂断                          close()    ← 挂断（触发四次挥手）
```

最小 C 代码骨架（POSIX 风格，lwIP 的 socket API 与之同构，winsock 只差初始化与关闭函数名）：

```c
/* ---- 服务端：开一家"侦听 8888 端口"的小店 ---- */
int srv = socket(AF_INET, SOCK_STREAM, 0);        /* 买电话机：IPv4 + TCP */
struct sockaddr_in addr = {0};
addr.sin_family      = AF_INET;                   /* 地址族：IPv4 */
addr.sin_addr.s_addr = htonl(INADDR_ANY);         /* 监听本机所有网卡；htonl=主机序转网络序 */
addr.sin_port        = htons(8888);               /* 端口 8888；htons 同理（网络字节序=大端） */
bind(srv, (struct sockaddr *)&addr, sizeof(addr));/* 把电话机固定在 (IP, 8888) 上 */
listen(srv, 5);                                   /* 开台：允许 5 个客人排队 */
int cli = accept(srv, NULL, NULL);                /* 阻塞等第一位客人；返回值 cli 是专用于此客人的新 fd */
char buf[128];
int n = recv(cli, buf, sizeof(buf), 0);           /* 收一句话（n=实际字节数） */
send(cli, buf, n, 0);                             /* 原样回一句（echo 服务） */
close(cli); close(srv);                           /* 挂断；不 close 就会堆积 CLOSE_WAIT */
```

```c
/* ---- 客户端：拨号 + 说一句话 ---- */
int fd = socket(AF_INET, SOCK_STREAM, 0);
struct sockaddr_in srv = {0};
srv.sin_family = AF_INET;
srv.sin_port   = htons(8888);
inet_pton(AF_INET, "192.168.1.50", &srv.sin_addr.s_addr); /* 把字符串 IP 填进结构体 */
connect(fd, (struct sockaddr *)&srv, sizeof(srv));        /* 拨号 = 内核替你跑完三次握手 */
send(fd, "hello", 5, 0);                                  /* 通话开始 */
char buf[128];
int n = recv(fd, buf, sizeof(buf), 0);                    /* 阻塞等回音 */
close(fd);
```

要点：
- `accept` 的返回值是**新 socket**，原 `srv` 继续接客——一个总机带无数分机；
- `send` 返回值要检查：发不满 = 发送缓冲区满，要循环补发；
- 嵌入式对应物：lwIP 提供**三套 API**——BSD socket（与上面同构，最易移植）、netconn（线程化）、RAW（回调式，裸机无 RTOS 用）；MQTT 客户端库底层调的就是这些。

## 9. 嵌入式落地："连接上了但发不出数据"排查思路

**这是什么**：嵌入式最常见网络故障之一：connect 成功，send 却卡死或收不到响应。思路 = **先看状态机、再抓包看现场**：

1. `netstat -ano`（PC 端）看连接状态：不是 ESTABLISHED？那"连上"是错觉（SYN_SENT=握手没成、SYN_RCVD 卡住=半连接）；
2. Wireshark 抓包问三个问题：三次握手完成了吗？我发的包对端 ACK 了吗（没有=中途丢或对端没收）？对方回的窗口（Win）是不是 0（=对端缓冲满，让你暂停发）？
3. 服务端真的在 `accept`/`recv` 吗？只 `listen` 不 accept，积压满了新连接也会僵住；
4. 嵌入式侧自查：lwIP 内存池是否耗尽（memp 统计）、发送缓冲是否太小、网卡中断是否被别的代码饿死。

## 章节小结

- TCP=打电话（连接、可靠、有序、字节流）；UDP=寄明信片（无连接、快、8 字节头、可广播）
- 端口找进程，四元组唯一标识一条连接；1883=MQTT、80=HTTP 等知名端口
- 三次握手：SYN → SYN+ACK → ACK；两次会让服务端无法确认+被旧 SYN 白占资源
- 四次挥手：FIN→ACK→FIN→ACK；TIME_WAIT 等 2MSL = 兜底重发 ACK + 让旧报文清场
- 状态机记四个：ESTABLISHED（正常）、CLOSE_WAIT（你忘了关）、TIME_WAIT（主动方等待）、SYN_SENT（没连上）
- 可靠三大件：确认重传（3 个重复 ACK 快速重传）、滑动窗口（在途上限，随 ACK 滑动）、拥塞控制（慢启动指数、拥塞避免线性）
- socket 顺序：服务端 socket→bind→listen→accept→recv/send→close；客户端 socket→connect→send/recv→close
- 排查"发不出数据"：状态机 + 抓包三问（握手完成？有 ACK 吗？窗口为 0 吗？）

## 常见问题 FAQ

**Q1：TCP 三次握手能不能精简成两次？四次挥手为什么不能合并成三次？**
A：两次不行——服务端无法确认自己的 SYN+ACK 被收到，且旧 SYN 迟到会凭空占资源。挥手则是"确认到达 ≠ 对方没有余话"，被动方可能还有数据要发，②③ 之间的间隔正是它清库存的时间，只有碰巧发完了才被内核合并成三包（这叫捎带确认，是特例不是设计目标）。

**Q2：UDP 不可靠，嵌入式还能放心用吗？**
A：看场景。DNS/对时/广播发现这类"丢了重试就行"的场景用 UDP 是正解；要一字不差的文件传输、命令下发，要么 TCP，要么 UDP+应用层自建确认重传（07-通信 02 的自定义协议思想就是给 UDP 兜底）。

**Q3：send 返回成功，数据就到对方了吗？**
A：没有。send 成功只说明数据进了**本机发送缓冲区**，真正送达由 TCP 负责。对端是否收到要看 ACK（抓包或 `tcp_analysis`），这也是"发完就断电的设备"丢数据的原因——close 后缓冲区里的数据可能还没出门。

**Q4：为什么 lwIP 的 socket 和 PC 上的几乎一样？**
A：lwIP 把 BSD socket API 移植进了嵌入式世界（函数名、语义基本一致），PC 学的代码换个头文件就能上 MCU。区别在底层：lwIP 默认跑在 RAW/回调模型或 RTOS 线程上，内存要精打细算（memp 池），这是嵌入式特有的坑位。
