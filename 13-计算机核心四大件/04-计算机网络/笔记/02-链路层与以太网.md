# 02 · 链路层与以太网

> 定位：网络分层里"最贴硬件"的一层——插上网线之后，数据在局域网里是怎么一帧一帧跑起来的。嵌入式对应物：PHY 芯片、RMII 接口、W5500 配 MAC。

**先说人话**：本篇讲链路层，也就是网络世界的"最后一公里快递"。IP 地址负责把包裹送到正确的城市和街道，但"塞进同一栋楼里某一扇具体的门"是链路层的活。为什么嵌入式工程师需要它？因为你插的网线、STM32 内部的以太网控制器、外挂的 PHY 芯片、W5500 里配的 MAC 地址，全都是这一层的实物——学完本篇，你在 Wireshark 里看到的每一个"帧"都不再是天书。

## 1. 链路层干什么：最后一公里快递

**这是什么**：链路层负责在**相邻设备之间**（同一个局域网内）把数据送达。类比：IP 是"跨城物流系统"，链路层是"同城快递员"——包裹到你的城市靠物流规划，但从站点到你家门口这最后一公里，靠的是另一套规则（认门牌、按铃、当面签收）。

- 上层（IP 层）给的是逻辑地址（192.168.1.x 这种），跨网有效，但"本楼内部"投递不认行政区划，认的是门牌（MAC，下一节）；
- 链路层的传输单位叫**帧（Frame）**：上层传来的字节流被切成一块一块，加上帧头帧尾打包装车；
- 接收方收到帧后先校验、再剥掉帧头帧尾，把里面的内容（IP 包）交还上层——发送端加头、接收端剥头，和 07-通信 01 讲的分层思想一模一样；
- 发送端的**封装流水线**：应用数据（如一条 MQTT 消息）→ TCP 套上头成为"段" → IP 套上头成为"包" → 以太网套头加尾成为"帧" → 网卡把帧变成电信号；接收端反向逐层剥包装——第 3.1 节有一笔具体到字节的"打包总账"；
- 嵌入式对应物：lwIP 移植时最底层那个 `ethernetif.c`（网卡接口文件），里面收发的就是帧。

## 2. MAC 地址：设备的身份证

**这是什么**：MAC 地址（Media Access Control，媒体访问控制地址）是网卡的**物理编号，固定 48 位（6 字节）**，出厂时烧进网卡（现在也允许软件改配）。类比：IP 是"家庭住址"（搬家就变），MAC 是"身份证号"（跟着网卡走）。同一栋楼里投快递，最终认的是身份证号。

- 写法：6 个字节两两一组，冒号或横线分隔，如 `aa:bb:cc:11:22:33`；
- 结构：前 3 字节叫 **OUI（组织唯一标识符）**，代表厂商（可在 IEEE 公开的 OUI 库里查），后 3 字节厂商自己编流水号；
- 两个特殊地址必须认识：
  - `ff:ff:ff:ff:ff:ff` = **广播地址**，意思是"楼里所有人注意"，ARP 请求、DHCP 发现都用它喊话；
  - 目的 MAC 最低位为 1 的是**组播地址**，发给"订阅了这一组"的一批设备（具体组播地址段可查 IEEE 标准【待查证】）；
- 嵌入式对应物：W5500 的 MAC 是你自己往寄存器里配的（见第 7 节），配成啥就是啥——所以**同一局域网里两块板子千万别配重了**，交换机会懵；
- 小项目没有厂商前缀怎么办：正规做法是使用芯片/模组厂商提供的合法 OUI + 自编流水号；只在**封闭内网**里跑时也可自编地址，但务必保证本网段内唯一；
- 现代手机/电脑普遍有"随机化 MAC"隐私功能——每连一个新 WiFi 就临时生成一个 MAC 对外用，防追踪。做 MAC 白名单的实验室环境要留意：设备的"真身 MAC"要看系统设置里的硬件地址。

## 3. 以太网帧逐字段拆解：念一遍快递面单

**这是什么**：以太网 II（也叫 DIX 格式）帧结构——局域网里真正的"包裹"长这样。类比快递面单：谁的件（目的 MAC）、谁寄的（源 MAC）、装的哪类货（类型）、货本身（数据）、封条（FCS）。逐字段过一遍：

| 字段 | 长度 | 作用（白话） |
|------|------|--------------|
| 前导码 Preamble | 7 字节 | 连续的 10101010 重复 7 遍，让接收方"对表"（时钟同步），不是正式内容 |
| 帧起始定界符 SFD | 1 字节 | 10101011，通知接收方"正片开始了" |
| 目的 MAC | 6 字节 | 收件人身份证号；广播就是 6 个 ff |
| 源 MAC | 6 字节 | 寄件人身份证号 |
| 类型 Type | 2 字节 | 说明"数据"字段里装的是哪个上层协议：0x0800=IPv4、0x0806=ARP、0x86DD=IPv6 |
| 数据 Payload | 46~1500 字节 | 上层（IP 包）整包塞进来；不足 46 字节要垫填充（保证碰撞检测有效） |
| FCS | 4 字节 | CRC32 校验值，"包裹封条"——接收方重算一遍对不上就整帧丢弃 |

具体例子走读：主机 A（192.168.1.10，MAC aa:bb:cc:11:22:33）ping 主机 B（192.168.1.20，MAC aa:bb:cc:44:55:66），假设 ARP 已经解析完（第 5 节），A 发出的那一帧从头念到尾：

```
[前导码 7B][SFD 1B]                    ← 对表+开场白，Wireshark 里通常直接被网卡剥掉
[目的MAC aa:bb:cc:44:55:66]            ← "这件是 B 的"
[源MAC   aa:bb:cc:11:22:33]            ← "A 寄的"
[类型    0x0800]                       ← "里面装的是 IPv4 包"
[数据    IP头20B + ICMP头8B + ping数据32B]  ← A ping B 的完整 IP 包
[FCS     4B]                           ← 封条，B 拆包前先验
```

验证方式：Wireshark 抓任意一包，中间的 "Ethernet II" 一行展开就是上面这张表——对照着认一遍，胜过背十遍。

### 3.1 打包总账：一条 MQTT 消息变身一帧的全过程

**这是什么**：把"封装流水线"算成一笔具体到字节的账。假设设备要发一条 27 字节的 MQTT 消息（`{"temp":25.6,"humi":60.0}`）给云平台，每过一层套一层包装：

| 步骤 | 动作 | 累计大小 |
|------|------|----------|
| 1 | 应用层：MQTT 消息本体 | 27 字节 |
| 2 | 传输层：加 TCP 头（端口、序号、确认号等） | +20 → 47 字节的"段" |
| 3 | 网络层：加 IP 头（源/目的 IP、TTL 等） | +20 → 67 字节的"包" |
| 4 | 链路层：加以太网头（MAC+类型）14 字节、尾部 FCS 4 字节 | +18 → 85 字节的"帧" |

时间线读法：每下一层套一层包装，收件方反向拆包——Wireshark 里从外到内依次是 Frame → Ethernet II → IP → TCP → MQTT，正是这张表的倒序。记住这笔账你就明白：为什么 04 篇说 MSS=1460（1500 减去 TCP+IP 头共 40 字节）；应用层消息每多 1 字节，线路上就要多扛 1 字节外加约 58 字节的固定包装（还没算前导码等线路开销）——所以嵌入式上报消息"短小精悍"是真金白银的省。

再进一步——把账本落到十六进制。下面是 A 广播 ARP 请求那一帧的真身（Wireshark 底部 hex 区就长这样，逐字节对照第 3 节和第 5 节的两张表）：

```
ff ff ff ff ff ff aa bb cc 11 22 33 08 06   ← 目的MAC(广播) + 源MAC(A) + 类型0x0806=ARP
00 01 08 00 06 04 00 01                     ← 硬件类型1 / 协议类型0x0800 / 长度6,4 / 操作码1=请求
aa bb cc 11 22 33 c0 a8 01 0a               ← 发送方MAC + 发送方IP(192.168.1.10)
00 00 00 00 00 00 c0 a8 01 14               ← 目标MAC(全0=未知) + 目标IP(192.168.1.20)
```

读法示范：`c0 a8 01 0a` 就是 192.168.1.10 的十六进制真面目（c0=192、a8=168、0a=10）——把任一抓包文件切到 hex 视图练"人工解码"，三层报文头从此再无神秘感。

对照练习：抓一个自己设备发出的包，把 hex 区截下来，用本章两张表人工解码一遍——能独立解出来，本篇就算真正学会了。

## 4. MTU 1500：为什么包裹不能太大

**这是什么**：MTU（Maximum Transmission Unit，最大传输单元）就是一帧里"数据"字段的上限，以太网标准是 **1500 字节**。类比：快递公司规定单件包裹不超 1500 件货，超了必须拆成多件寄（分片），到目的地再拼回来。

- 为什么是 1500：历史折中——帧太大，一帧占线时间长、出错重发的代价大；帧太小，帧头开销占比又太高（具体定值源于早期以太网的历史选择【待查证】）；
- 顺带解释字段表里"不足 46 字节要垫填充"：早期共享式以太网用 CSMA/CD（载波侦听多路访问/冲突检测——大家先听线再说话，撞车了各自退避重来），帧太短就听不出"撞车"，故设最短帧长；如今交换机全双工已无冲突，但格式兼容沿用至今；
- 影响：上层 IP 包超过 1500 字节 → IP 层被迫**分片**（详见 03 篇 IPv4 头的"标识/片偏移"字段），而任何一片丢了，整个包都得重传——所以**应用层单个包别做得太大**；27 字节的温湿度 JSON 离分片很远，但一个 2KB 的升级固件包就会被拆成两片；
- 嵌入式对应物：lwIP 里 TCP 的 MSS（最大报文段）默认 1460 字节 = 1500 − 20（IP 头）− 20（TCP 头）；07-通信 07 建议 MQTT 单包控制在 64~256 字节，理论根子就在这里。

## 5. ARP：从 IP 查 MAC 的"广播寻人"

**这是什么**：ARP（Address Resolution Protocol，地址解析协议）解决的问题是"我知道邻居的 IP，但不知道他的 MAC，包裹没法写面单"。类比：在小区群里喊一嗓子——"**谁是 192.168.1.20？领快递请报一下身份证号！**"

时间线（A=192.168.1.10 想给 B=192.168.1.20 发包，本地 ARP 缓存是空的）：

| 步骤 | 动作 | 白话 |
|------|------|------|
| 1 | A 先查本机 ARP 缓存（一张"IP 对 MAC"的小通讯录） | "通讯录里有他吗？"——没有 |
| 2 | A 发出 **ARP 请求**，目的 MAC = ff:ff:ff:ff:ff:ff（广播帧） | 全楼都听得见："谁是 192.168.1.20？报 MAC！" |
| 3 | 楼里所有设备都收到，只有 B 认领 | 其他人心不在焉，顺手把"A 的 MAC"也记进了小本本 |
| 4 | B 用**单播**（点对点）回 ARP 应答 | "我是 192.168.1.20，我的 MAC 是 aa:bb:cc:44:55:66" |
| 5 | A 把映射写进缓存（带老化时间，超时作废重查） | 记下小本本，之后直发不再喊话 |

ARP 请求报文本身也是逐字段的（Wireshark 里展开 ARP 层可见）：

| 字段 | 长度 | 作用（白话） |
|------|------|--------------|
| 硬件类型 | 2 字节 | 查的是什么硬件：1=以太网 |
| 协议类型 | 2 字节 | 查的是什么协议地址：0x0800=IPv4 |
| 硬件地址长度 | 1 字节 | MAC 长 6 字节 |
| 协议地址长度 | 1 字节 | IPv4 长 4 字节 |
| 操作码 | 2 字节 | 1=请求（喊话）、2=应答（报名） |
| 发送方 MAC / IP | 6+4 字节 | "我是 A 的 MAC，我是 .10" |
| 目标 MAC / IP | 6+4 字节 | 请求里目标 MAC 填全 0（"就是想知道这个"），目标 IP 填 .20 |

两个工程要点：
- 跨网段时 A 发现目的 IP 不在本地网段，就不喊 B 了，直接 ARP **网关**的 MAC——"包裹送前台就行，后面它负责"。排查"ping 同网段通、跨网段不通"，先看能不能 ARP 到网关；
- 验证命令：`arp -a`（Windows）查看本机 ARP 表，里面应该能看到网关 IP 对应的 MAC；
- 安全常识：ARP 天生**没有认证**——局域网里谁都能谎报"我是网关"，这正是 ARP 欺骗（中间人攻击的老套路）的根源；设备接入不可信网络时要有防范意识（交换机侧防护/静态绑定属进阶内容【待查证】）。

## 6. 交换机 vs 路由器：同楼派送 vs 跨城物流

**这是什么**：两种转发设备工作在不同层、看不同的"地址"。类比：交换机是**小区内部分拣员**（只认门牌 MAC，在本小区内投递）；路由器是**跨城邮局**（只认行政区划 IP，决定往哪个城市发）。

| 对比项 | 交换机（Switch） | 路由器（Router） |
|--------|------------------|------------------|
| 工作层 | 链路层（二层） | 网络层（三层） |
| 转发依据 | MAC 地址表 | 路由表（IP 前缀，见 03 篇） |
| 对广播帧 | 泛洪到所有口（不隔离广播域） | 拦下不转发（隔离广播域） |
| 一句话 | 同楼派送 | 跨城物流 |

交换机"学表"过程时间线（它怎么知道哪个 MAC 在哪个口）：
1. 收到一帧 → 先记下"源 MAC + 进来的端口号"（寄件人从哪个门进的）；
2. 查目的 MAC：表里有 → 从对应端口转发（精准投递）；
3. 表里没有 → 除了进来的口，其余所有口各发一份（泛洪，"谁认识他谁签收"）；
4. 广播帧（ff:ff:...）永远泛洪——这就是为什么路由器要说"隔离广播域"。

两台交换机级联时原理不变：跨交换机的设备通信，靠双方 MAC 表各自学出的"上联口"路径逐段接力——表里没有就泛洪，学到了就直转。注意级联口是两片网络之间的公共咽喉，大流量场景里它最先成为瓶颈。

### 6.1 家里那台"路由器"其实是三合一

**这是什么**：家用"路由器"是个合体怪——路由器 + 交换机 + 无线 AP（Access Point，无线接入点）三件装。看清分工排障才不迷路：电脑和电视之间互拷文件走的是**交换机**部分（同网段 MAC 直达，不劳驾路由）；访问外网才走**路由器**部分（NAT 转换，03 篇细讲）；手机连 WiFi 接的是 **AP** 部分。所以"内网两台设备互 ping 不通"多半是交换/AP 侧的问题（访客网络隔离、AP 隔离开关），与"上不了外网"是两类完全不同的故障。顺带一提：光猫/路由器/交换机串成一串时，定位故障用"替换法"——怀疑哪一段，就把那台设备旁路掉再测一次。

## 7. 嵌入式落地：PHY、RMII 与 W5500

**这是什么**：MCU 要跑以太网，链路层的硬件由三块拼成。类比：**MAC 控制器**是"打包车间"（组帧、算校验），**PHY 芯片**是"货车司机"（把数字字节变成网线上的差分电信号），**RMII 接口**是车间和司机之间的传送带。

- **MAC 控制器**：STM32F4/F7/H7 片内自带 ETH 外设，lwIP 驱动它完成组帧/收帧/CRC 校验；
- **PHY 芯片**（常见型号如 LAN8720、KSZ8081）：片内 MAC 只能输出数字信号，PHY 负责编解码成双绞线上的差分信号——抗噪思想和 07-通信 01 的 RS485 差分传输同源；PHY 上电后会做**自协商**（两端自动商定 10/100/1000M 速率与全/半双工），网口灯不亮先怀疑协商没成；
- **RMII 接口**（Reduced Media Independent Interface，精简媒体独立接口）：MCU 与 PHY 之间的数据传送带，2 位数据宽度，典型引脚：REF_CLK（50MHz 参考时钟）、TXD0/TXD1/TX_EN（发送方向）、RXD0/RXD1/CRS_DV（接收方向）、MDC/MDIO（配置 PHY 寄存器用的小串口）；引脚比老标准 MII 少一半，省 IO；
- **W5500**：另一条路线——**硬件协议栈芯片**，MAC + TCP/IP 全部用硬件电路实现，MCU 只需要 SPI 读写它的寄存器和收发缓冲：MAC 地址是配置进去的（写 SHAR 源硬件地址寄存器），IP/子网掩码/网关/DNS 也是寄存器即配即用，socket 收发像读写文件一样——单片机裸机小项目"不会 lwIP 也能上网"的懒人方案；
- 另外一些 SoC（如 ESP32 系列）把 MAC 和 PHY 都集成进芯片内部，外围只需要网口变压器和 RJ45 座——选型时"片内自带到什么程度"直接影响 BOM 和布板难度。

## 章节小结

- 链路层 = 最后一公里快递：把帧送到**同一局域网**的邻居，传输单位是帧
- MAC 地址 = 48 位设备身份证，前 3 字节厂商标识；ff:ff:ff:ff:ff:ff 是广播
- 以太网帧 = 前导/SFD + 目的MAC + 源MAC + 类型 + 数据(46~1500) + FCS，Wireshark 对照认字段最快
- MTU 1500 → 超了 IP 分片、丢一片全包重传 → 应用层单包别太大（lwIP MSS=1460 的由来）
- ARP 用"广播喊话+单播应答"查 IP 对 MAC，有缓存有老化；跨网段 ARP 的是网关
- 交换机看 MAC（同楼派送、不隔离广播域），路由器看 IP（跨城物流、隔离广播域）
- 嵌入式硬件三件套：片内 MAC + 外挂 PHY（RMII 相连），或 W5500 硬协议栈一条龙（MAC 是配置进去的）
- 家用"路由器"实为路由 + 交换 + AP 三合一，"内网互不通"与"上不了外网"是两类故障

## 常见问题 FAQ

**Q1：已经有 IP 地址了，为什么还需要 MAC 地址？**
A：分工不同——IP 负责"跨网络找到你在哪个网"（逻辑地址，会随接入位置变化），MAC 负责"在本地网段内把这帧实际投递到哪块网卡"（物理身份）。类比：跨城物流按"省市区"分拣（IP），小区内部按"门牌"派送（MAC），两层各管一段，缺一不可。

**Q2：广播帧到底会被谁收到？**
A：同一广播域里的所有设备都会收到并处理。交换机不隔离广播（泛洪转发），路由器隔断广播。所以一个局域网设备太多时广播流量会成负担——大网络通常用路由器（或 VLAN，进阶内容可暂不深究）来划分广播域。

**Q3：两块 W5500 板子 MAC 配成一样的会怎样？**
A：交换机的 MAC 表会不停在两个端口之间"来回改口"，帧时而被送到错误端口，表现为时通时断、极难排查。同网段内 MAC 必须唯一，拿到新板子先检查出厂/例程 MAC。

**Q4：FCS 校验失败的帧去哪了？**
A：网卡直接丢弃，上层完全无感知（也收不到通知）。所以"线路上偶发误码"表现为丢帧，由上层（TCP 重传或应用层超时）兜底——这也是 TCP 可靠传输存在的原因之一。

**Q5：Wireshark 里为什么看不到前导码和 FCS？**
A：因为收发都由网卡硬件完成——前导码用于芯片级时钟同步，收到即被网卡剥掉；FCS 由网卡校验，不合格的帧根本不上交系统。所以 Wireshark 里的帧从"目的 MAC"字段开始，这是正常现象，不是抓包工具坏了。
