# 05 · 应用层与抓包实战

> 定位：网络栈的"最终业务对话"（DNS/HTTP/MQTT），以及把前四篇全部串起来验证的武器——Wireshark。嵌入式对应物：设备连云全靠这层的报文说话，抓包是排障终极手段。

**先说人话**：前面几篇讲的以太网、IP、TCP 全是"物流"——打包、寻址、可靠运输；本篇讲"货本身"：DNS 翻译地址、HTTP 请求网页、MQTT 收发物联网消息，这些才是业务的真面目。为什么嵌入式工程师需要它？设备上云出问题，九成卡在应用层到物理层的某一环——本篇给一条"五步排查树"和一套 Wireshark 实战流程，把故障一层层剥出来。

## 1. 应用层是什么：最终业务对话

**这是什么**：应用层协议定义"程序之间说什么话、按什么格式说"。类比：物流系统（下三层）负责包裹完好送达，应用层协议则是**收发双方约好的对话剧本**——先说什么、后说什么、答非所问算违约。

- 前四篇解决"送得到"（链路层送达、IP 寻址、TCP 可靠），应用层解决"说什么"（业务语义）；
- 应用层报文（消息）会整包塞进 TCP/UDP 的载荷里运输：HTTP/MQTT 走 TCP，DNS/DHCP 走 UDP；
- 自研协议的"帧头+长度+校验+序号+应答"清单（07-通信 02）与 HTTP/MQTT 的设计一一对应——读现成协议就是读"官方标准答案"；
- 嵌入式对应物：ESP8266 的 AT 指令、lwIP 的 httpd、MQTT 客户端库，全是应用层的实现。

## 2. DNS：把域名翻译成 IP 的全流程

**这是什么**：DNS（域名系统）是"网络电话簿"——机器只认 IP，人类只记域名，DNS 负责翻译。递归与迭代的白话：**递归查询**=你问旅行社"帮我订到最后的票，办不成就告诉我"；**迭代查询**=旅行社自己不跑腿，告诉你"这问题该去 A 部门，A 说去 B 部门"，你自己一层层跑。

时间线（浏览器输入 www.example.com 后，到建立连接前的每一步）：

| 步骤 | 动作 | 白话 |
|------|------|------|
| 1 | 查浏览器缓存 → 查系统缓存 → 查 hosts 文件 | "电话簿里查过吗？有没有私人备注？" |
| 2 | 都没有 → 问**本地 DNS 服务器**（路由器/运营商给的），这是**递归查询** | "旅行社，帮我把这事办到底" |
| 3 | 本地 DNS 也不知道 → 问**根服务器**（迭代）：谁管 .com？ | 每层只回"下一个该问谁" |
| 4 | 问 .com 顶级域服务器：谁管 example.com？ | 再拿到"下一跳" |
| 5 | 问 example.com 的**权威服务器**：www 的 IP 是？ | 终于拿到答案 93.184.x.x |
| 6 | 本地 DNS 把答案缓存（带 TTL）并回给浏览器 | 旅行社记进备忘录，下次直接报 |
| 7 | 浏览器拿到 IP → 发起 TCP 三次握手（04 篇）→ 发 HTTP 请求 | 查完地址才拨号 |

- 验证：`nslookup www.example.com` 直接问 DNS；Wireshark 过滤 `udp.port == 53` 能看到完整问询链；

典型输出逐行读（Windows）：

```
> nslookup www.example.com
服务器:  router.localdomain      ← 当前使用的本地 DNS（往往就是路由器）
Address:  192.168.1.1            ← 它的地址

非权威应答                        ← "答案是从缓存/上游转来的，不是该域名的权威服务器亲口说的"
名称:    www.example.com
Address:  93.184.x.x             ← 最终翻译结果，浏览器/设备拿它去发起 TCP 握手
```

- 嵌入式对应物：设备里要正确配 DNS 服务器地址（DHCP 第 4 步顺带下发），否则"ping IP 通、ping 域名不通"。

## 3. HTTP：请求/响应报文逐行拆

**这是什么**：HTTP 是"点单式"文本协议——客户端递上一张结构化的单子（请求），厨房回一份结构化的单子（响应）。文本化意味着人能直接读懂，抓包时明文可见（HTTPS 则加密了内容）。

一个真实的 GET 请求（浏览器访问 http://device.example.com/api/v1/temp）：

```
GET /api/v1/temp HTTP/1.1            ← 请求行：方法 空格 路径 空格 版本
Host: device.example.com             ← 头：目标主机（一台服务器挂多站点时靠它区分）
User-Agent: STM32-httpclient/1.0     ← 头：我是谁（设备名/固件版本）
Accept: application/json             ← 头：我想要 JSON 格式
                                     ← 空行：头部结束的标志（必须有！）
（GET 无正文；POST 会在这里带表单/JSON 数据）
```

服务器的响应：

```
HTTP/1.1 200 OK                      ← 状态行：版本 状态码 短语（200=成、404=查无此路径、500=服务器出错）
Content-Type: application/json       ← 头：给你的是 JSON
Content-Length: 27                   ← 头：正文 27 字节（TCP 字节流靠它切出消息边界）
                                     ← 空行
{"temp":25.6,"humi":60.0}            ← 正文
```

三个嵌入式要点：
- **Content-Length 就是应用层的"长度域"**——TCP 是字节流没有消息边界（04 篇），HTTP 靠这个头切分消息，与 07-通信 02 自研协议的长度域同一思想；
- 状态码三兄弟：2xx 成功、4xx 你（客户端）错了、5xx 我（服务器）错了——设备上云报错先看它；
- 单片机做 HTTP 客户端时，整个请求就是往 TCP 连接里写一段拼好的文本，没有魔法。

### 3.1 设备上报一条数据的完整对话

**这是什么**：单片机设备用 HTTP POST 上报一次温湿度——你会看到它和 GET 只差"方法名"和"有正文"两处：

```
POST /api/v1/report HTTP/1.1        ← 方法换成 POST：我要提交数据
Host: cloud.example.com
Content-Type: application/json      ← 正文是 JSON
Content-Length: 27                  ← 正文 27 字节（服务器照此读够为止）
                                    ← 空行：正文从这里开始
{"temp":25.6,"humi":60.0}           ← 正文：本次上报的数据

→ 响应 HTTP/1.1 200 OK（业务层常见报错：400 参数不合法 / 401 鉴权失败 / 429 请求过于频繁）
```

完整时间线：DNS 拿 IP（第 2 节）→ TCP 三次握手（04 篇第 3 节）→ 发请求 → 收响应 → 按连接复用策略保活或关闭。注意：设备若**每次上报都新建连接**，服务器端会堆积大量 TIME_WAIT（04 篇第 4 节的运维经典题）——高频上报应当长连接复用，或干脆换 MQTT（本来就是长连接）。

## 4. MQTT 报文家族速览

**这是什么**：MQTT 是物联网的"订阅-发布"消息协议，跑在 TCP 上。报文结构极简：**固定头（2 字节起）+ 可变头 + 载荷**。类比：快递系统里不同的业务单——寄件单（CONNECT）、发货单（PUBLISH）、订阅单（SUBSCRIBE），单据格式统一、字段少、省流量。

固定头第 1 字节：高 4 位 = 报文类型，低 4 位 = 类型专用标志；第 2 字节起 = 剩余长度（变长编码，最多 4 字节）。常用类型速记：1=CONNECT、2=CONNACK、3=PUBLISH、4=PUBACK、8=SUBSCRIBE、9=SUBACK、12=PINGREQ（心跳）、13=PINGRESP。

**CONNECT（连云的第一句话）** 可变头+载荷拆解：

| 字段 | 作用（白话） |
|------|--------------|
| 协议名 "MQTT" + 协议级别 | "我说的是 MQTT 3.1.1 方言"（级别 4）【MQTT 5.0 为级别 5】 |
| 连接标志 | 一排开关：清除会话？有遗嘱消息？带用户名/密码？ |
| Keep Alive | "我最多 X 秒吭一声"——超时没动静 Broker 判定掉线 |
| 载荷：ClientID | 设备身份证（同一 Broker 上重复 ClientID 会互踢） |
| 载荷：用户名/密码 | 平台鉴权（如 OneNET/阿里云的 token 机制） |

**PUBLISH（发一条传感器数据）**：可变头 = 主题名（2 字节长度 + UTF-8 字符串）+ 报文标识符（QoS1/2 时才有）；载荷 = 你发的业务数据（JSON/二进制都行）。

**QoS 三档差异表**（服务质量，面试常考）：

| QoS | 含义 | 机制 | 代价 |
|-----|------|------|------|
| 0 | 至多一次（可能丢） | 发完就忘 | 最快 |
| 1 | 至少一次（可能重） | PUBLISH → 等 PUBACK，没等到就重发 | 中，可能重复 |
| 2 | 恰好一次（不丢不重） | 四步握手 PUBREC/PUBREL/PUBCOMP 去重 | 最慢 |

嵌入式选型：绝大多数平台用 **QoS1 折中**（业务侧容忍重复即可），QoS2 留给"绝对不能重复执行"的控制指令。

## 5. Wireshark 抓包实战全流程

**这是什么**：Wireshark 是"网络显微镜"——网卡上的每一个帧都被它摊开展示，前四篇学的每个字段在这里都能亲眼看到。三步上手：**选网卡 → 过滤 → 看流**。

第一步，选网卡：打开后双击"流量在跳动"的那块（有线选以太网，WiFi 选 WLAN），开始捕获；
第二步，显示过滤器（只显示你要的包，语法是"字段 + 运算符 + 值"）：

| 过滤表达式 | 含义（白话） |
|-----------|--------------|
| `ip.addr == 192.168.1.100` | 只看跟这台设备的往来 |
| `tcp.port == 1883` | 只看 MQTT 明文流量 |
| `udp.port == 53` | 只看 DNS 查询 |
| `icmp` | 只看 ping |
| `tcp.flags.syn == 1 && tcp.flags.ack == 0` | 只看握手第一包（找新连接） |
| `http` / `mqtt` | 只看应用层报文 |
| `tcp.stream eq 0` | 只看第 0 条 TCP 连接（一条连接从头到尾） |

第三步，跟踪 TCP 流：右键任意 TCP 包 → Follow → TCP Stream，把一条连接的往来字节拼成可读对话（HTTP 明文、MQTT 报文都还原出来）。

三个递进实验（做一遍 = 前四篇全部落袋）：
- **实验一（链路/网络层）**：过滤 `icmp`，命令行 ping 同网段设备——看到 Echo Request/Reply 成对出现，展开 IP 头核对 TTL 与协议号；
- **实验二（传输层）**：过滤 `tcp`，浏览器打开一个 http:// 开头的网站——前三包 SYN / SYN,ACK / ACK 即三次握手，再找 GET 请求明文（HTTPS 站点看不到明文，只有加密流）；
- **实验三（应用层）**：PC 装 mosquitto 客户端，向 1883 端口的 Broker `mosquitto_pub -h 服务器 -t test -m hi`——过滤 `mqtt`，依次认出 CONNECT（含 ClientID/KeepAlive）→ CONNACK（返回码 0=接受，非 0=拒绝原因）→ PUBLISH → PUBACK（QoS1 的回执）。

## 6. 嵌入式落地：设备连不上云平台的"五步排查树"

**这是什么**：设备上云失败的标准化排查流程——**从物理层往上，一层只问一个问题**，不跳步。类比查水管漏水：先看总阀（物理），再查水表（IP），最后才怀疑水龙头（应用）。

```
① 物理层：网线插好吗？灯亮吗？WiFi 真连上 AP 了吗（AT+CWJAP 返回）
     └ 不通 → 查供电/水晶头/天线，止步于此
② IP 层：ping 网关 → ping 114.114.114.114
     └ 网关不通 = 内网配置问题（掩码/DHCP 没拿到，见 03 篇）
     └ 公网 IP 不通 = 出口问题（NAT/路由器 WAN 断了）
③ DNS：ping 你的云平台域名，看能否解析出 IP
     └ 解析失败 = DNS 没配/被劫持；nslookup 对比正常电脑的结果
④ TCP：测端口通不通（PC 上 telnet mqtt.example.com 1883 或 TCPing 工具）
     └ 不通 = 中间网络拦了（防火墙/白名单没加设备出口 IP/平台维护）
⑤ MQTT：用 MQTTX 等 PC 客户端连同一个 Broker 对比
     └ PC 能连设备不能 → 回头查设备代码（ClientID 重复互踢、KeepAlive 太短、
       时间戳错误导致 token 失效）；Wireshark 抓设备侧流量看 CONNECT/CONNACK
```

每步的"用什么验证"一句话：①看灯/AT 回显；②ping；③nslookup/ping 域名；④telnet/端口工具；⑤MQTTX 对比 + Wireshark 抓 `mqtt`。这棵树与 07-通信 07 综合项目的联调经验互为印证。

## 章节小结

- 应用层 = 最终业务对话，前四层全是物流；HTTP/MQTT 走 TCP，DNS/DHCP 走 UDP
- DNS = 电话簿：浏览器缓存→hosts→本地 DNS（递归）→根/顶级域/权威（迭代）→拿 IP 才拨号
- HTTP 请求行/头/空行/正文四段式；Content-Length 是应用层长度域；状态码 2xx/4xx/5xx 分清"谁的错"
- MQTT 固定头 2 字节起：类型+标志、剩余长度；CONNECT 带 ClientID/KeepAlive/鉴权；QoS0 快、QoS1 可能重、QoS2 慢而准
- Wireshark 三步：选网卡 → 显示过滤（ip.addr/tcp.port/icmp/mqtt）→ Follow TCP Stream 还原对话
- 三个递进实验：ping 抓 ICMP、浏览器抓三次握手、mosquitto 抓 CONNECT/PUBLISH
- 连云排障五步树：物理→IP→DNS→TCP→MQTT，每步一个命令一层问题，不跳步

## 常见问题 FAQ

**Q1：DNS 为什么用 UDP 而不用 TCP？**
A：一次查询就是"一问一答"，报文小、追求快，UDP 一发一收最划算；答不上来客户端重问一次即可。域名响应过大（超过一包）或区域传送等场景才会退回 TCP【细节待查证】。

**Q2：HTTP 的"空行"为什么必须存在？**
A：头部是若干行文本，解析器需要明确知道"头到哪结束、后面是正文"——空行就是分隔符。这和自研协议的"帧头/载荷定界"是同一问题，HTTP 的答案是空行+Content-Length，你的协议可以是长度域。

**Q3：MQTT QoS2 既然"恰好一次"，为什么不用它？**
A：四步握手（PUBLISH→PUBREC→PUBREL→PUBCOMP）时延和流量都翻倍，单片机弱网下更容易卡在中间态。工程上通常 QoS1 + 业务幂等（重复消息业务侧去重）更划算。

**Q4：抓包时 MQTT 的内容看不到明文怎么办？**
A：说明走了 8883 端口的 TLS 加密——链路上只有密文。调试期可让设备连 1883 明文端口（仅测试环境），或用平台提供的日志/本地代理解密【各平台手段不同，具体查平台文档】。

**Q5：五步树走完都通，但业务还是不工作？**
A：那就是应用层语义问题——主题（Topic）权限没开、JSON 格式被平台拒、心跳间隔超过 Keep Alive 被踢。用 MQTTX 复现同样操作，对比设备与 PC 的报文差异，差异点就是答案。
