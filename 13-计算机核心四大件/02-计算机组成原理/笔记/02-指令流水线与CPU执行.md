# 02 · 指令流水线与 CPU 执行

> 定位：组成原理详解第一篇，回答"CPU 怎么把一条条指令跑起来"。是导读篇（[01-计算机组成原理-嵌入式视角](01-计算机组成原理-嵌入式视角.md)）2.1 节的展开，学完 STM32 启动与中断后回看收获最大。

**先说人话**：本篇讲 CPU 内部的干活节奏——执行一条指令分三步（取指→译码→执行），以及怎么让三步**重叠**起来提速（流水线）。为什么嵌入式工程师需要它？因为 Cortex-M3 的三级流水直接决定了三件你天天遇到的事：**中断为什么响应要十几个周期、跳转为什么有代价、循环展开为什么能提速**——这些都不是玄学，是流水线一笔一笔算出来的。

## 1. CPU 执行一条指令的三步：取指 → 译码 → 执行

**这是什么**：CPU 干活的基本节奏就三步——**取指**（Fetch，从存储器把指令取回来）、**译码**（Decode，弄清这条指令要干什么）、**执行**（Execute，真去干）。类比：厨师照菜谱做菜——先翻到那一页（取指），读懂"红烧肉步骤"（译码），再动手开炒（执行）。

先把三个术语说人话：

- **指令（Instruction）**：CPU 能听懂的一条"最小命令"，用二进制编码。你写一行 C `a = b + c;`，编译后就是几条指令的组合（一条"读 b"、一条"读 c 加"、一条"写 a"级别的活）；
- **PC（Program Counter，程序计数器）**：存"下一条指令地址"的寄存器——菜谱里的书签，永远指着下一页；
- **汇编（Assembly）**：指令的"人话写法"，一条汇编对应一条机器码（怎么把机器码翻回汇编，本目录 05 篇细讲）。

三步各自的动作，以 `ADD R0, R1, R2`（即 R0 = R1 + R2）为例：

```text
取指：按 PC 里的地址，从存储器把这条指令的编码取回来，PC 指向下一条
译码：控制器"翻译"编码——哦，是加法，两个源操作数在 R1、R2，结果放 R0
执行：R1、R2 进加法器，结果写回 R0
```

嵌入式注脚：Cortex-M 用 **Thumb-2** 指令集，16 位 / 32 位混合编码——一条指令可能占 2 字节也可能占 4 字节，所以 PC 有时 +2 有时 +4。定长还是变长，是"译码好做"和"程序省空间"之间的取舍（导读篇讲过 RISC vs CISC 的取舍）。

**补一点世界观（存储程序思想）**：指令和数据都存在同一个存储器里——这是冯·诺依曼体系最核心的一步。你的 C 代码编译成指令序列放进 Flash，CPU 复位后从固定地址逐条取——**"程序也是一种数据"**，所以才能有编译器（生成指令）、Bootloader（搬运指令）、OTA（远程更新指令）。类比：菜谱本身也是一页纸，可以复印、修改、换一本——改菜谱不用换厨房。

## 2. 流水线：让三步像洗衣店一样重叠

**这是什么**：流水线（Pipeline）= 把三步分给三个"工位"，**前一条指令在执行时，后一条已经在译码，再后一条在取指**——三步不互相干等。类比：洗衣店三台设备（洗衣机→烘干机→熨烫台），第一批衣服烘干时，第二批已经在洗、第三批已经进洗——三台设备同时忙，而不是一台干完全场围观。

先算**不开流水线**的账（代入具体数字，设每步 1 个时钟周期）：

```text
一条指令 = 3 步 = 3 周期
跑 3 条指令（串行干等）：3 × 3 = 9 周期
```

**开流水线**后的时间表（△=取指，○=译码，□=执行）：

```text
周期:    1    2    3    4    5
指令1:   △    ○    □
指令2:        △    ○    □
指令3:             △    ○    □
```

看懂这张表的关键：

- 第 1 条指令仍要 3 周期才出结果——**单条延迟没变**；
- 但从第 3 周期起，**每个周期都有一条指令完工**——吞吐量（单位时间完成的指令数）变成 1 条/周期；
- 通用公式：**N 条指令总周期 = 3 + (N − 1)**。代入 N = 1000：流水线 1002 周期 vs 串行 3000 周期，**提速约 3 倍**；
- 平均到每条指令的周期数叫 **CPI**（Cycles Per Instruction）≈ 1。

串行 vs 流水线（代入三组 N 验证公式"3+(N−1)"）：

| 指令数 N | 串行（3N） | 流水线（3+N−1） | 提速倍数 |
|---------|-----------|----------------|---------|
| 3       | 9 周期     | 5 周期          | 1.8 |
| 100     | 300 周期   | 102 周期        | 约 2.9 |
| 1000    | 3000 周期  | 1002 周期       | 约 3.0 |

规律看表即得：N 越大，流水线前 2 个周期的"启动开销"越可忽略，提速越逼近级数 3——**流水线赚的是"长跑"的钱，短程序吃不饱**。

换成主频算一笔真金白银的账：STM32F103 主频 72MHz（来龙去脉见 [07-STM32 时钟树](../../../07-STM32/笔记/01-工程建立与时钟树.md)），即每秒 72,000,000 个周期。流水线满载时 1 条/周期 → 理论每秒完工约 7200 万条指令（≈72 MIPS 量级）。Cortex-M3 官方标称 1.25 DMIPS/MHz，72MHz 约 90 DMIPS——注意这是"理想满载"值，现实中会被下面的冒险拉低。

## 3. 流水线冒险：三种"堵车"

**这是什么**：冒险（Hazard）= 让流水线断流的情况——本该每周期完工一条，现在某些周期只能空转。洗衣店同样有三种堵车：抢设备、等前道工序、临时改单。

### 3.1 结构冒险：两批衣服抢同一台机器

**白话**：硬件资源冲突——同一周期两条指令要用同一个部件。洗衣店版本：第一批衣服要烘、第三批要洗，可洗衣机和烘干机插的是同一个插座，功率只够一台。

- CPU 例子：取指要从存储器读指令，上一条"加载数据"的指令也要从存储器读数——**一条存储器通道忙不过来**；
- 硬件解法预告：**哈佛结构**让指令和数据各走各的总线（本篇第 5 节）——等于给"抢插座"的地方修了两条电线。

### 3.2 数据冒险：晾衣服之前必须先洗完

**白话**：前后指令有数据依赖——后一条要用前一条的结果，只能等。洗衣店版本：叠衣服必须等烘完，烘完前熨烫台只能闲着。

```text
ADD R0, R1, R2    ; R0 = R1 + R2   ← 结果还没写回寄存器
SUB R3, R0, R4    ; R3 = R0 - R4   ← 却已经要用 R0（数据冒险）
```

- 不处理就只能在中间插空转周期（叫**流水线气泡**，bubble——流水线上一个"什么都没有"的空位）；
- 硬件解法：**前递/旁路（Forwarding / Bypassing）**——加法器算完的结果不等写回，直接"从锅递到下一道工序"。类比：炒好的菜直接递给摆盘的，不用先放回冰箱再拿出来。

### 3.3 控制冒险：客户临时改单，排好的流程全废

**白话**：遇到分支/跳转指令时，CPU 还不知道"下一条该取哪"——流水线里预取的指令可能全作废。洗衣店版本：烘干机正烘着第二批，客户突然说"这批不合格重洗"——烘干机的排程清空重来。

```text
BEQ  skip       ← 跳不跳，要等它走到执行级才知道
（中间的指令）    ← 流水线已预取：赌它"不跳"继续往下取
skip 处的指令    ← 若真跳了：预取的作废，重新按新地址取指（流水线冲刷 flush）
```

- 代价 = 重新填满流水线的周期，量级约 2~3 个周期（精确数字随指令与访存条件变化，以 TRM 为准）；
- 软件解法：把**最可能走的路径**安排在"不跳"的那条路上——编译器做分支优化，你写循环时把最常见的情况放前面，都是这个思路。

三种冒险速查（以后见到"程序莫名变慢"，按这张表对号入座）：

| 冒险类型 | 一句话识别 | 洗衣店版本 | 常见解法 |
|---------|-----------|-----------|---------|
| 结构冒险 | 两条指令抢同一部件 | 两台机器抢一个插座 | 哈佛双总线、资源复制 |
| 数据冒险 | 后条要用前条的结果 | 叠衣必须等烘干 | 前递/旁路、编译器重排 |
| 控制冒险 | 跳转后不知该取哪条 | 临时改单、计划作废 | 预取"不跳"路径、展开循环 |

## 4. Cortex-M3 三级流水：中断延迟与循环展开的答案

**这是什么**：Cortex-M3 内核就是一个**三级流水线**——取指、译码、执行各一级。你平时听到的两个"经验之谈"，全是它推出来的。

**为什么中断响应要十几个周期**：中断一来，CPU 不是"瞬间传送"到 ISR，要按顺序办四件事——

```text
① 收尾当前指令、识别并裁决中断请求
② 硬件自动压栈 8 个寄存器（R0~R3、R12、LR、PC、xPSR）——现场打包
③ 查向量表拿到 ISR 入口地址
④ 流水线重填，ISR 第一条指令开始执行
零等待存储器条件下：合计典型 12 个周期（72MHz 下 ≈ 0.17μs）
```

（压栈为什么是这 8 个、MSP/PSP 怎么分，见 [07-STM32 调试实战](../../../07-STM32/笔记/07-调试实战.md)；向量表长什么样见本目录 04 篇。）

**为什么循环展开能提速**：循环结尾的跳转是控制冒险的常客——每次跳转都可能付 ~2~3 周期的冲刷代价。代入算例：

```text
for (i = 0; i < 10; i++) { 小活 }     → 10 次跳转 × 3 周期 ≈ 30 周期纯浪费
循环展开 ×2（循环体做两份活）          → 5 次跳转，浪费减半
```

代价是代码变大（空间换时间）——Flash 只有几十 KB 的 MCU 上要掂量，这也是编译器 `-O2` 展开有上限的原因。

**M3 没有分支预测，怎么活得还不错**：PC 级 CPU 有复杂的分支预测器去"猜跳不跳"，Cortex-M3 干脆固定按顺序预取（赌"不跳"）。好处：硬件简单省电、时序行为可预期；坏处：跳转一定有代价、没有"猜对白赚"的运气。所以 M3 上的优化原则更朴素——**热路径少跳转**，比在 PC 上玩分支花活更实在。

**为什么 ISR 要短**（08-FreeRTOS 那条纪律的硬件根源）：ISR 越长，排在后面的同/低优先级中断等待越久，最坏响应延迟越不可控——实时性的敌人不是那 12 周期，是不确定的排队时间。

**Flash 等待周期会放大一切**：跳转后要重新取指，Flash 慢一拍，重填成本更高——等待周期的账见本目录 [03-Cache 与存储层次](03-Cache与存储层次.md)。

## 5. 哈佛结构 vs 冯·诺依曼：指令和数据分不分家

**这是什么**：两种"厨房布局"——**冯·诺依曼结构**：食谱和食材放同一个柜子、进出只有一扇门（指令、数据共用一套总线）；**哈佛结构**：食谱柜和食材柜分开、各走各的门（指令总线、数据总线分开）。Cortex-M 系列是哈佛结构。

- 冯·诺依曼的老毛病：正是 3.1 节的结构冒险——取指和取数抢同一条总线；
- 哈佛的解法：指令、数据各一条路，**可以同时走**；
- **Cortex-M3 的三条内部总线**（注意：这是内核到存储的通路，与 AHB/APB 总线分级不是一回事，后者见 04 篇）：

```text
I-Code 总线：取指令专用（代码区 0x00000000~0x1FFFFFFF，Flash 就映射在这里）
D-Code 总线：对同一地址区的数据访问（如读常量表）
System 总线：SRAM、外设寄存器等其余区域
```

- 嵌入式兑现：STM32 的 Flash 挂在 I-Code 一侧，CPU 取指的同时，数据照常走 D-Code/System 总线——流水线不至于因为"读一次数据"就断流，3.1 的结构冒险被硬件布局直接拆掉了大半。

**自检一个问题**：查表用的常量表也放在 Flash（Code 区），CPU 读它走哪条总线？——走 **D-Code 总线**（数据访问），而不是取指的 I-Code 总线。同一片 Flash，指令和数据两条路进来——这就是哈佛结构在你每天代码里的日常。

## 章节小结

- CPU 执行一条指令 = 取指→译码→执行三步；PC 是"下一页书签"
- 流水线让三步重叠：单条延迟仍是 3 周期，但吞吐量≈1 条/周期，N 条总周期 = 3+(N−1)
- 72MHz 满载 ≈ 7200 万条指令/秒的量级，是理想值，冒险会拉低
- 三种冒险：结构（抢部件→哈佛双总线解）、数据（依赖→前递解）、控制（跳转→流水线冲刷）
- Cortex-M3 三级流水 → 中断响应典型 12 周期（含自动压栈 8 寄存器）
- 循环展开 = 少跳转 = 少冲刷，代价是代码变大
- 哈佛结构：I-Code/D-Code/System 三总线，取指与取数并行

## 常见问题 FAQ

**Q1：流水线之后，一条指令到底花几个周期？**
A：分口径——**延迟**（单条从取指到执行完）仍是 3 周期；**吞吐量**（平均完工速度）≈ 1 周期一条。"M3 每周期跑 1 条指令"说的都是后者。

**Q2：中断响应 12 周期是保证值吗？**
A：是"零等待存储器、无更高优先级中断"下的**典型值**。Flash 有等待周期、总线被 DMA 占用、正在尾链处理时都会更长——所以硬实时系统要给中断启动时间留余量，且 ISR 前几条指令天然有抖动。

**Q3：既然跳转有代价，是不是代码里越少 if/for 越好？**
A：不必走极端。M3 流水线浅、冲刷代价小，正常写代码影响有限；只在循环内核（每秒跑几十万圈的热路径）才值得展开、查表、消除分支。

**Q4：Cortex-M4 也是三级流水吗？**
A：M4 是 4 级流水（把"访存"独立成一级），流水线更深才能撑更高主频，但原理与本篇完全相通，多一级的代价是分支冲刷更深【详细差异查对应 TRM】。

**Q5：哈佛结构下，运行中的代码能改写 Flash 里的指令吗？**
A：能访问（自编程/OTA 场景走 System 总线操作 Flash 外设），但要格外小心——取指路径上的流水线里还有旧指令在飞，改写后要保证跳转、冲刷时序正确，这是 IAP/Bootloader 的经典坑点。
