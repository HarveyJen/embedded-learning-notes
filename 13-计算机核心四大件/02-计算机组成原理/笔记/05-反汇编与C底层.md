# 05 · 反汇编与 C 底层

> 定位：组成原理详解第四篇，回答"我的 C 代码到底变成了什么"。是导读篇 2.1 节"函数调用约定"的展开——反汇编是把前面三篇（流水线/存储/总线）和你的 C 代码对上号的显微镜，HardFault 定位与体积优化都靠它。

**先说人话**：本篇讲怎么把芯片里的二进制机器码**翻译回汇编**，让你亲眼看到"编译器到底把你的 C 写成了什么"。为什么嵌入式工程师需要它？因为四件事绕不开它：**验证 volatile 有没有生效、证明 const 真的进了 Flash、数清位操作是几条指令、HardFault 时找到出错那一行**——前两个是"听说"，反汇编给出铁证。

## 1. 反汇编是什么：打开编译器的黑盒

**这是什么**：机器码是 CPU 的"母语"（一串二进制数），汇编是它的助记写法。**反汇编（Disassembly）**= 从二进制反推出对应的汇编。类比：拿到一份摩斯电报，反汇编就是把"滴滴答答"翻回字母——内容一个字没变，只是翻译回人能读的形式。

- 编译的完整链路：C 源码 → 编译器翻译 → 汇编 → 汇编器变成机器码（进 .o/.elf）。**反汇编是往回走一步**：从机器码回到汇编——但回不到你原始的 C（变量名、注释已丢，只能靠猜和源码对照）；
- 为什么嵌入式必会：调试器单步实际走的、HardFault 现场停的、启动文件里手写的，全是汇编层——这一层看不懂，调试永远隔一层毛玻璃；
- 与前几篇的衔接：汇编里每条指令就是 02 篇流水线上的一个"货"，访存指令就是 03 篇存储层次的"顾客"，访外设地址就是 04 篇总线上的传输。

## 2. 生成反汇编的命令

**这是什么**：两条路——GCC 工具链命令行（通吃所有平台和 CI）与 Keil 图形窗口（点两下就出）。下面命令都在 Windows 的命令行里执行（arm-none-eabi 工具链装好后可用）。

```bash
# 路线一：直接让编译器输出汇编文本（不汇编成机器码）—— 看"编译器的翻译稿"
# -mcpu=cortex-m3：按 M3 的指令集生成；-mthumb：Thumb 指令模式；-O2：优化级别
arm-none-eabi-gcc -mcpu=cortex-m3 -mthumb -O2 -S main.c -o main.s

# 路线二：从编译好的 ELF 反汇编 —— 看"芯片实际存的货"
arm-none-eabi-objdump -d main.elf > main.dis

# 常用增强参数
arm-none-eabi-objdump -d -S main.elf > main.dis   # -S：把 C 源码交错插进汇编，逐行对照
arm-none-eabi-objdump -t main.elf > main.sym      # -t：符号表——每个函数/变量落在哪个段、哪个地址
arm-none-eabi-size main.elf                       # 各段大小：text(代码+常量)/data/bss，看 Flash 占用
```

Keil（图形化，最快上手）：

```text
① 点 Start/Stop Debug Session 进入调试
② 菜单 View → Disassembly Window——源码与汇编对照显示
③ 选中某行 C 代码，窗口同步高亮它对应的汇编地址；配合寄存器窗口单步看 R0~R3 变化
④ 想看"某地址处是什么指令"：在反汇编窗口地址栏直接输入地址（HardFault 定位就这么用）
```

**怎么看反汇编**：每行格式一般是"地址 + 机器码 + 汇编"，例如 `08001234 1840  adds r0, r0, r1`——先只读汇编列，地址列用来定位，机器码列用来体会"汇编和二进制一一对应"。

## 3. 一个函数的栈帧：压参 → 返回地址 → 局部变量

**这是什么**：**栈帧（Stack Frame）**= 一个函数在栈上占的"临时工作台"——放局部变量、保存要用的寄存器旧值。函数开工先搭台（序言 prologue），收工拆台（尾声 epilogue），栈台随调用一层层叠。类比：食堂餐盘架——每打一份菜压一个盘子（每次调用压一层帧），吃完撤盘（返回弹帧），永远从最上面那份动手。

看这个函数（故意写个局部变量，好让栈上有东西）：

```c
int add3(int a, int b, int c) {
    int s = a + b + c;
    return s;
}
// 调用方：int r = add3(1, 2, 3);
```

-O2 下它被优化到只剩两条算术（参数根本没碰栈）：

```text
add3:
    adds r0, r0, r1     ; r0 = r0 + r1（a+b）——参数已经按约定在 r0/r1/r2
    adds r0, r0, r2     ; r0 = r0 + r2（+c）——返回值约定放 r0
    bx   lr             ; 跳回调用方（lr 里存着返回地址）
```

-O0 下的典型栈帧布局（"老实人模式"，逐条落栈；布局为示意，实际随工具链略有差异）：

```text
高地址
┌────────────────────┐
│ 调用方的栈帧         │
├────────────────────┤ ← 进入函数时的 sp
│ 返回地址（lr 压入）   │ ← push {lr}：回来要用的"书签"
├────────────────────┤
│ 局部变量 s           │ ← sp 再往下让出 4 字节
├────────────────────┤
│ 被保存的寄存器旧值    │ ← 若函数用了 r4~r11 才压
├────────────────────┤ ← 当前 sp
└────────────────────┘
低地址          栈向下生长：地址越用越低
```

- 白话流程：调用 `add3(1,2,3)` → 1/2/3 按约定送进 r0/r1/r2（**不压栈**）→ `bl add3` 跳转的同时把返回地址写进 lr → add3 需要栈才 push（-O2 这里全程没碰栈）→ 收工 `bx lr` 返回；
- 记住这个图，HardFault 时看栈、写汇编启动文件、读库函数源码，全靠它打底。

## 4. 函数调用约定：参数走 R0~R3

**这是什么**：**调用约定**（ARM 上叫 AAPCS）= 所有编译器共同遵守的"交接暗号"——参数放哪、返回值放哪、哪些寄存器谁负责保存。没有暗号，你编译的函数就没法调用别人编译的库。类比：流水线交接规程——上一道工序的货固定放在左手第二个筐，下一道工序闭眼去拿，不用喊话。

```text
参数：前 4 个走 R0~R3，第 5 个起压栈
返回值：R0（64 位返回值用 R0+R1 两个寄存器）
R0~R3、R12：调用方自保（caller-saved）——被调函数随便用，用前不救
R4~R11：被调方自保（callee-saved）——想用先压栈保存，收工前必须还原
LR(R14)：返回地址；SP(R13)：栈指针；PC(R15)：程序计数器
```

- **代入算例**：`f(1, 2, 3, 4, 5)` → 1/2/3/4 进 R0~R3，**第 5 个参数 5 由调用方压到栈上**——反汇编里若看到往 sp 指向的栈写参数的指令，就是"参数溢出进栈"；
- 为什么要懂：调试器的调用栈回溯、启动文件的汇编、C 与汇编混合编程的接口、HardFault 现场的 LR/栈分析——全部建立在这套暗号上（HardFault 实战见 [07-STM32 调试实战](../../../07-STM32/笔记/07-调试实战.md)）。

## 5. 三个经典落地：用反汇编验证 C 的说法

### 5.1 volatile：有没有它，编译器判若两人

```c
// 轮询一个（示例用）寄存器地址；真实寄存器映射见 07-STM32 寄存器篇
#define STAT (*(volatile uint32_t *)0x40021000U)   // 版本 A：volatile
// #define STAT (*(uint32_t *)0x40021000U)          // 版本 B：去掉 volatile
while (STAT & 0x01) { }
```

-O2 且**无 volatile**（被优化掉）：

```text
    ldr  r0, =0x40021000
    ldr  r0, [r0]        ; 只读了一次！
    tst  r0, #1
    beq  skip
loop:
    b    loop            ; 之后原地死循环——编译器认为"值不会自己变"，不再读
skip:
```

-O2 且**有 volatile**：

```text
loop:
    ldr  r0, =0x40021000
    ldr  r1, [r0]        ; 每一圈都真的发一次读——volatile 的禁令生效
    tst  r1, #1
    bne  loop
```

（汇编为示意，指令顺序随工具链版本可能不同，**看关键差异：循环里读了几次内存**。）C 语义侧完整解释见 [01-C 09 预处理器与关键字专题](../../../01-C语言基础/笔记/09-预处理器与关键字专题.md)。

### 5.2 const 数据进 Flash 的证据

```c
const uint32_t table[4] = {1, 2, 3, 4};   // 只读查表
uint32_t var = 5;                          // 对照组：普通全局变量
```

用 `arm-none-eabi-objdump -t`（符号表）看两个符号的落点：`table` 在 `.rodata`（只读数据段），链接后地址在 **0x08xxxxxx**（Flash 区）；`var` 在 `.data`，地址在 **0x20xxxxxx**（SRAM 区）。反汇编里访问 table 的取数指令，目标地址也落在 0x08 开头——**"const 省 RAM、进 Flash"从此不是背诵，是证据**（地址分段原理见 04 篇总线/内存映射）。

### 5.3 位操作 `|=` 到底是几条指令

```c
GPIOA_ODR |= (1u << 5);    // 置位第 5 位（GPIOA_ODR 地址 0x4001080C，同 01-C 06 篇）
```

反汇编（ARM 上是**三条**；x86 的 `or [mem], imm` 才是一条）：

```text
    ldr  r0, =0x4001080C    ; 取寄存器地址
    ldr  r1, [r0]           ; ① 读旧值
    orr  r1, r1, #0x20      ; ② 或上第 5 位
    str  r1, [r0]           ; ③ 写回去 —— 读-改-写三连
```

由此明白两件事：**ARM 上对内存做位操作天然是三条指令**（没有"直接改内存某位"的单指令）；**它不是原子的**——三条指令之间若被中断插进来改了同一寄存器，写回时就把人家的改动覆盖了。所以"中断与主程序共享变量要注意原子性"（volatile 只保可见性不保原子，01-C 09 有结论）。

## 6. 嵌入式用途：HardFault 定位与代码瘦身

**这是什么**：反汇编在实战里的两大高频用途——查案（HardFault）与减肥（体积）。

- **HardFault 找出错指令**：异常触发时硬件把出错前的 PC、LR 等压进异常栈帧。调试器里取出压栈的 PC → **到反汇编窗口输入该地址** → 亲眼看到"撞墙那一刻 CPU 正在执行哪条指令、访问哪个地址"；再配合故障状态寄存器判断原因（空指针/未对齐/栈溢出）。完整勘查流程见 [07-STM32 调试实战](../../../07-STM32/笔记/07-调试实战.md)；
- **代码体积优化**：用 `-Os` 替换 `-O2` 重新生成反汇编，对比 text 段大小（`arm-none-eabi-size`）；在反汇编里找"同一个函数体被复制了好几份"（内联展开的代价）；Flash 只有几十 KB 的 MCU 项目里，这是每周都可能做的日常。

## 章节小结

- 反汇编 = 机器码 → 汇编的回译，看懂"编译器到底干了什么"的显微镜
- GCC 两条路：`-S` 出汇编文本；`objdump -d` 反汇编 ELF（-S 交错源码，-t 看符号表，size 看段大小）
- Keil 里 View → Disassembly Window，源码与汇编对照，可直接输地址定位
- 栈帧 = 函数的临时工作台：返回地址、局部变量、保存的寄存器，随调用层层叠
- 调用约定：参数 R0~R3（第 5 个起压栈）、返回值 R0、R4~R11 被调方自保
- volatile 对比实验：无它循环里只读一次内存，有它每圈真读——铁证到手
- const 表落 .rodata/0x08 区，普通变量落 .data/0x20 区——省 RAM 有了证据
- `|=` 是"读-改-写"三条指令、非原子；HardFault 拿压栈 PC 去反汇编窗口定位

## 常见问题 FAQ

**Q1：反汇编出来的汇编，和编译器 -S 生成的汇编一样吗？**
A：可能不完全一样。-S 是"编译器的翻译稿"，反汇编是"从最终机器码回读"——链接器、编译器后端可能做了再调整。分析最终行为以反汇编为准，理解编译意图两边都看。

**Q2：-O0 和 -O2 反汇编差很多，该看哪个？**
A：各看一次。-O0 是"老实人模式"，逐句对应你的 C，适合学栈帧和调用约定；-O2 是"实战模式"，看懂它才知道发布代码的真实行为和优化思路（比如变量全进寄存器、指令重排）。

**Q3：`|=` 三条指令会导致什么真实 bug？**
A：典型场景：主循环 `reg |= BIT_A` 执行到"读旧值"和"写回"之间被中断打断，ISR 里改了同一寄存器的 BIT_B 并返回——主循环写回时用旧值覆盖，BIT_B 丢了。对策：临界区关中断、或改用有原子置位/清零寄存器的写法（如 STM32 的 BSRR 类寄存器）【寄存器名查你所用型号参考手册】。

**Q4：为什么第 5 个参数要压栈，前 4 个不用？**
A：AAPCS 的设计取舍：寄存器传参快（流水线不用等访存），但寄存器只有 16 个，划 4 个给参数是"速度与通用性"的平衡——够覆盖绝大多数函数，超过才动用栈（呼应 02 篇：访存比寄存器慢一个量级）。

**Q5：反汇编能还原回 C 吗？**
A：不能完全还原。变量名、注释、部分控制结构已丢，只能推断"大概是什么 C 写法"。这也是为什么发布固件不等于公开源码——但专业逆向者仍能从汇编读懂逻辑，安全上不要迷信"编译过的代码没人看得懂"。
