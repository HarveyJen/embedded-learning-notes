# 03 · Cache 与存储层次

> 定位：组成原理详解第二篇，回答"数据到底存在哪、CPU 取一次数据要等多久"。是导读篇 2.2 节的展开——存储层次是嵌入式的命脉：Flash 等待周期、外设为什么不缓存、DMA 一致性，全部从这里长出来。

**先说人话**：本篇讲一件工程世界的根本矛盾——**又快、又大、又便宜的存储器不存在**，所以只能金字塔分层，再用 Cache（高速缓存）把常用数据放在最顶层。为什么嵌入式工程师需要它？因为你要回答三个日常问题：**为什么 STM32 高主频要插 Flash 等待周期、为什么外设区绝不能缓存、为什么 Cache+DMA 会读到旧数据**——最后一个是换平台（M7/H7）时最容易翻车的坑。

## 1. 存储金字塔：快、大、便宜，三者不可兼得

**这是什么**：存储器有个铁律——速度越快→容量越小→单价越贵。工程师的答案是金字塔分层：顶层快而小，底层大而慢，常用的数据尽量放上层。类比：**书桌（寄存器）→ 书架（Cache）→ 书房书柜（内存）→ 图书馆（Flash/SD 卡）**——随手要用的摊在桌上，暂时不用的塞远点，反正贵的是"近处的面积"。

数量级对比表（PC 常见值为参考，MCU 是缩小版）：

| 层 | 速度量级 | 容量量级 | 芯片上的对应物 |
|----|---------|---------|---------------|
| 寄存器 | <1ns（与 CPU 同频） | 几十个 × 4B | Cortex-M 的 R0~R15 |
| Cache | 1~几 ns | KB~MB | M3 无；M7 起可选（见第 7 节） |
| SRAM | 几~十几 ns | MCU 几十 KB | STM32F103 的 20KB SRAM |
| DRAM | ~100ns | PC 的 GB 级 | 电脑内存条 |
| NOR Flash | 读较快、写慢 | MCU 几百 KB | F103 内置 Flash |
| NAND/SD | 最慢最便宜 | GB 级 | SD 卡、EMMC |

**代入算例感受差距**：72MHz 时 1 个周期 ≈ 1/72MHz ≈ **13.9ns**（主频怎么来的见 [07-STM32 时钟树](../../../07-STM32/笔记/01-工程建立与时钟树.md)）。那么——SRAM 一次 ≈ 1 个周期；DRAM 一次 ≈ 7 个周期；SD 卡一次毫秒级 ≈ **几万到几十万个周期**。顶层和底层差 5~6 个数量级，**没有分层，CPU 九成时间在干等**。

**为什么造不出"又快又大"的一块存储器**：快 = 电路短小直接（存储单元紧贴 CPU，触发器电路复杂但一步到位）；大 = 单元密集廉价排布（容量优先，速度靠边）。两者在电路结构和成本上天生互斥——好比"随身小抄"（快、少）和"图书馆"（全、远）没法合并成一样东西。**分层不是妥协，是唯一可行解**。

## 2. 局部性原理：Cache 敢存在的底气

**这是什么**：程序访存不是乱来的，只有两个规律——**时间局部性**：刚用过的数据马上还会用；**空间局部性**：用了这个地址，马上会碰它隔壁的地址。类比：翻书时刚查过的词还会再查（时间），而且你会连着读同一页而不是隔一页读一页（空间）。Cache 的一切前提就是这两条——若程序真的随机访问，Cache 就是白花钱。

```c
uint32_t buf[1000];
uint32_t sum = 0;

for (int i = 0; i < 1000; i++) {
    sum += buf[i];    // 空间局部性：访问 buf[i] 后接着访问 buf[i+1]，地址挨着
}

for (int j = 0; j < 1000; j++) {
    sum += j;         // 时间局部性：j 和 sum 每一圈都被重复使用
}
```

- 时间局部性的兑现：循环变量、累加器干脆常驻寄存器——编译器 -O2 干的第一件事就是它；
- 空间局部性的兑现：Cache 每次搬数据不只搬 1 个字节，而是搬**一整行**，把邻居捎带回来——下次访问大概率"白捡"。

**反例感受一下"局部性差"**：

```c
// 顺路访问：数组顺序扫，每次搬一整行能白捡 15 个邻居（64B/行 ÷ 4B/元素）
uint32_t a[100], b[100];
for (int i = 0; i < 100; i++) sum += a[i] * b[i];

// 乱跳访问：链表逐跳 node = node->next;
// 每个节点在内存里随机散布——整行 64 字节只用得上 4 字节，Cache 白搬
```

链表遍历是"局部性最差"的经典结构——数据结构选型时，这就是数组与链表性能差异的**硬件根源**（数组只在 01-C 05 篇的层面比较过语法，这里才是性能底牌）。

## 3. Cache 怎么干活：行、命中、未命中、映射

**这是什么**：Cache 是 CPU 和内存之间的"小而快的书架"，以**行（Line）**为单位搬运数据（PC 常见 64B/行，Cortex-M7 的 Cache 行是 32B）。**命中**=书架上有，直接抽出来用；**未命中**=书架上没有，去大仓库搬一整行回来再读。

- **命中/未命中的代价白话**：命中 = 从书架抽书（1 个周期量级）；未命中 = 跑一趟图书馆搬回一整排书（几十~上百周期）——所以性能的关键是"少跑图书馆"；
- **映射方式**（内存块允许放进书架哪一格，三种由死到活）：
  - **直接映射**：每个内存块只能进固定一格（像工位按工号分配）——查得快，但两块会"轮流踢对方下岗"（冲突）；
  - **组相联**：块先进固定"分区"，分区里格子随便停（像分区停车场：区号固定、区内随便停）——撞车概率大降，现代 CPU 主流；
  - **全相联**：随便停——最灵活但每格都要比对，查找太贵，只用在 TLB 这类小部件；
- **命中率算例**（代入数字，感受 5% 的杀伤力）：

```text
命中率 95%，命中 1 周期，未命中补 100 周期
平均访问耗时 = 0.95×1 + 0.05×100 = 0.95 + 5 = 5.95 周期
结论：比"全走内存"的 100 周期快约 17 倍；
     但只要命中率从 95% 掉到 90%，平均耗时立刻翻倍到 10.9 周期
     —— 3~5% 的未命中率就毁掉大半性能，这就是 Cache 调优为什么抠细节
```

**顺带一个词——写策略**：读讲完了，CPU 往 Cache **写**时怎么办？**写通（Write-Through）**：立刻同步写进内存——简单、两份永远一致，但每次写都占总线；**写回（Write-Back）**：先只改 Cache、给这行记个"脏"标记，等它被踢出时才写回内存——快，但会留下"两份副本不一致"的窗口（第 6 节 DMA 问题的伏笔，先记下）。

## 4. 嵌入式三连问：RAM 快 Flash 慢、等待周期、代码搬 RAM

**这是什么**：把金字塔套到 STM32 上——CPU 的数据放 SRAM（RAM 的一种，快）、指令从内置 Flash 取（大但慢）。快慢差决定了两个工程动作：等一等（等待周期）、搬一搬（代码进 RAM）。

- **为什么 RAM 快、Flash 慢**：SRAM 用触发器存位，通电就稳，寻址直接、一个周期出数；Flash 用浮栅上的电荷存位（所以掉电不丢），读时要靠感应电路慢慢"称电荷"，写之前还要先整块擦除——**可靠性是拿速度换的**；
- **为什么 STM32 读 Flash 要插等待周期**：F103 的 Flash 取指速度跟不上 72MHz 的 CPU。手册规定：SYSCLK ≤24MHz 用 0 等待、≤48MHz 用 1 等待、≤72MHz 用 2 等待。**代入算例**：72MHz 时每个取指周期要插 2 个空转，本来 1 周期能拿到的指令现在 3 周期才到手——这就是 F1 高主频跑分打折的主因。芯片配了**预取缓冲**（提前排队取下一条）缓解，但治标不治本。

**预取缓冲怎么缓解**（固定硬件版的"赌空间局部性"）：

```text
CPU 正在执行第 N 条指令 → 预取缓冲已提前把第 N+1、N+2 条从 Flash 排队取好
→ 轮到它们时零等待直接喂给流水线（02 篇的取指级不断粮）
→ 但一旦跳转，排队的全白取——正好呼应 02 篇"跳转代价"
```
- **为什么要把函数拷到 RAM 跑**：SRAM 零等待，把热函数（每秒跑几万圈的那种）搬进 RAM 能省等待周期——GCC 手法是 `__attribute__((section(".ramfunc")))` 把函数放进自定义段，再靠链接脚本把这个段指到 SRAM；另一个**绕不开**的场景是 IAP/OTA：改写 Flash 自己的时代码必须在 RAM 里跑——一边烧 Flash 一边从 Flash 取指，是做不到的。

## 5. volatile 与 MMIO：外设区为什么不能缓存

**这是什么**：**MMIO**（Memory Mapped I/O，内存映射 I/O）= 把外设寄存器做成"特殊地址上的内存"，读写这些地址就是操作硬件。这片区域**绝不能进 Cache**——Cache 的逻辑是"值没变就不重读"，而外设寄存器的值会**自己变**（硬件在改），甚至**读这个动作本身就是事件**。

两个经典翻车现场（C 语法侧的完整机制见 [01-C 09 预处理器与关键字专题](../../../01-C语言基础/笔记/09-预处理器与关键字专题.md)）：

```c
// 翻车一：等标志位死循环
while ((UART->SR & RXNE) == 0) { }   // 等接收标志
// 若状态寄存器被缓存：第一次读到"空"之后，缓存认定"这值没变"
// → CPU 从此不再真的去读外设 → 死循环（硬件明明已收到数据）

// 翻车二：读 FIFO 丢字节
data = UART->DR;    // 读数据寄存器 = 取走 FIFO 里的一个字节
// 若这次读被缓存"代替"了：字节被"幽灵"读走，真数据没了
```

- 所以芯片设计上，外设区地址映射（0x40000000 起）被划为**非缓存区**——硬件层先堵死；
- C 代码还要给寄存器访问加 `volatile`——编译器层再堵一条（不许把读写优化掉）。两层保险各管一个"想偷懒的部件"：Cache 管硬件缓存，volatile 管编译器缓存。寄存器地址怎么映射成 C 变量，实操见 [07-STM32 寄存器方式直操外设](../../../07-STM32/笔记/09-寄存器方式直操外设.md)。

## 6. Cache 与 DMA 的一致性：CPU 读到旧数据怎么办

**这是什么**：**一致性（Coherency）**问题 = 同一份数据在 Cache 和内存里出现两个版本。**DMA**（Direct Memory Access，直接存储器访问）是个不经过 CPU 的搬运工，它直接写内存——**Cache 完全不知情**，CPU 再读就可能拿到旧数据。这是嵌入式里 Cache 知识最值钱的地方。

时间线还原一次事故：

```text
① CPU 第一次读 buf[0]：未命中 → 从 SRAM 搬进 Cache（此刻内存里 buf[0] = 0）
② DMA 收完一包数据：直接写 SRAM，buf[0] = 100（Cache 里仍是旧值 0，不知情）
③ CPU 再读 buf[0]：命中 Cache！读到 0 ← 旧数据，校验失败，事故现场
```

解法（按成本从低到高）：

- DMA 写完后，CPU **作废（Invalidate）**对应 Cache 行——强制下次重读内存；CMSIS 提供 `SCB_InvalidateDCache_by_Addr()` 这类函数【具体 API 名以你所用 CMSIS 版本为准】；
- 反方向的坑同理：CPU 写过的数据要 **Clean（刷回内存）**，DMA 才读得到新值；
- 更省心的办法：用 MPU（内存保护单元）把 DMA 缓冲区划成**非缓存区**——从根上绕开两份副本。

**M3/M4 板子的你先别慌**：Cortex-M3/M4 内核没有 Cache（靠 Flash 预取缓冲这类固定硬件缓解），所以 F103 上 DMA 天然一致，从没听说过"缓存不一致"；从 **Cortex-M7**（STM32F7/H7）起内核带可选 I/D Cache，一致性才真正上岗。但"CPU 可能读到旧数据"的意识要从现在建立——将来把 F1 代码平移到 F7/H7 时，这是最高危的坑之一。

**Clean / Invalidate 记忆法**（两个方向别搞反）：

```text
Clean（清洗）     = 把 Cache 里的"新"值刷回内存     → CPU 写完、DMA 要读之前做
Invalidate（作废）= 把 Cache 里的"旧"值扔掉不用     → DMA 写完内存、CPU 要读之前做
口诀：DMA 写完内存 → Invalidate（防 CPU 读旧）；CPU 写完要给 DMA 读 → Clean（防 DMA 读旧）
```

## 7. 对照表：PC 有 Cache，我学局部性还有用吗

怎么读这张表：左列处理器、右列 Cache 实情——重点看清"你手上的 M3/M4 板子其实没有传统 Cache"。

| 处理器 | Cache 实情 |
|--------|-----------|
| PC（x86/x64） | L1/L2/L3 齐全，Cache 知识直接决定性能 |
| Cortex-M3 | 无 Cache（Flash 预取缓冲缓解慢 Flash） |
| Cortex-M4 | 无传统 Cache（部分型号配加速器/预取手段） |
| Cortex-M7 | 可选 I-Cache / D-Cache（STM32F7/H7 上可见） |

顺手把 Cortex-M3 的 4GB 地址分区挂上号（只列最常用四区，完整映射见芯片手册）：

| 地址范围 | 分区 | 放什么 |
|---------|------|--------|
| 0x00000000~0x1FFFFFFF | Code 区 | Flash（向量表、代码、const 常量） |
| 0x20000000~0x3FFFFFFF | SRAM 区 | 变量、栈、堆 |
| 0x40000000~0x5FFFFFFF | 外设区 | 所有外设寄存器（MMIO，非缓存） |
| 0xE0000000~0xFFFFFFFF | 私有区 | NVIC、SysTick 等内核外设 |

外设区整段被划为非缓存——第 5 节的结论在**地址映射层面就定死了**，不是 C 代码写得好不好的问题。

**局部性照样有用，三个理由**：

1. **编译器替你用局部性**：-O2 的循环优化、热变量进寄存器、指令重排，全是局部性的自动化应用——不懂局部性，你就看不懂编译器在优化什么；
2. **硬件预取也在赌局部性**：Flash 预取缓冲、总线流水，本质都是"赌你接下来按顺序取指"——空间局部性的硬件版（呼应本目录 02 篇的取指流水）；
3. **代码编排有实测收益**：热函数集中摆放、查表数据连续排布、少跳来跳去——在 M3 上提升不大但方向正确，到 M7/PC 上会成倍放大。

## 章节小结

- 存储金字塔：越快越贵越小——寄存器→Cache→SRAM→Flash/SD，量级差 5~6 倍不止
- 72MHz 时 1 周期 ≈ 13.9ns；DRAM 一次 ≈ 7 周期，SD 卡 ≈ 几万周期
- 局部性（时间/空间）是 Cache 成立的前提，也是编译器优化的依据
- Cache 以行（Line）为单位搬运；映射三式：直接映射/组相联/全相联
- 算例：95% 命中率下平均 5.95 周期——命中率掉 5%，性能近半
- F103 @72MHz 需 2 个 Flash 等待周期；热函数可搬 RAM（ramfunc/OTA 必须）
- MMIO 外设区：硬件划非缓存 + 代码加 volatile，双保险缺一不可
- Cache+DMA 一致性：M3 无 Cache 无此坑，M7 起要 Invalidate/Clean 或划非缓存区

## 常见问题 FAQ

**Q1：我的 M3 没有 Cache，是不是这篇白学了？**
A：没有 Cache，但存储层次还在——寄存器/SRAM/Flash 的速度差真实存在，等待周期、预取缓冲、ramfunc 都是你现在就用的知识；局部性思维决定编译器优化和代码编排；将来上 M7/H7 时一致性知识直接变现。

**Q2：volatile 已经加了，为什么外设区还要硬件不缓存？**
A：两者防的不是同一个偷懒者。volatile 防编译器把读写优化掉；Cache 是硬件，volatile 管不了它——就算编译器老老实实生成读指令，硬件也可能用缓存里的旧值应付。所以芯片直接把外设区划成非缓存，C 代码再加 volatile，双保险。

**Q3：Flash 写慢我能理解，为什么读也慢？**
A：Flash 存数据靠浮栅里的电荷，读取时要用感应放大器分辨"有电/没电"，比 SRAM 触发器直接翻转慢一拍；而且为了可靠性，读取路径上还有电压建立等固定开销——所以高主频下要插等待周期。

**Q4：DMA 一致性在 F103 上真不用管吗？**
A：内核没有 Cache，CPU 读的永远是 SRAM 本体，DMA 写的也是 SRAM 本体，天然一致。但缓冲区若被别的手段缓存（某些总线的写缓冲等）仍需留意【具体以型号手册为准】；更重要的是为将来上 M7 建立正确习惯。

**Q5：命中率 95% 和 99% 差别很大吗？**
A：代入第 3 节公式（命中 1 周期、未命中 100 周期）：95% → 5.95 周期，99% → 1.99 周期，**差 3 倍**。Cache 世界的残酷之处：性能由那少数几次未命中决定，所以调优盯的全是"漏网之鱼"。
