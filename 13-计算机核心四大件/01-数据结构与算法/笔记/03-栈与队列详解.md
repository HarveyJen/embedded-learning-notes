# 03 · 栈与队列详解

> 定位：两种"只在固定端操作"的受限线性结构。栈撑起函数调用与中断现场；队列（环形缓冲区）是嵌入式串口/DMA 数据流的标配，本篇重点是环形缓冲区的完整 C 实现。

**先说人话**：本篇讲栈和队列。**栈**像**摞盘子**——后放的在上，取也只能从最上取（后进先出）；**队列**像**食堂排队**——先来的先打饭（先进先出）。嵌入式工程师离不开它们：每次函数调用、每次中断进出的"现场保存"都是栈在工作；而串口收数据、DMA 搬运、日志缓冲，标配是"环形缓冲区"（本质是数组实现的队列）。学完本篇你会明白：为什么栈要估大小，为什么收数据要用环形而不用普通数组。

## 1. 栈：后进先出（LIFO）

**这是什么**：只允许从一端（栈顶）进出的线性结构。LIFO = Last In First Out，白话："最后进去的，最先出来"。类比：摞盘子——洗好的盘子压在最上面，取也是先取最上面；最先洗完的盘子反而最后被取走。

三个术语先过一遍：
- **入栈 push**：放一个盘子到顶上；
- **出栈 pop**：从顶上拿走一个；
- **栈顶 top**：当前最上面那个位置（游标）。

只进不出无限压盘 → 盘塔倒塌，对应程序世界的"栈溢出"（第 3 节细讲）。

## 2. 栈的两种实现

**这是什么**：数组或链表都能实现栈。选型一句话：嵌入式容量可预估时优先**数组栈**（静态、快、防碎片）；数量完全不可预估才考虑链表栈。

**数组栈**（重点掌握）：

```c
#define STACK_MAX 32

typedef struct {
    int buf[STACK_MAX];   // 存数据的静态数组
    int top;              // 栈顶游标：约定指向"下一个空位"
} stack_t;

void stack_init(stack_t *s) { s->top = 0; }           // 空栈：top=0

int stack_push(stack_t *s, int v) {
    if (s->top >= STACK_MAX) return -1;   // 满：嵌入式必须处理，不能假设内存无限
    s->buf[s->top] = v;
    s->top++;
    return 0;
}

int stack_pop(stack_t *s, int *out) {
    if (s->top == 0) return -1;           // 空：取前必判，取空是经典崩溃源
    s->top--;
    *out = s->buf[s->top];
    return 0;
}
```

运行逻辑：push 是"先放货再挪指针"，pop 是"先挪指针再取货"——顺序保证取到的永远是最新压入的。入栈出栈都只动 top 一个游标，都是 O(1)。

**链表栈**：头插 + 头删就是 push/pop，天然 O(1)，不整段贴代码——把 [02-链表详解](02-链表详解.md) 的 push_front 改名 push、删头节点改名 pop 即可。代价是每节点多一个 next 指针和 malloc 开销。

## 3. 函数调用栈与栈溢出（嵌入式必会）

**这是什么**：函数 A 调 B、B 调 C，C 返回后怎么知道回到 B 的哪一行？靠 CPU 的**硬件栈**：每次调用自动压入"返回地址 + 参数 + 局部变量"（合称**栈帧**），返回时弹出。类比：你边看主剧边追更番剧，追完番剧（函数返回）要回到"主剧第几分钟"——这个进度条就存在栈里。

```
main() 压栈帧 → funcA() 压栈帧 → funcB() 压栈帧 → ... → 逐层弹栈返回
```

栈溢出的三大来源：
1. **递归太深**：每层递归压一帧，递归 1 万层 = 压 1 万帧；
2. **局部变量太大**：函数里定义 `char buf[4096]`，一帧就吃 4KB；
3. **调用链深 + 库函数叠加**：printf 这类函数内部局部变量也可能吃掉几百字节，嵌在深层调用里容易被忽略。

嵌入式怎么估栈大小：
- 看**启动文件/链接脚本**：Keil 的 STM32 启动文件 `.s` 里 `Stack_Size EQU 0x400`（1KB，默认值，实测经常不够用）；
- 手算最深路径：沿"最深的那条调用链"把每层局部变量 + 返回地址 + 寄存器保存加起来，再乘 1.5~2 倍余量；
- 中断也要压栈：Cortex-M 内核进入中断时硬件自动压 8 个寄存器（32 字节），ISR 里再调函数消耗更多；
- RTOS 下**每个任务有独立栈**：用 `uxTaskGetStackHighWaterMark()` 查任务栈的"历史最小剩余"（高水位线），余量建议留 30% 以上；
- PC 上栈溢出大概率立刻崩溃；MCU 上更隐蔽——**栈底紧挨着其他变量，溢出只是悄悄改写邻居**，程序乱跳、HardFault，症状飘忽难查。所以只能事前留余量 + 高水位线测量。

## 4. 队列：先进先出（FIFO）与假溢出

**这是什么**：一端进（队尾 rear）、另一端出（队头 front）的线性结构。FIFO = First In First Out："先来的先走"。类比：食堂排队打饭——先排的先打，插队会被骂。

数组实现（普通版）：

```c
#define QUEUE_MAX 8

typedef struct {
    int buf[QUEUE_MAX];
    int front;    // 队头：下一个出队的位置
    int rear;     // 队尾：下一个入队的位置
} queue_t;

void q_init(queue_t *q) { q->front = 0; q->rear = 0; }
// 入队：buf[rear]=v; rear++   出队：v=buf[front]; front++
```

**假溢出问题**：出队几次后 front 前面的格子明明空着，rear 却一路加到数组尽头——"还有空位却报满"。画图看：

```
出队 3 次、入队 8 次后：
buf: [X][X][X][ ][ ][ ][ ][ ]   X=已取走腾空的格子
      front=3 ──▶ rear=8（越界！）前 3 格空着却不能再用
```

解法：让 rear 走到头**绕回开头**——这就是环形缓冲区。

## 5. 环形缓冲区完整 C 实现（嵌入式重中之重）

**这是什么**：首尾相接的数组。类比：**传送带上的格子**——传送带转圈，写的人（中断）往空格放货，读的人（主循环）从有货的格子取货，各管各的指针，永不撞车。它是嵌入式处理数据流（串口/ADC/DMA/日志）的**无条件首选**。

```c
#include <stdint.h>
#define RB_SIZE 8

typedef struct {
    uint8_t buf[RB_SIZE];   // 数据池
    volatile int head;      // 写指针：下一个要写的格子
    volatile int tail;      // 读指针：下一个要读的格子
} ringbuf_t;

void rb_init(ringbuf_t *r) {
    r->head = 0;
    r->tail = 0;
}

// 写 1 字节：中断/生产者调用
int rb_write(ringbuf_t *r, uint8_t b) {
    int next = (r->head + 1) % RB_SIZE;   // 模运算：走到尾就绕回头
    if (next == r->tail) return -1;       // 满（留空位法）：再写会追上读指针
    r->buf[r->head] = b;
    r->head = next;
    return 0;
}

// 读 1 字节：主循环/消费者调用
int rb_read(ringbuf_t *r, uint8_t *out) {
    if (r->tail == r->head) return -1;    // 空：读指针追上写指针
    *out = r->buf[r->tail];
    r->tail = (r->tail + 1) % RB_SIZE;
    return 0;
}
```

**模运算逐符号解释**：`(head + 1) % RB_SIZE`——head 加 1 后对 8 取余。head=7 时 (7+1)%8=0，绕回开头。代入走一遍（8 格）：

```
初始:       head=0 tail=0（空）
写 A..G:    存满 7 格，head=7 tail=0（留 1 格哨兵）
写 H:       next=(7+1)%8=0==tail → 返回 -1 拒绝（实际容量只有 7）
读 A,B,C:   tail=3（前 3 格腾空可复用）
再写 H:     next=(7+1)%8=0 != tail=3 → 写入 buf[7]，head=0
再写 I:     next=(0+1)%8=1 != tail=3 → 写入 buf[0]（A 的旧格被复用）
```

**满/空判断两种流派**：
1. **留空位法**（上面用的）：牺牲 1 格当哨兵，永远 `head==tail` 为空、`(head+1)%SIZE==tail` 为满。省变量、无歧义，代价是实际容量 = SIZE−1；
2. **计数法**：另设 `count` 变量，入队 count++、出队 count--。`count==0` 空、`count==SIZE` 满，容量足额。代价：多一个变量，且中断与主循环**同时改 count 有竞态风险**（count 需要关中断保护），单写者场景下 head/tail 各归一人管反而天然安全。

**为什么单生产者+单消费者时它是"无锁"的**：head 只有写者改、tail 只有读者改，两边各自独占一个变量，volatile 防止编译器把读写缓存到寄存器——读写互不干扰，不需要关中断。这是嵌入式面试高频考点。

**串口收发应用场景**（背下来，面试能直接讲）：

```c
ringbuf_t uart_rb;

// 串口中断：每收到 1 字节进一次
void USART1_IRQHandler(void) {
    uint8_t b = USART1->DR;              // 读数据寄存器（同时清标志）
    rb_write(&uart_rb, b);               // 只管往传送带放货，快进快出
}

// 主循环：慢慢消费
while (1) {
    uint8_t b;
    while (rb_read(&uart_rb, &b) == 0)   // 有货就取
        protocol_feed(b);                // 喂给协议解析（状态机）
    do_other_work();
}
```

设计意图：中断里只做"存"，把耗时的解析放主循环——**中断越短，丢数据概率越低**。缓冲满时 rb_write 返回 -1，丢弃新数据还是覆盖旧数据，按业务定。

## 6. 优先队列：RTOS 按优先级取任务

**这是什么**：出队顺序不看"谁先来"，看"谁优先级高"。类比：医院分诊台——不是先挂号先看，而是急诊优先。

- 裸机"大循环 + 标志位轮询"是**无优先级队列**：按代码书写顺序轮询，再急的事件也要排在后面；
- 改进版：按优先级从高到低扫描标志位（软件优先级调度雏形）；
- **RTOS 调度器就是优先队列的工业级实现**：FreeRTOS 给每个优先级维护一条就绪任务链表（链表见 [02-链表详解](02-链表详解.md) 第 6 节），调度时挑最高优先级链表里的任务运行，同优先级再按先来后到轮转；
- 入队时挂到"对应优先级的链"而不是简单追加 → 出队 O(1) 找到最高优先级任务。

任务间传数据则用消息队列（本质是静态数组 + 环形存取 + 阻塞唤醒），见 [08-FreeRTOS · 02-消息队列](../../../08-FreeRTOS/笔记/02-消息队列.md)。

## 章节小结

- 栈 LIFO 摞盘子：push/pop/top 只动一端；数组栈容量固定、嵌入式首选
- 函数调用 = 压栈帧（返回地址 + 局部变量）；递归深、局部变量大、printf 都会吃栈
- MCU 栈溢出不报错而是踩内存，用高水位线法（如 uxTaskGetStackHighWaterMark）留足余量
- 普通数组队列有假溢出；环形缓冲区用模运算绕回，是串口/DMA 数据流标配
- 环形缓冲满空两流派：留空位法（牺牲 1 格）与计数法（足额但 count 需防竞态）
- 单生产者单消费者时 head/tail 各归一人管，volatile 加持下天然无锁
- 优先队列 = 按优先级出队，RTOS 调度器（每优先级一条就绪链）就是它的实现

## 常见问题 FAQ

**Q：栈溢出为什么在 MCU 上特别难查？**
A：PC 上溢出大概率段错误立刻崩；MCU 上栈底紧挨着别的变量/堆，溢出只是**悄悄改写邻居**，程序可能照跑几小时才出诡异 bug。只能事前留余量 + 高水位线测量，不能事后靠崩溃定位。

**Q：环形缓冲区实际容量是多少？**
A：留空位法下 RB_SIZE=8 只能存 7 个——满格判断要 `(head+1)%SIZE==tail`，第 8 格是哨兵格。要足额容量换计数法，但注意 count 的并发保护。

**Q：中断里能直接调 rb_write 吗，要不要关中断？**
A：单写者（只有这一个中断写）+ 单读者（只有主循环读）时不用关：写者只动 head，读者只动 tail，互不踩。但**多个中断同时写同一个环形缓冲**就有竞态，必须关中断，或每个中断源各用一个缓冲。

**Q：为什么收串口数据不直接在中断里解析协议？**
A：中断原则"短平快"。解析一帧可能几十字节还要查表判错——放进中断会阻塞其他中断、容易丢字节。正确姿势：中断只 rb_write，主循环取出来慢慢解析。

**Q：栈用数组实现好还是链表实现好？**
A：容量可预估（嵌入式常态）→ 数组：静态分配、无 malloc、访问快；容量波动极大且接受动态分配 → 链表。嵌入式九成场景选数组。
