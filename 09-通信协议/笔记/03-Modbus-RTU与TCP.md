# 03 · Modbus RTU 与 TCP：工业第一协议

> 目标：吃透 Modbus 寄存器模型与帧格式，手写 RTU 主站/从站，理解"同一协议跑两种物理层"的设计。工业岗位面试必考。

## 1. Modbus 是什么（1979 年至今长盛不衰）

这是什么：一条 RS485 线上挂着十几台不同厂家的仪表，谁先说谁后说、问谁要什么数据、答错了怎么办——总得有个大家公认的规矩，这个规矩就是 Modbus。它解决的问题：**不同厂家的设备怎么用同一套黑话对话**。

**主从问答协议**：主站（PLC/网关/上位机）发问题，从站（传感器/仪表/变频器）答数据——**从站永不主动说话**。为什么活了 45 年：简单、开放免费、一颗 8 位机都能跑。

类比：**课堂点名**——老师（主站）点名提问，被点学生（从站）起立回答，其他学生闭麦；全班共享一条总线，秩序靠"一次只有一个人说话"。

**两种形态**：
| | Modbus RTU | Modbus TCP |
|---|-----------|-----------|
| 物理层 | RS485/RS232 | 以太网 |
| 帧尾校验 | CRC16 | 无（TCP 自带校验） |
| 帧头 | 从站地址 1B | MBAP 头 7B |
| 端口 | — | 502 |

**同一个应用层语义（功能码+寄存器），换皮跑两种网络**——01 篇分层思想的完美案例。

## 2. 四张表：Modbus 的数据模型（核心概念）

每个从站对外暴露四张"标准表格"，主站按表号+行号访问：

| 表 | 类型 | 读写 | 典型内容 |
|----|------|------|----------|
| **线圈** Coils | 1 位 | 读/写 | 继电器开关、启停命令 |
| **离散输入** Discrete Inputs | 1 位 | 只读 | 按键状态、限位开关 |
| **输入寄存器** Input Registers | 16 位 | 只读 | 温度采样值、电流表读数 |
| **保持寄存器** Holding Registers | 16 位 | 读/写 | 设定阈值、PID 参数、波特率配置 |

类比：**酒店四层楼**——一层开关房（线圈，可按可看）、二层告示板（离散输入，只能看）、三层展示柜（输入寄存器，只能看）、四层储物柜（保持寄存器，可存可取）。**记住：主站"写"只能写线圈和保持寄存器；"读"四张都能读。**

再给一个工程师视角的记法——按"位还是字 × 能不能写"划四象限：

```
          可写              只读
1位   线圈（继电器）     离散输入（按键）
16位  保持寄存器         输入寄存器
      （设定值）          （采样值）
```

**主站一次查房的时间线**（每步一句话：谁在做什么）：

```
T1  主站：点名"1 号从站，把你 0x0000 起的 2 个保持寄存器报上来"（发 0x03 请求帧）
T2  1 号从站：收到 → 查表取数 → 把 2 个 16 位值打包进应答帧
T3  其余从站：听到点的不是自己 → 全程装死
T4  主站：验 CRC → 拆数记账（存进自己的变量）；等 3.5 字符静默后开始下一轮
```

## 3. RTU 帧格式与常用功能码

### 3.1 帧结构

这是什么：Modbus RTU 的帧极简——**信封上只写"给谁"（地址）和"要干什么"（功能码）**，正文是参数，末尾贴封条（CRC）。没有帧头帧尾标记，靠"静默期"分帧（§4 讲）。

```
| 从站地址(1B) | 功能码(1B) | 数据(nB) | CRC16(2B，低字节在前！) |
```

### 3.2 高频功能码（够用 90% 场景）

这是什么：功能码就是"动词表"——读（0x01~0x04，四张表各一个码）、写单个（0x06）、写多个（0x10）。背下这六个，90% 的现场设备都能对话。

| 码 | 功能 | 数据段（请求） |
|----|------|----------------|
| 0x01 | 读线圈 | 起始地址(2B) + 数量(2B) |
| 0x02 | 读离散输入 | 同上 |
| 0x03 | **读保持寄存器** | 同上 |
| 0x04 | 读输入寄存器 | 同上 |
| 0x06 | **写单个保持寄存器** | 地址(2B) + 值(2B) |
| 0x10 | 写多个保持寄存器 | 地址(2B)+数量(2B)+字节数(1B)+数据 |

### 3.3 实例手拆帧（必须练到秒懂）

主站读 1 号从站、从 0x0000 起读 2 个保持寄存器：

```
01 03 00 00 00 02 C4 0B
│  │  └──────┘ └──────┘ └───┘
│  │  起始0x0000 数量0x0002  CRC16
│  └ 功能码=读保持寄存器
└ 从站地址 1

从站应答（两寄存器值 = 0x0FA0、0x0BB8）：
01 03 04 0F A0 0B B8 xx xx
│  │  │  └──────┴────┘
│  │  └ 4 字节=2 寄存器
│  └ 回的功能码（原码）
└ 我就是 1 号
```

**请求帧逐字节念一遍**：
- 第 1 字节 `01`：从站地址——"叫的是 1 号"，1 号竖起耳朵，其余从站装死；
- 第 2 字节 `03`：功能码——"读保持寄存器"，从站据此去查第四张表；
- 第 3~4 字节 `00 00`：起始地址 0x0000（16 位大端，高字节在前）——"从第 0 行开始"；
- 第 5~6 字节 `00 02`：数量 0x0002——"连读 2 个寄存器"；
- 第 7~8 字节 `C4 0B`：CRC16——**低字节 C4 在前、高字节 0B 在后**，从站重算对账，对不上装死。

**应答帧逐字节念一遍**：
- 第 1 字节 `01`：还是 1 号在回话；
- 第 2 字节 `03`：功能码原样奉还——"你问的就是这个"；
- 第 3 字节 `04`：**字节数**——"后面跟 4 字节 = 2 个寄存器 × 2 字节"，没有它主站不知道数据段多长；
- 第 4~7 字节 `0F A0 0B B8`：两个寄存器的值，大端各自拼接：0x0FA0=4000、0x0BB8=3000（如温度 40.00、湿度 30.00 的定点数——线上只跑整数，小数点位置是双方事先约好的：约定"实际值=寄存器值÷100"，4000 读出来就是 40.00）；
- 第 8~9 字节：CRC16，同请求帧规则（低前高后）。

**异常应答**：功能码 +0x80（如 0x83）+ 异常码（0x02=非法地址，0x03=非法数据，0x06=从站忙）——主站必须处理，不能只等正常帧。异常帧同样能手拆：`01 83 02 xx xx` 念出来就是——"我是 1 号；你问的读保持寄存器（0x03）出了异常（0x83 = 0x03|0x80）；原因是非法地址（0x02）"。

## 4. RTU 时序：3.5 字符静默（01 篇思考题揭晓）

这是什么：RTU 帧没有头尾标记，接收方怎么知道"这句话说完了"？约定：**说话人闭嘴 3.5 个字符的时间，就算一句话结束**——像老师讲课停顿超过三秒，学生就知道这题问完了。9600bps 下约 4ms（这笔账：1 字符≈10~11 位（8N1 或 8E1），3.5 字符≈35~38 位，除以 9600 就是 3.6~4ms）。

RS485 没有帧头分隔符，靠**静默期分帧**：线上安静 ≥3.5 字符时间 = 一帧结束。9600bps 下约 4ms。

```c
/* 从站侧：用定时器测静默（裸机版思路，RTOS 版用 Tick 计数） */
void RS485_IdleCheck(void)                  /* 主循环/定时器里周期调 */
{
    if (g_rxIdx > 0 && HAL_GetTick() - g_lastRxTick >= 4) {
        Modbus_ParseFrame(g_rxBuf, g_rxIdx);  /* 静默到 → 收到完整帧 */
        g_rxIdx = 0;
    }
}
```

**更好的姿势**：STM32 串口的 **IDLE 中断**（总线空闲中断）——硬件检测静默自动触发，不用软件掐表（07-STM32 篇 DMA 循环接收 + IDLE 的组合在 Modbus 从站是绝配）。

## 5. CRC16-MODBUS（必须手写一次）

这是什么：CRC 本质是**对整帧数据做一次"数学除法"，把余数当封条贴在帧尾**——数据任何一比特被干扰咬过，余数几乎必然对不上；比累加和强在"错位相消"在除法世界里极难发生。查表法 = 把除法的逐步运算预先算成 256 项表格，运行时一步一查。

多项式 0x8005（反映射 0xA001），初值 0xFFFF，低字节先发：

```c
/* 查表法：预生成 256 项表（代码体积换速度） */
static const uint16_t crcTable[256] = { /* ...生成代码见实操... */ };

uint16_t CRC16_Modbus(const uint8_t *data, uint16_t len)
{
    uint16_t crc = 0xFFFF;
    while (len--) {
        crc = (crc >> 8) ^ crcTable[(crc ^ *data++) & 0xFF];  /* 逐字节查表异或 */
    }
    return crc;                              /* 发送时低字节在前（小端） */
}
```

关键行拆解：
- `crc = 0xFFFF`：封条纸上先写好初值（协议规定，两端必须一致）；
- `crcTable[(crc ^ *data++) & 0xFF]`：拿"当前 CRC 低 8 位 XOR 新来的字节"当索引查表——这一步等价于 8 轮移位除法，查表把它压缩成一次数组访问；
- `crc >> 8` 再异或：把查表结果拼回 16 位寄存器，相当于"余数滚动前进"；
- 发送方拿到返回值后拆成两字节：**低字节先上总线**——这是"从站装死"类故障的头号根源（§9 坑表第一行）。

**标准测试向量**：`"123456789"` 的 CRC16-MODBUS = **0x4B37**——写完必须先过这个向量再上总线。

## 6. 从站实现骨架（FreeRTOS 任务版）

这是什么：从站的一生只有三件事——**听、查、答**。听（收帧入队）、查（地址+CRC+查表）、答（组帧回话）；没叫到自己（地址不符）和听不清（CRC 错）都装死。

```c
void ModbusSlaveTask(void *arg)             /* 挂在 08-FreeRTOS 三任务链上 */
{
    uint8_t frame[256]; uint16_t len;
    for (;;) {
        if (xQueueReceive(mbQueue, frame, portMAX_DELAY) == pdTRUE) {   /* IDLE 收帧入队 */
            len = ((frame[1] << 8) | frame[2]);                            /* 假设先收了长度，实际按地址+功能码判断 */
            if (frame[0] != MY_ADDR || !CRC_OK(frame, len)) continue;      /* 不是我的/校验错 → 静默丢弃（不回话！） */
            Modbus_Handle(frame, len);                                     /* 分发功能码 → 查表 → 组应答帧 */
            RS485_SendFrame(resp, respLen);                                /* 回话 */
        }
    }
}
```

**从站一次问答的时间线**（每步一句话）：

```
T1  IDLE 中断：总线静默了 → 把字节流打成完整帧丢进 mbQueue
T2  ModbusSlaveTask：从队列取帧 → 先看地址：不是我的 → 直接丢弃（连 CRC 都不验，省 CPU）
T3  是我的 → 验 CRC：错 → 依旧沉默（主站会超时重试）
T4  CRC 对 → 按功能码分发：0x03 查保持寄存器表 / 0x06 改一个 / 0x10 改一批
T5  组应答帧+补 CRC → 切 485 方向发回 → 发完切回收听，等下一帧
```

**从站三纪律**：地址不符装死（别抢答）；CRC 错不回应（让主站超时重试）；应答 < 3.5 字符静默后再听（防主站话没说完就插嘴）。

## 7. 主站轮询骨架与超时重试

这是什么：主站是班长——按花名册一个个问，每人限时 100ms，答不上来记一次"缺勤"，连续缺勤三次标"离线"上报。**超时重试与离线判定是主站和从站的本质区别**：从站可以装死，主站必须心里有账。

```c
uint8_t pollSlave(uint8_t addr, uint16_t reg, uint16_t cnt, uint16_t *out)
{
    BuildReadReq(req, addr, 0x03, reg, cnt);    /* 组请求帧+CRC */
    RS485_SendFrame(req, 8);
    if (WaitResp(resp, &rl, 100 /*ms 超时*/) == OK
        && resp[1] == 0x03
        && memcmp(&resp[2], ...) /* 长度/从站号/CRC 全核对 */) {
        for (i = 0; i < cnt; i++)
            out[i] = (resp[3 + i*2] << 8) | resp[4 + i*2];  /* 大端拼接 */
        return OK;
    }
    return ERR;                                  /* 超时/错帧 → 上层计数重试/标记离线 */
}
```

工业实战：连续 N 次超时 → 从站标记"离线"告警，恢复后自动回归——**没有重试与离线判定的 Modbus 主站不算完工**。

## 8. Modbus TCP 一眼懂

这是什么：把 RTU 那套"地址+功能码+数据"原封不动装进 TCP 包里寄走——**信不变，换了个快递公司**。CRC 省了（TCP 自带校验），地址域换成了 MBAP 头。

**MBAP 头逐字段念一遍**：

```
MBAP 头(7B)：事务ID(2) | 协议ID=0(2) | 长度(2) | 从站ID(1) || PDU：功能码+数据
```

- 事务 ID（2B）：请求编号——TCP 上可以连发多个请求，应答回来靠它配对（串口版靠"一次只问一个"天然配对，TCP 版必须显式编号）；
- 协议 ID（2B）：恒为 0——"我是 Modbus"；
- 长度（2B）：从"从站 ID"到 PDU 结束共多少字节；
- 从站 ID（1B）：RTU 的地址域在这里降级为路由标识（TCP 连接已定位到设备，它主要服务于"网关后再挂串口从站"的场景）。

- 去掉 CRC（TCP 校验兜底）、加 MBAP 头、一连接一从站（端口 502）；
- **功能码/寄存器模型与 RTU 完全一致**——写好 RTU 核心逻辑，换传输层即成 TCP（又是分层红利）。

## 9. 常见坑

Modbus 的故障分两类：**"根本没回音"**（接线/字节序/静默期）和"回了但数据不对"（地址基偏移/字节序拼接）。调现场卡住时先对下表分类，再逐行排查。

| 坑 | 现象 |
|----|------|
| CRC 字节序发反 | 从站永远不回（装死） |
| 寄存器地址 0 基 vs 1 基混乱 | 上位机读错一格（协议地址 0x0000，不少软件界面显示"40001"=保持寄存器区第 1 个——两个偏移叠加，新人杀手） |
| 忽略 3.5 字符静默 | 两帧粘连解析错 |
| 从站 CRC 错也回话 | 主站等待正常帧逻辑被打乱 |
| 一次读数量超限（>125 寄存器） | 从站回异常 0x03 |
| 波特率不匹配静默期 | 4ms 掐表在 9600 够用，115200 下要按公式重算 |

## 10. 章节小结

- 主从问答 + 四张表（线圈/离散输入/输入/保持寄存器）= Modbus 全部心智模型
- RTU 帧 = 地址+功能码+数据+CRC16（低前）；TCP = MBAP+同款 PDU
- 3.5 字符静默分帧 → STM32 上用 DMA+IDLE 中断硬件化
- 主站要有超时重试与离线判定；从站要"不对装死、错帧静默"

## 课后思考题

1. 为什么 Modbus 数据是大端（高字节在前）而 x86 内存是小端？（协议诞生于大端小型机时代，跨厂商总线的"网络字节序"传统（TCP/IP 同为大端）——字节序是"约定"不是"对错"，难点只在两套约定对接时的显式转换）
2. 从站收到"广播帧"（地址 0）该怎么处理？（执行但不回应——地址 0 是广播，谁回话谁撞车；这就是主站写广播命令后"没有确认"的原因，可靠性要靠再读回验证）
3. 若让从站支持"寄存器值变化主动上报"，如何改造且不破坏主从模型？（Modbus 本身不支持主动上报（从站无发言权）——方案：主站高频轮询；或升级为"从站有网口"用 MQTT 上报（07 篇）；工业上还有 Modbus+事件记录表供主站事后拉取——理解"协议模型的边界"比记住功能码更重要）
