# 07 · MQTT 与综合项目：设备上云（阶段毕业）

> 目标：掌握 MQTT 发布订阅模型与 QoS/遗嘱机制；毕业项目——把 FreeRTOS 多传感器系统接入 MQTT，实现云端可看、可告警的完整物联网链路。

## 1. 发布/订阅：MQTT 的世界观革命

这是什么：1000 台设备两两直连要 50 万条线，任何一台掉线就乱套。MQTT 的答案：**所有人只跟邮局（Broker）打交道**——寄信的写清"话题"投进邮局，收信的向邮局订阅话题，谁也不认识谁，送达由邮局保证。这就是"发布/订阅"。

传统 TCP 通信 = 点对点（A 连 B 私聊）。MQTT 引入**中间人 Broker（消息代理）**：

```
[温湿度设备] --publish "home/bedroom/temp", 25.3--> [Broker（邮局）]
                                                        │ 按话题分发
[手机App] --subscribe "home/bedroom/#"--> 收到 25.3
[网页面板] --subscribe "home/#"--> 收到 25.3
```

| 对比 | 点对点 TCP | MQTT 发布订阅 |
|------|-----------|---------------|
| 耦合 | 收发双方必须同时在线 | 通过 Broker 解耦，收方不在线补发 |
| 一对多 | 自己写广播逻辑 | 话题天然广播 |
| 设备身份 | 互相知道 IP | 只认话题名，IP 无关 |

类比：**群聊**——设备发到"群话题"里，谁订阅谁收到；发的人不用管群里有谁、在不在线（邮局 Broker 兜底）。**这就是物联网选 MQTT 而非裸 TCP 的根本原因：弱网、海量设备、多消费者。**

## 2. 核心概念四件套

这四件套（话题/QoS/遗嘱/心跳）就是 MQTT 的全部心智模型——分别回答：**发给谁、丢了怎么办、死了谁知道、活着怎么证明**。

### 2.1 话题（Topic）：分层的地址

这是什么：话题就是 MQTT 世界的"收件地址"——按 `/` 分层，像小区/楼栋/单元/门牌：`home/bedroom/temp` = 家/卧室/温度。通配符让你能"订整个小区的信"。

```
home/bedroom/temp          ← 发布到这
home/+/temp                ← + 匹配单层：bedroom/living 都收
home/#                     ← # 匹配多层全部：整个家的消息全收
```

规则：以 `/` 分层；`+` 单层通配、`#` 多层通配（只能放末尾）；**别用中文/空格/超长话题**。

### 2.2 QoS：消息质量三档（面试必考）

这是什么：QoS 回答一个问题——**"这条消息丢了/重了，你打算怎么办"**。三档就是三种寄信方式：QoS0 = 往报箱塞传单（塞完就忘，丢没丢不知道）；QoS1 = 挂号信（对方签收才算完，没签收就再寄，所以可能收到两封）；QoS2 = 签合同（双方核对编号、确认、再确认，保证一份且只有一份）。

| QoS | 语义 | 机制 | 成本 |
|-----|------|------|------|
| 0 | 至多一次（发完就忘） | 火不过夜 | 可能丢 |
| 1 | **至少一次** | PUBACK 应答，没收到就重发 | 可能重复 |
| 2 | 恰好一次 | 四步握手（PUBREC/PUBREL/PUBCOMP） | 最慢最贵 |

**QoS1 的完整时间线**（每步一句话：谁在做什么）：

```
T1  发布者：发出 PUBLISH（带报文 ID，如 42）
T2  Broker：收到 → 转发给订阅者 → 回 PUBACK(42)
T3  发布者：等到 PUBACK(42) → 这一单完结
T3' 发布者：超时没等到 → 认为丢了 → 重发 PUBLISH(42)
    （Broker/订阅者可能因此收到两遍——这就是"至少一次"的重复来源）
```

**QoS2 的四步握手时间线**：

```
T1  发布者 → Broker：PUBLISH(42)（"我要发 42 号消息"）
T2  Broker → 发布者：PUBREC(42)（"42 号收到并记下，先别发第二遍"）
T3  发布者 → Broker：PUBREL(42)（"确认，这单正式交付"）
T4  Broker → 发布者：PUBCOMP(42)（"交付完毕，42 号编号作废可复用"）
```

**工程选择**：遥测数据 QoS 0~1（丢一帧无所谓，下一帧马上来）；**控制命令/告警 QoS 1 起**（漏一条是事故）；QoS 2 极少用。**"够用就好"再次胜出。**

接收端去重小抄：QoS1 的"可能重复"靠**报文 ID + 业务层幂等**兜底——比如 LED 命令带序号，执行过的序号直接忽略（呼应 02 篇 SEQ 去重，同一个思想换了个楼层）。

### 2.3 遗嘱消息（LWT）：设备的"讣告"

这是什么：设备被拔电源/断网时**来不及说再见**——订阅端怎么区分"它死了"和"它只是没数据"？遗嘱 = 入职时签的"代发讣告委托"：我失联了，请邮局替我喊一嗓子。

连接时预登记："如果我异常掉线，请替我在 `home/bedroom/status` 发 `offline`"。

```c
/* Broker 检测 keepalive 超时/连接异常 → 自动代发遗嘱 → 订阅端立刻知道设备死了 */
```

**遗嘱触发的时间线**（每步一句话）：

```
T1  设备连接时：CONNECT 包里夹带遗嘱（话题+内容"offline"）——Broker 存档但不发
T2  设备失联（拔电/断网）：再也无法发任何包
T3  Broker：keepalive 超时（§2.4）到点 → 判定失联 → 代发遗嘱 offline 到 status 话题
T4  订阅端（手机/面板）：立刻收到 offline → 界面灰显
```

配套：上线时主动发 `online` 到同一话题（**遗嘱+上线报备 = 设备在线状态机**，智能面板的"离线"灰显就靠它）。注意分工：`online` 是设备自己说的（主动报备），`offline` 是 Broker 代说的（设备已不能说话）——**两个说话人，一个话题**。

### 2.4 KeepAlive 与 PING：心跳保活

这是什么：TCP 连接"看起来还在"，不代表对端"人还在"——拔电源、中途断网都能让连接变成"幽灵"。心跳就是定时喊一声"在吗"，喊不应才判死——既不把"没数据"误判成"死了"，也不把"死了"当成"还活着"。

连接时约定 keepalive（如 60s）——期间至少发一个包，没业务就发 `PINGREQ`。Broker 超时没动静 → 判死 → 发遗嘱。**这与 06 篇"心跳探活 AT"是同一个思想：拿不到心跳=默认死亡。**

## 3. 完整连接流程（一次看懂）

这是什么：MQTT 会话的建立是一场有先后顺序的"报到流程"——先建 TCP 管道，再亮明身份，被认可后才能收发。**顺序错一步（如 CONNECT 没成功就发订阅）会被静默丢弃**——这是新手第一大坑。

**报到流程时间线**（每步一句话：谁在做什么）：

```
T1  客户端：TCP 三次握手连上 broker:1883（05 篇 socket 台阶的活）
T2  客户端：发 CONNECT 包——亮身份（ClientID）、递凭证（用户名/密码）、
    约心跳（keepalive）、交遗嘱（LWT）
T3  Broker：验身份 → 回 CONNACK（"认可，开始营业"）
    ——收到 CONNACK 之前发的任何 SUBSCRIBE/PUBLISH 都是无效的
T4  客户端：SUBSCRIBE "cmd/led" → Broker 回 SUBACK（订阅成功回执）
T5  客户端：PUBLISH "data/temp" → QoS1 时等 PUBACK；此后循环"上报+收命令"
```

```
TCP connect(broker:1883)          ← 05 篇 socket 三台阶的成果直接用
CONNECT 包：ClientID + 用户名/密码 + keepalive + 遗嘱
    ↓
CONNACK（连接认可）                ← 此后才能收发
    ↓
SUBSCRIBE "cmd/led"（订阅命令话题）→ SUBACK
PUBLISH "data/temp"（发布数据）     → QoS1 时等 PUBACK
```

（原图保留作速记版。）

**安全提示**：1883 是明文端口（调试用），公网产品用 **8883（TLS）**——证书校验+加密，MQTTS。学习阶段用 EMQX 公共 Broker（broker.emqx.io:1883）即可。

## 4. 实现路径（两条腿）

这是什么：上 MQTT 有两条路——让模组代管 MQTT 协议（MCU 只发 AT 文本命令，快），或 MCU 自己跑 MQTT 客户端库（连打包都自己干，深）。入门先走第一条，想懂协议走第二条。

| 方案 | 说明 | 适合 |
|------|------|------|
| **AT 模组自带 MQTT**（ESP8266/ESP32 新版固件 `AT+MQTTUSERCFG/MQTTPUB`） | 模组代管协议，MCU 发文本命令 | 快速落地（推荐入门） |
| STM32 跑 **MQTT 客户端库**（MQTT-C/paho.mqtt.embedded-c）+ LwIP socket | 自己管协议（CONNECT/PING 打包） | 深入理解+以太网方案 |

AT 版连接示例（串口三连）：

```
AT+MQTTUSERCFG=0,1,"dev001","user","pass",0,0,""     （账号配置+遗嘱可在此带）
AT+MQTTCONN=0,"broker.emqx.io",1883,1                （连 Broker，keepalive 60s）
AT+MQTTSUB=0,"cmd/dev001/led",1                       （订阅控制话题 QoS1）
AT+MQTTPUB=0,"data/dev001/temp","25.3",1,0            （发布遥测）
```

参数白话：`USERCFG` 开头的 `0,1` = 链接 ID 0 + 协议类型 1（MQTT over TCP）；`MQTTPUB` 结尾的 `,1,0` = QoS1 + retain=0——retain 置 1 时 Broker 会留底最后一条消息，后订阅的人一上线就能收到。

库版核心结构（MQTT-C 风格，伪码）：

```c
mqtt_connect(&client, sock, "dev001", ... /* 含 will 话题 */);
mqtt_subscribe(&client, "cmd/dev001/led", 1);
for (;;) {
    mqtt_sync(&client);                       /* 收发泵：处理 PUBACK/PINGREQ/下行消息 */
    if (haveNewTelemetry())                   /* dataQueue 来了新数据（08-FreeRTOS 队列） */
        mqtt_publish(&client, "data/dev001/temp", payload, len, 1, 0);
    osDelay(100);
}
```

**下行命令处理**：`publish` 收到 `cmd/dev001/led "on"` → 回调里解析 → 发队列给执行任务 → 执行后回发状态到 `status/dev001/led`（**命令+状态回执 = 可信控制**）。

## 6. 常见坑

MQTT 的坑大多不体现在"连不上"，而是"连上了但消息没了/多了/迟了"——按"会话建立→收发→断线恢复"三个阶段排查下表。

| 坑 | 现象 |
|----|------|
| ClientID 重复 | Broker 互踢，随机断连（多设备务必唯一，用 MAC 尾号） |
| keepalive 期间不发 PING | 60s 后被踢（遗嘱误发"离线"） |
| 订阅放在 CONNECT 成功前 | SUBSCRIBE 被静默丢弃（先 CONNACK 再订阅） |
| QoS1 无 PUBACK 处理 | 消息重发风暴/丢失（必须处理应答） |
| 回调里直接干重活 | 阻塞收发泵（下行只入队列，慢活给任务） |
| 1883 上公网裸奔 | 凭据明文被嗅探（产品必须 TLS+独立账号） |
| 断线后不重订阅 | 重连成功但收不到命令（clean session 时 Broker 不记忆订阅！） |

表里 clean session 的白话：连接时跟 Broker 约定的"会话模式"——clean=1 表示"断线即忘"，Broker 不保存你的订阅与离线消息（设备端图省事常用），所以重连后必须重新订阅；clean=0 则由 Broker 替你记着会话，配合 QoS1 还能补发离线期间的消息，代价是 Broker 多占内存。

## 课后思考题

1. 为什么 MQTT 选 TCP 而不是 UDP？（可靠有序由 TCP 兜底（05 篇），MQTT 专注"发布订阅语义"；丢消息处理下沉到 QoS 机制——分层复用，不重造轮子）
2. 设备 A 发布后自己掉线，订阅者 B 还能收到这条消息吗？（已送达 Broker 就能（Broker 存活即转发）；若要"离线补发"需 persistent session + QoS1 且订阅在线——**在线时机与会话保持决定消息可达性**，产品保活设计的关键）
3. 如果让你设计"1000 台设备各上报 1 个温度"的云端架构，话题怎么组织？（工厂/楼层/设备三级：`plant1/floor2/dev007/temp`；云端按 `plant1/#` 汇聚——话题即组织架构，运维按通配符聚合订阅；再加 `dev007/status` 在线监控——**命名即架构**）
