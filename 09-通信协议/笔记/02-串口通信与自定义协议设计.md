# 02 · 串口通信与自定义协议设计

> 目标：把 UART 从"会用外设"升级到"懂协议"——帧格式逐位吃透、波特率误差会算、自定义协议含转义透明传输、状态机解析完整落地。本篇是 01 篇（物理层家族）与 03 篇（Modbus）之间的桥梁：Modbus 就是"串口协议设计"的工业级范本。

## 1. UART 帧格式：逐位拆解（协议的本体）

这是什么：UART 是最小单位的"说话规矩"——一次说一个字节：先拉低喊一声"注意"（起始位），再从最低位到最高位把 8 个 bit 摆上线，最后抬手示意"说完了"（停止位）。没有地址、没有帧头——它是"字母"级协议，"单词和句子"要靠上层自己组织（§3）。

UART 没有"协议头"概念——它只有一种固定的小帧：

```
空闲(高) │ 起始位 │ D0 D1 D2 D3 D4 D5 D6 D7 │ [校验位] │ 停止位 │ 空闲(高)...
   1     │   0    │   LSB 先发 → MSB 最后     │  0/1     │   1    │
```

| 组成 | 电平 | 作用 |
|------|------|------|
| 空闲态 | 高电平 1 | 总线没事时的"默认站姿" |
| **起始位** | 低电平 0 | 通知接收方："数据来了，开始对表" |
| 数据位 | 5~9 位（常用 8） | 真数据，**LSB（最低位）先发** |
| 校验位（可选） | 0/1 | 奇/偶校验（01 篇：只能查 1 位错，弱） |
| **停止位** | 高电平 1（1/1.5/2 位） | 帧结束标记，保证两帧间有高电平隔离 |

**三个关键认知**：
1. **"高=1、低=0"只对 TTL 成立**——RS232 反相（负电平=1），485 看差分（01 篇家族表），但**帧格式三者相同**：协议（怎么组织位）与物理层（用什么电压表达位）正交，这就是分层的力量；
2. **起始位下降沿=同步锚点**——UART 是异步通信，没有时钟线，双方靠约定波特率+起始位对齐；每帧重新对表一次，误差不累积；
3. **接线交叉**：TX→RX、RX→TX、GND 共地——调试串口不通，第一步就查这三根线（交叉忘了=各说各话）。

**示波器实测**（逻辑分析仪更佳）：9600bps 时一位 ≈ 104μs，抓一帧 `0x55`（01010101）看方波节拍，对帧格式的理解胜过读十遍文档——实操任务必做。

**把 0x55 这一帧逐位"念"出来**（8N1，9600bps）：

```
空闲(高) → 起始位拉低(0)：接收方在此对表 → 发 D0=1（线抬高 104μs）
→ D1=0 → D2=1 → D3=0 → D4=1 → D5=0 → D6=1 → D7=0
（LSB 先行：0x55 的最低位是 1，所以线序是 1、0、1、0、1、0、1、0——标准方波）
→ 停止位拉高(1)：一帧收工 → 总线回空闲，等下一帧
```

0x55 是 UART 教学的"标准音"；0xAA 是它的反相兄弟（线序 0、1、0、1、0、1、0、1）。

## 2. 波特率与误差：为什么 STM32 用 11.0592MHz（51 时代遗留的智慧）

这是什么：UART 没有时钟线，双方全靠"各自的手表"（波特率）约定节拍——两只表有快慢，误差就像长跑拉开的身位，一位一位累积，到帧尾可能错到把 1 采成 0。本节回答：误差多大算大？什么时钟才养得起串口？

接收方在**每位的中点采样**（16 倍过采样：起始位下降沿后数 8 个采样时钟到中点）。若收发双方波特率有偏差，越到帧尾累计越大：

```
误差容忍 ≈ ±2.5%（最后一位中点仍要在位宽内）
8N1 帧共 10 位 → 总偏差容忍 ≈ 2.5%
双方向各摊一半 → 每侧约 ±1.2% 安全线
```

- **51 用 11.0592MHz 的真相**：9600 = 11059200/12/32/3 整除无误差（式子里 12=51 每 12 个时钟才算 1 个机器周期、32=串口内部固定分频、3=定时器重装值 256−253——分母全是整数，除出来才没有小数误差）；用 12MHz 算出重装值 256−TH1=6.51（SMOD=1 口径），TH1≈249.5 非整数 → 取整 249 后误差 6.99% → **必乱码**（06-51 05 篇推导的理论补全）；
- STM32 的 BRR 带 4 位小数分频，72MHz 下 115200 误差仅 0.02%——硬件进化消化了问题，但**内部 RC 时钟（HSI ±1%）跑高速串口仍会偶发乱码**（06 篇模组坑表的根源）；
- 工程习惯：串口不通先查两端波特率实测值（逻辑分析仪量位宽反推），再查时钟源。

## 3. 自定义协议完整设计：从"能发字节"到"可靠对话"

这是什么：UART 只保证"每个字母都送到了"，不保证"这句话完整、没重复、没串台"。要"对话"，得自己定义句子结构。还是寄快递那套：**帧头=纸箱+面单抬头、LEN=面单件数、CMD=收件部门、SEQ=快递单号、PAYLOAD=货物、CRC16=封条**。

UART 帧只保证"一个字节不坏"，**一串字节有没有被截断/重复/串包，UART 不管**——应用层协议的职责。完整模板（01 篇骨架的满血版）：

```
│ 帧头 0xAA 0x55 │ 长度 LEN │ 命令 CMD │ 序号 SEQ │ 数据 PAYLOAD │ CRC16 │
│      2B        │    1B    │    1B    │    1B    │      nB      │  2B   │
```

**完整报文实例（逐字节标注）**——"主站让 1 号从站把灯调到 50%"，请求帧（本例约定 LEN = CMD+SEQ+DATA 的字节数）：

```
AA 55 03 01 07 32 xx xx
│  │  │  │  │  │  └─┴── CRC16（对 01 07 32 计算，低字节在前）
│  │  │  │  │  └ DATA = 0x32 = 50（亮度 50%）
│  │  │  │  └ SEQ = 0x07（第 7 号"对话"；应答帧会带回同一个 07）
│  │  │  └ CMD = 0x01（"设置亮度"命令）
│  │  └ LEN = 0x03（本例口径：CMD+SEQ+DATA 共 3 字节）
│  └ 帧头第 2 字节 0x55
└ 帧头第 1 字节 0xAA
```

应答帧（示例约定：原命令回执+同 SEQ+执行结果）：`AA 55 03 01 07 01 xx xx` ——读出来就是"1 号从站对第 07 号'设亮度'命令的回执：执行成功（0x01）"。**主站凭相同的 SEQ 认领回话**。

比 01 篇多出 **SEQ 序号域**，三大用途：
1. **应答配对**：应答帧带相同 SEQ，主站知道回的是哪条命令（超时重发后不认错答案）；
2. **去重**：重发后对方可能收到两次（上次其实到了但应答丢了）——SEQ 相同的重复帧丢弃；
3. **丢包检测**：SEQ 跳号=中间丢了包。

SEQ 的生活类比：**奶茶店取餐号**——下单拿了 07 号，叫号对上才取餐；叫了没回应你会再叫一次（重发），店员不会因为叫两遍就做两杯（去重靠同号）。

这正是 TCP 序号思想（05 篇）的微缩版——**自己设计协议时，问自己"TCP 那些机制（序号/确认/重传/校验）我需要哪几个"**。

### 3.1 转义与透明传输：数据里出现帧头怎么办

这是什么：定界符是"句号"，可万一正文里本来就要写"句号"呢？转义就是定一条暗号："正文里的句号写成'。_'，收到'。_'还原成句号"——正文再"脏"也不会被误断句。

若 PAYLOAD 里恰好有 `0xAA 0x55`，接收方会误判帧头。解法=**转义法**（串口界标准做法，HDLC/PPP 同款思路）：

```
发送侧：帧定界符 0xC0；数据中 0xC0 → 0xDB 0xDC；数据中 0xDB → 0xDB 0xDD
接收侧：收到 0xDB 必看下一字节还原；连续两 0xC0 之间 = 一帧
```

**转义实例**：要发数据 `C0 AB C0`（0xC0 是定界符）——线上实际跑的是：

```
C0 [DB DC] AB [DB DC] C0
│   帧内容逐字节转义后原样到达      │
开帧                              闭帧
```

接收侧逐字节扫：看到 0xDB 就把下一字节按表还原（DB DC→C0，DB DD→DB）——数据里藏再多 0xC0 也污染不了帧边界。

代价：最坏情况长度翻倍（全 0xC0 数据）——用**长度域+CRC**的帧（本篇模板）可以**不转义**（靠 LEN 精确知道数据段边界，帧头撞上概率被状态机+校验双重过滤），但**流式无长度协议（如日志流）必须转义**。选型：

| 方案 | 适用 | 代价 |
|------|------|------|
| 长度域 + CRC（不转义） | 有明确 LEN 的结构化帧 | 数据段内出现假帧头要靠校验兜底 |
| 转义法 | 流式数据/无长度域 | 长度膨胀+编解码复杂度 |
| COBS 编码 | 高效转义替代 | 膨胀仅 1 字节（进阶） |

COBS 的白话：它保证编码后的数据里不含 0x00，于是可以拿 0x00 独占当帧定界符——每个字节记录"距下一个 0x00 还有几步"，代替 0xDB 那种成对转义符，最坏也只膨胀 1 字节。

### 3.2 完整状态机解析（含转义还原，可直接抄）

这是什么：字节是一个一个进的、随时可能断，解析器就像海关安检员——没看见箱子（帧头）时对散件视而不见，见了箱子才按流程验货。**状态机的每个状态就是安检流程的一步，`switch` 就是他手里那张流程单**；状态之间是单行道，走完（无论成败）都回到起点，绝不纠缠。

**先看时间线：一帧 `AA 55 03 01 07 32 crcL crcH` 进站时，状态机怎么走**（每步一句话：谁在做什么）：

```
T1  收到 0xAA：S_HEAD1 → "可能是帧头第 1 字节"，转 S_HEAD2 等第 2 字节
T2  收到 0x55：帧头坐实 → 转 S_LEN 等面单
T3  收到 0x03：记下 LEN，清零缓冲与 CRC 累加器 → 转 S_PAYLOAD 开始收货
T4  收到 0x01/0x07/0x32：逐个存入缓冲、边存边算 CRC → 收满转 S_CRC_LO
T5  收到 crcL/crcH：与本地算的 CRC 对账 → 相等 FRAME_OK，不等 FRAME_BAD
T6  无论成败：状态回 S_HEAD1，准备下一帧（单行道，绝不回头纠缠）
```

```c
typedef enum { S_HEAD1, S_HEAD2, S_LEN, S_PAYLOAD, S_CRC_LO, S_CRC_HI } ParseState;

typedef struct {
    ParseState state;
    uint8_t  len, idx;
    uint8_t  buf[256];
    uint16_t crcCalc;
} FrameParser;

/* 每收到 1 字节喂一次（ISR/队列里逐字节调用，C 笔记10 模板的转义版） */
int Parser_Feed(FrameParser *p, uint8_t b)
{
    switch (p->state) {
    case S_HEAD1:   p->state = (b == 0xAA) ? S_HEAD2 : S_HEAD1; break;
    case S_HEAD2:   p->state = (b == 0x55) ? S_LEN : S_HEAD1;   break;
    case S_LEN:
        if (b > 240) { p->state = S_HEAD1; break; }             /* 长度合法门（防假帧头） */
        p->len = b; p->idx = 0; p->crcCalc = 0xFFFF; p->state = S_PAYLOAD; break;
    case S_PAYLOAD:
        p->buf[p->idx++] = b;
        p->crcCalc = CRC16_Update(p->crcCalc, b);               /* 边收边算 CRC */
        if (p->idx >= p->len) p->state = S_CRC_LO;              /* 收满 LEN 字节（CMD+SEQ+DATA）转 CRC 段 */
        break;
    case S_CRC_LO:  p->buf[p->idx++] = b; p->state = S_CRC_HI;  break;
    case S_CRC_HI: {
        uint16_t crcRx = (uint16_t)(p->buf[p->idx-1] | (b << 8)); /* 低字节先收：先收的低字节放低位 */
        p->state = S_HEAD1;                                     /* 无论成败都回初始态 */
        return (crcRx == p->crcCalc) ? FRAME_OK : FRAME_BAD;
    }
    }
    return 0;
}
/* 配套：100ms 定时检查"半帧卡住"→ 强制回 S_HEAD1（01 篇超时复位军规） */
```

**switch 每个分支在干嘛（对照安检流程单）**：

- `S_HEAD1`：候检区。不是 0xAA 的字节一律无视——垃圾流量在门口就被弹开；
- `S_HEAD2`：只认 0x55。不是就打回 S_HEAD1（注意是"打回"而不是"原地死等"——防止 `AA 00 AA 55` 这种序列漏掉真帧头）；
- `S_LEN`：验面单。长度超 240 直接拒收转回 S_HEAD1——假帧头在第一道门就被拦下；
- `S_PAYLOAD`：装货+同步贴封条。边收边算 CRC（流水化，大帧不卡顿），收满"LEN 口径约定的字节数"（本实现为 `p->len`，即 CMD+SEQ+DATA 的字节数，移植时把你自己的 LEN 口径写死在注释里）转 CRC 段；
- `S_CRC_LO` / `S_CRC_HI`：对账。注意 `S_CRC_HI` 分支里**无论对错都先回 S_HEAD1 再返回结果**——坏帧不会毒害下一帧的解析。

**设计要点回顾**：状态机驱动（不是 find+memcpy）、长度合法门（假帧头早期拦截）、边收边算 CRC、超时兜底——四件套齐了才叫"可靠解析"。

**超时兜底的时间线**（配套的 100ms 定时检查）：

```
T0  收到 AA 55 03 后，线路被干扰掐断，状态机停在 S_PAYLOAD
T1  之后每 100ms 定时器问一句："最近还有新字节吗？"
T2  发现"收了半截但 100ms 没动静" → 强制回 S_HEAD1，丢弃半帧
T3  下一个真帧头照常入场，链路自愈
```

没有这一步，一个坏字节能让解析器"卡在半路"等到天荒地老（见 §6 坑表）。

## 4. 调试三板斧与乱码排查树

这是什么：串口不通时最忌"到处乱改"。三板斧的核心思想是**二分隔离**——先证明"我这边没问题"（环回），再让仪器说话（抓波形），最后找中间人对质（监听）。排查树则把"瞎猜"变成"按命中率查表"。

**三板斧**：
1. **环回测试**：TX 短接 RX，发什么收什么=MCU 侧没问题（隔离"我 vs 对方"）；
2. **逻辑分析仪抓波形**：量位宽反推波特率（104μs≈9600），逐位核对帧格式——**串口问题最终仲裁者**；
3. **USB 转 TTL + 串口助手**：中间人监听，看谁的话不对。

**乱码排查树**（按命中率排序）：

```
乱码/无输出
├─ 波特率两端不一致？（最常见，量位宽确认）
├─ TX/RX 没交叉？GND 没共地？
├─ TTL/RS232 电平直连了？（反相+超压，01 篇坑）
├─ 时钟不准？（HSI 跑 115200 → 降 9600 或换 HSE）
├─ 数据位/停止位/校验位配置不一致？（8N1 两端要对齐）
└─ 只坏个别字节 → 485 切方向早于 TC / 地环路干扰
```

## 5. 与 STM32 外设的衔接（细节在 07-STM32 04/05 篇）

这是什么：协议层（本篇）与外设层（收发怎么搬运）是两本账——本篇管"句子怎么组织"，STM32 篇管"字母怎么搬"。这里只交代两本账交界处的关键姿势：

- 收发三姿势：阻塞/中断/DMA——**DMA 循环 + IDLE 空闲中断**是不定长帧的最优解（03 篇 Modbus 从站就用它，硬件化"静默分帧"）；
- printf 重定向（fputc）、环形缓冲收发架构（C 笔记11 落地）——外设层技能清单见 07-STM32 04 篇，本篇不重复，聚焦协议层。

## 6. 常见坑

| 坑 | 现象 |
|----|------|
| 12MHz 晶振硬算 9600（51） | 7% 误差必乱码 |
| 只等 TXE 不等 TC 就关串口/切 485 方向 | 尾字节丢失（01 篇头号坑的协议层表述） |
| 假帧头不加长度门 | 数据里撞上 AA55 就解析崩（后续全错） |
| CRC 收完再整体重算 | 大帧费时（边收边算流水化） |
| 重发后不查 SEQ | 同一命令执行两次（开关灯类命令=事故） |
| 忽略半帧超时 | 一个坏字节永久卡死状态机 |
| HSI 时钟跑高速串口 | 偶发乱码（温漂+出厂误差） |

## 7. 章节小结

- UART 帧=起始位+LSB 数据+校验+停止位；下降沿即同步锚点，每帧对表误差不累积
- 波特率误差容忍 ±2.5%，双方向各摊一半；11.0592 的智慧=BRR 整除，HSI 高速会露馅
- 自定义协议四域：帧头/长度/CRC/序号——SEQ 解决"应答配对/去重/丢包检测"，TCP 思想微缩版
- 无长度域的流式数据必须转义（0xDB 法/COBS）；状态机+长度门+边收边算+超时=可靠解析四件套
- 调试三板斧：环回隔离、逻辑分析仪仲裁、串口助手监听；乱码先查波特率与接线

## 课后思考题

1. 为什么 UART 校验位"可有可无"而 CRC 不能省？（奇偶校验只查单比特错，串口突发干扰常连坏多位（查不住）且字节内错不等于帧错；帧级 CRC16 才是工业可靠线——校验粒度要匹配错误模式）
2. 如果只有一根线（半条 UART，如单总线调试口）能通信吗？（能：半双工轮替（像 485 无方向线的版本），靠协议约定轮次+超时接管——1-Wire 就是极值案例（一根线供电+通信）；**协议设计能在物理层残缺时补位**，但代价是复杂度）
3. 对比"长度域帧"与"转义流"两种方案在 OTA 固件传输（08 篇）中的选择？（OTA 用长度域+分块+SEQ+CRC（结构化、可断点续传、校验独立）；转义方案对 200KB 二进制会膨胀且逐字节状态机慢——**块化结构传输选长度域，连续字节流才选转义**）
