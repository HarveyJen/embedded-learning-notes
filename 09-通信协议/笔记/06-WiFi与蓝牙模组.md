# 06 · WiFi 与蓝牙模组：无线两条腿

> 目标：掌握"MCU+AT 模组"的无线联网套路（ESP8266/ESP32），理解透传模式；了解 BLE 广播与连接模型，为 07 篇 MQTT 铺路。

## 1. 为什么要"模组"：射频是专业的事

这是什么：STM32 自己发不了 WiFi——射频（2.4GHz 调制、功率校准、天线匹配）是另一个专业，且无线产品必须过认证。工程惯例：**MCU 出脑、模组出力**——用串口发文本命令遥控模组联网，就像老板不亲自开车，雇个专职司机（模组）。

WiFi/BLE 射频（2.4GHz 调制、功率校准、天线匹配）设计门槛高，且模组已过**无线认证**（SRRC/CE/FCC）——工程惯例：MCU 负责业务，射频交给模组。两种协作姿势：

| 姿势 | 结构 | 说明 |
|------|------|------|
| **AT 指令模式** | STM32 --UART--> ESP8266/ESP32 模组 | MCU 发文本命令控模组（本篇主线） |
| **透传模式** | 串口数据 ≈ 网络数据 | 配好后模组变"无线网线" |
| 芯片当主控 | ESP32 单芯片跑业务+WiFi | 不用 STM32，ESP-IDF/Arduino 开发 |

## 2. AT 指令：模组的遥控命令行

AT = Attention（源自调制解调器时代）。格式：`AT+命令[=参数]\r\n`，模组回 `OK`/`ERROR`/`+事件`。

### 2.1 ESP8266 STA 模式连 WiFi 全流程（背下来）

做什么：七条命令把模组从"通电砖头"带到"TCP 已连接"——像给新人办入职：先确认他听得见你（AT），再定身份（CWMODE）、安宿舍（CWJAP）、派工位（CIPSTART），最后才交活（CIPSEND）。

**时间线读法**：每行都是"MCU 发一句 → 模组答一句"，**上一句没等到 OK 别发下一句**——AT 流程是严格的一问一答。

```
AT                          → OK                    （握手：波特率/接线对了没）
AT+CWMODE=1                 → OK                    （STA=连别人的站模式）
AT+CWJAP="SSID","password"  → WIFI CONNECTED / WIFI GOT IP   （连路由器，几秒）
AT+CIFSR                    → +CIFSR:STAIP,"192.168.1.101"   （查自己 IP）
AT+CIPSTART="TCP","192.168.1.5",8888  → CONNECTED  （TCP 连服务器——05 篇 echo 服务器！）
AT+CIPSEND=5                → >                     （要发 5 字节，模组回">"等你打字）
hello                       → SEND OK               （数据上网络了）
AT+CIPCLOSE                 → OK                    （挂断）
```

顺带把 CWMODE 三档说全：1=STA（连别人）、2=AP（自己当热点）、3=STA+AP 混合——做联网上报的设备几乎只用 1。

**注意**：`CIPSEND` 是"先报长度再发数据"的两段式——模组按字节计数组包，发多/发少都出错。

再补一个 AT 应答判读常识：模组的应答可能多行（`WIFI CONNECTED` 和 `WIFI GOT IP` 分两行到、中间隔几秒）——所以解析必须"按行循环匹配"（见 §3 的 AT_SendExpect 循环）。**拿一行就下结论**，是 AT 框架最常见的半成品写法。

### 2.2 透传模式（最省心姿势）

这是什么：透传 = 把模组变成一根**无线网线**——STM32 写串口就是写网络，读串口就是读网络，模组隐身。代价是"隐身"期间它不听指挥（AT 命令失效），退隐要靠 `+++` 暗号。

```
AT+CIPMODE=1                → OK      （进透传模式）
AT+CIPSTART=...             → CONNECTED
AT+CIPSEND                  → >       （从此进入"隐形"状态）
──此后串口进什么网络出什么，反方向亦然──
──退透传：独占发 "+++"（前后停 1 秒、不带回车）──
```

透传本质：模组变成**双向管道**，STM32 以为自己在写串口，实际在聊网络。**适合**：长连接固定服务器的产品（数据上报类）。**代价**：透传中不能发指令（退出要 `+++` 独占包），断线要靠心跳感知。

## 3. STM32 驱动模组的标准架构（重点：任务化）

这是什么：AT 交互有两个特点——发命令要等应答（同步），模组还会主动喊话（异步事件）。裸机里"死等 OK"会拖死整个系统，标准答案是**任务化+队列**：把"等"这个苦差事交给专门的等待者。

AT 交互 = "请求-应答 + 事件上报"混合体，必须异步驱动。**FreeRTOS 三件套架构**（08-FreeRTOS 队列思想直接复用）：

```
[发送任务] --AT命令--> [发送队列] --> [AT解析任务] --UART ISR/DMA 收字节--> 
                                             │ 匹配期待应答（OK/ERROR/事件）
                                             ├→ 应答信号量（唤醒等待的发送任务）
                                             └→ 网络数据 → [netQueue] → 业务任务
```

图怎么读（一分钟版）：发送任务把 AT 命令排进队列就走人（不傻等）；AT 解析任务是唯一的"话务员"——收模组的每一行，是应答就摇信号量叫醒等待者，是 `WIFI DISCONNECT` 这类事件就走事件分支，是网络数据就转发给业务任务。

简化版关键代码：

```c
/* 发一条 AT 并等指定应答（带超时） */
int AT_SendExpect(const char *cmd, const char *expect, uint32_t ms)
{
    AT_FlushRx();                                    /* 清旧数据防串包 */
    HAL_UART_Transmit(&huart3, (uint8_t*)cmd, strlen(cmd), 100);
    char line[128];
    TickType_t t0 = xTaskGetTickCount();
    while (xTaskGetTickCount() - t0 < pdMS_TO_TICKS(ms)) {
        if (AT_ReadLine(line, sizeof(line), 20)) {   /* 从接收环形缓冲取一行 */
            if (strstr(line, expect)) return AT_OK;
            if (strstr(line, "ERROR")) return AT_ERR;
            AT_DispatchEvent(line);                  /* WIFI DISCONNECT 等事件单独派发 */
        }
    }
    return AT_TIMEOUT;
}

/* 典型调用 */
if (AT_SendExpect("AT+CWJAP=\"Home\",\"12345678\"\r\n", "GOT IP", 15000) != AT_OK)
    xEventGroupSetBits(sysEvents, BIT_NET_FAIL);     /* 网络事件组（08-FreeRTOS 04 篇） */
```

AT_SendExpect 逐行拆解（一次"发命令等应答"的完整回合）：
- `AT_FlushRx`：先倒掉上一次对话的残渣——否则旧 `OK` 会冒充本次应答骗过匹配；
- `HAL_UART_Transmit`：把命令发出去（阻塞发送，几毫秒，可接受）；
- `while (…t0…)`：限时等待循环——不是死等，到点必须能退出；
- `AT_ReadLine`：按行取模组的话（20ms 没凑齐一行就继续转），拿到整行才做匹配；
- `strstr(expect)` / `strstr("ERROR")`：一行话三种命运——是期待应答 → 功成身退；是 ERROR → 报错返回；都不是 → 当事件派发（`WIFI DISCONNECT` 就在这里被拦下，而不是被当垃圾丢掉）。

**设计三纪律**：
1. **按行解析**（AT 全是行协议），环形缓冲 + "找 \r\n"；
2. **超时必须分层**：命令超时（几秒）、连网超时（15 秒）、TCP 建连超时（10 秒）——一刀切必翻车；
3. **事件要派发**：`WIFI DISCONNECT`/`CLOSED` 是模组主动喊的（不是应答）——单独事件处理触发重连，别当垃圾丢掉。

## 4. 断线重连：无线产品的生命线

这是什么：WiFi 路由器会重启、信号会漂移、服务器会维护——**断线不是故障而是日常**。产品的分水岭在于：断了能不能自己爬起来。重连状态机 + 指数退避（失败越久重试间隔越长，别对着关门的店反复砸门）就是"爬起来"的标准姿势。

WiFi 比 I2C 不可靠得多，**重连状态机**是标配：

```
NET_DOWN →(每5s)→ 重连WiFi → 成功 → 重连TCP/MQTT → 成功 → NET_UP
                │ 失败3次 → 退避加倍（5s→10s→20s…上限60s）│ 失败 → NET_DOWN
```

**断线后的时间线**（每步一句话：谁在做什么）：

```
T0  模组：主动喊"WIFI DISCONNECT"（§3 说的"事件派发"——绝不能丢）
T1  AT 解析任务：收到事件 → 置 NET_DOWN → 通知业务任务"网络没了，先别发"
T2  网络监控任务：按 5s 节拍探活/重连；失败一次退避翻倍（5s→10s→20s…）
T3  WiFi 回来了 → 按序重建：连 AP → 建 TCP/MQTT → 重新订阅话题（07 篇的坑：不重订阅收不到命令）
T4  全部就绪 → 置 NET_UP → 业务任务恢复上报（断线期间缓存的那一帧补发）
```

```c
void NetMonitorTask(void *arg)                       /* 08-FreeRTOS 软件定时器/任务 */
{
    for (;;) {
        if (!AT_SendExpect("AT", "OK", 1000)) {      /* 心跳探活：模组还活着吗 */
            ReconnectStateMachine();                  /* 指数退避重连 */
        }
        osDelay(5000);
    }
}
```

## 5. BLE：蓝牙低功耗一页入门

这是什么：经典蓝牙像"通话中不许挂"（一直连着费电），BLE 反过来——**不聊天就闭嘴省电，需要时先广播再秒连**。手环、温度贴、电子价签全是这个思路。

BLE 两态模型（与经典蓝牙"永远连接"不同）：

- **广播态（Advertising）**：设备定时喊话（37~39 号信道——三个广播信道散布在 2.4GHz 频段的开头/中间/末尾，无论 WiFi 占住哪一段，总有一个大概率干净，属于"分散下注"的抗干扰设计），喊话包 31 字节——iBeacon/温度信标/配网入口全在这。主机扫描广播即可收到数据，**连都不用连**；
- **连接态（Connection）**：主机（手机）发起连接 → GATT 服务模型：**Service → Characteristic（特征值）**，手机按特征值读/写/订阅（Notify）。

类比：广播=路边喊"新鲜草莓便宜卖"（谁路过谁听）；连接=进店慢慢挑（GATT 货架按标签取）。

GATT 名词只有三个要记：**Service（货架分区）→ Characteristic（货架上的商品）→ Notify（店员主动递货）**。手机订阅某个 Characteristic 后，设备有新数据（比如温度变了）就主动推——这就是传感器 App 实时刷新的机制。

**嵌入式应用套路**：传感器 → 放进 Characteristic → 手机 App/小程序订阅 Notify 展示。STM32+BLE 模组（JDY-23 等国产透传模组）= 串口透传+自动广播，上手比 WiFi 还快。

## 6. 模组选型速查

选型口诀：**看供电（能不能喂饱 300mA 峰值）、看接口（UART 够不够）、看认证（量产过没有）**——下表按预算和场景对号入座。

| 模组 | 价 | 强项 | 场景 |
|------|----|------|------|
| ESP8266-01S | ~8 | 最便宜、AT 成熟 | 简单 WiFi 上报 |
| ESP32-C3/WROOM | ~15~25 | WiFi+BLE 双模、算力强 | 主流首选 |
| ESP32 直接当主控 | ~20 | 省 MCU、ESP-IDF 生态 | 新项目联网核心 |
| JDY-23/Nordic 系 | ~10~40 | BLE 透传/低功耗 | 手机互联、可穿戴 |

## 7. 常见坑

模组的"玄学"表象（忽好忽坏、莫名复位）九成出在供电与时钟——下表按"物理层→协议层→应用层"排序，玄学故障先查前三行。

| 坑 | 现象 |
|----|------|
| 波特率不稳（模组默认 115200，用内部 RC 时钟的 MCU 偏差大） | 偶发乱码（换外部晶振/降波特率 9600） |
| 3.3V 供电不足（ESP8266 峰值 300mA+） | 发射瞬间复位重启（"AT 忽好忽坏"的头号元凶，加 470μF 电解） |
| CWJAP 密码含引号/特殊字符转义错误 | 一直 ERROR |
| CIPSEND 长度与实际不符 | SEND FAIL 卡死 |
| 透传退出 `+++` 带回车/不足停顿 | 退不出去（当普通数据发走了） |
| 事件没派发（WIFI DISCONNECT 丢掉） | 断网了业务还在傻等 |
| AT 响应与网络数据混流 | 解析状态机要按"AT 行 vs 原始数据段"分流（CIPMODE=0 时） |

## 8. 章节小结

- AT 指令=模组遥控器；连网五连：AT→CWMODE→CWJAP→CIPSTART→CIPSEND
- 透传=模组变管道，省心但断线要心跳感知；`+++` 独占退出
- STM32 驱动标配：按行解析 + 分层超时 + 事件派发 + 指数退避重连
- BLE=广播喊话 + GATT 连接服务；模组选型按场景对号入座
- **供电不足是"玄学故障"第一嫌疑人**——ESP 发射峰值电流先查电源

## 课后思考题

1. 为什么 ESP8266 发射瞬间会把"供电正常"的系统拉复位？（2.4GHz PA 峰值电流 300mA+，电源内阻×ΔI=ΔV 跌落 → 模组/同电源 MCU 电压跌破复位阈值——**电源阻抗意识**：大电容+短粗走线，BOM 篇"去耦/储能"思想的无线版）
2. AT 命令为什么用"文本+行"而不是二进制帧？（调试友好（人眼可读可手敲）、解析简单（strstr 即可）；代价是流量效率低——**协议设计在"人效率与机器效率"间取舍**，与 Modbus 二进制帧正好相反，两种取向都要会）
3. 透传模式和 AT+CIPSEND 模式，产品上怎么选？（固定服务器长连接选透传（CPU 零管理）；需要动态多连接/切换服务器选 AT 模式（灵活可控）——稳定性与灵活性永远在拔河）
